# AI 비서의 검색 조건 추출을 별도 단계로 분리하며 배운 점

렌트카 회사의 AI 비서를 개발하면서, 조회가 필요한 질문을 올바르게 선택해도 검색 조건이 흔들리면 답변이 달라질 수 있다는 문제를 경험했다. 같은 차량 조건으로 존재 여부와 차량번호를 각각 물었는데, 한쪽에는 차량이 있다고 답하고 다른 쪽에는 없다고 답했다.

이를 계기로 모델이 조회 방법을 선택하는 판단과 검색 조건을 만드는 판단을 나누었다. 검색 조건만 추출하는 별도 호출을 만들고, 서버도 모델명·연료·연식·사양을 각각 검사하고 검색하도록 바꿨다. 이 글은 그 설계의 의도와 기대, 확인한 결과, 그 경험에서 얻은 배움을 정리한다.

2026년 10월 2일부터 4일까지의 조사와 구현·평가 기록을 바탕으로 2026년 10월 5일에 정리했다. 당시 확인한 사실과 원인 가설을 구분하며, 평가 결과를 모든 운영 질문의 정확성으로 확대하지 않는다.

## 어떤 시스템에서 발생한 문제인가

이 시스템은 렌트카 회사의 질문에 한국어로 답하는 AI 비서다. 이름은 카비이며, 문장을 이해하고 답변을 만드는 언어 모델로 Claude를 사용한다. 일반적인 렌트 절차를 설명하고, 연결된 기능으로 차량 사진이나 현재 대기 차량 정보를 조회해 안내한다. 대기 차량은 회사 시스템의 대기 목록에 올라온 차량을 뜻하며, 목록에 있다는 사실만으로 실제 배차 가능 여부까지 확정하지는 않는다.

모델과 서버는 역할을 나누어 맡는다. 모델은 사용자 표현을 해석해 조회가 필요한지와 어떤 차량을 찾아야 하는지 판단한다. 서버는 응답을 검사하고 실제 차량 데이터를 검색하는 프로그램이다. 마지막으로 모델이 검색 결과를 사용자에게 필요한 문장으로 설명한다.

모델 호출은 지침과 데이터를 보내고 모델 응답을 받는 한 번의 요청이다. 조건 추출은 “가솔린 셀토스 26년형” 같은 문장에서 검색에 사용할 모델명·연료·연식 등을 읽어 항목별 값으로 만드는 일이다. 실제 차량이 있는지 확인하는 검색과는 다른 단계다.

개선 전에는 첫 모델 호출이 답변·거절·조회 중 하나를 선택하면서, 조회를 선택한 경우 검색 조건도 함께 만들었다. 서버가 그 조건으로 검색하면 두 번째 호출이 결과를 안내했다. 일반 질문이나 지원하지 않는 업무를 조회 없이 처리하는 경로는 이미 명시적인 응답 구조로 표현하고 있었다.

## 같은 차량을 물었지만 답변이 달라졌다

문제의 두 질문은 다음과 같았다.

> 카비 대기 중인 가솔린 셀토스 1.6 2WD 26년형 있어?

> 카비 대기 중인 가솔린 셀토스 1.6 2WD 26년형 차번호가 뭐야?

첫 질문에는 한 업체의 차량 한 대가 있다고 답했고, 두 번째 질문에는 해당 차량이 없다고 답했다. 사용자가 원하는 출력은 존재 여부와 차량번호로 달랐지만, 찾아야 할 차량 조건은 같았다.

셀토스는 모델명이고 가솔린은 연료다. 이 사례에서 `1.6`과 `2WD`는 배기량과 구동방식의 사양 표기이며, `26년형`은 2026년형을 뜻한다. “카비”는 비서를 부르는 말이므로 업체명이나 차량 조건이 되어서는 안 된다.

당시 저장된 차량 목록에는 조건에 해당하는 2026년형 차량이 있었다. 넓은 모델명 검색으로는 함께 존재하는 2020년형 차량도 검색될 수 있었다. 따라서 필요한 조건을 빠뜨리지 않는 것과, 다른 연식의 차량을 포함하지 않는 것이 모두 중요했다.

조사에서는 해당 시간 구간에 조회 대상으로 가리키는 저장 목록이 바뀌지 않았다는 점도 확인했다. 다만 당시 두 요청에서 모델이 만든 실제 검색 조건과 결과 건수는 남아 있지 않았다. 데이터가 있었다는 사실만으로 모델의 조건 생성, 서버 검색, 최종 답변 중 어느 단계가 직접 원인이었는지 확정할 수는 없었다.

여기서 얻은 첫 배움은 조회 경로를 선택한 사실과 원하는 차량 조건을 보존한 사실을 따로 확인해야 한다는 것이었다. 서버 요청이 성공하고 모델이 답변을 반환했다는 결과만으로 검색 의미의 일관성까지 확인되지는 않았다.

## 조건을 한 문자열에 담으면 검색 방식에 따라 차량을 놓쳤다

당시 서버는 차량명 안에 모델이 만든 검색어가 연속된 문자열로 들어 있는지를 검사했다. 실제 차량명의 예는 다음과 같았다.

```text
디 올뉴셀토스 1.6 가솔린 터보 2WD 트렌디
```

검색어가 `셀토스`이면 이 차량을 찾을 수 있었다. 그러나 `셀토스 1.6 2WD`로 검색하면 맞지 않았다. 검색어의 `1.6`과 `2WD` 사이에는 공백만 있고, 실제 차량명에는 `가솔린 터보`가 들어 있기 때문이다. 연식은 차량 데이터에 있었지만 별도 검색 조건으로 표현하지 못했다.

이는 검색어를 구체적으로 만들었는데 오히려 조건에 맞는 차량을 놓칠 수 있는 취약점이었다. 가능한 원인 가설은 두 질문에서 모델이 서로 다른 길이의 검색어를 만들고, 그중 한쪽이 서버의 연속 문자열 비교에서 실패했다는 것이었다. 당시 실제 조건이 남아 있지 않아 해당 사건의 직접 원인으로 확정하지는 못했다. 결과를 최종 답변으로 해석하는 단계의 오류도 배제할 수 없었다.

이 조사에서 조건 추출을 개선하려면 검색 조건을 표현하는 방식과 서버의 비교 방식도 함께 살펴야 한다는 점을 배웠다. 모델이 자연어 질문을 얼마나 자세히 옮겼는지만으로 검색 품질을 판단할 수 없었다.

## 조건 추출에 필요한 입력과 출력만 주었다

새 설계에서는 첫 호출이 조회 필요성을 선택한 뒤, 두 번째 호출이 원래 질문에서 검색 조건만 추출하도록 했다. 이 호출에는 현재 질문, 짧은 조건 전용 지침, 반환할 항목과 형식을 정의한 스키마를 제공했다. 첫 호출의 판단 내용이나 검색 결과를 조건 추출 입력에 추가하지 않았다.

모델에게 제공한 핵심 지침은 다음과 같았다.

```text
문장에서 차량 검색 조건만 추출해 JSON 객체로 반환하세요. 조회 실행이나 사용자 답변은 하지 마세요.
모델명은 model, 연료는 fuel, 4자리 모델 연식은 modelYear, 배기량·구동방식·트림은 specificationTerms로 분리하세요.
가솔린은 휘발유로 표준화하세요. 문장에 없는 조건은 필드를 생략하고 추측하지 마세요.
```

JSON은 프로그램이 항목 이름과 값을 읽을 수 있는 데이터 형식이다. 아래는 위 두 질문에 대해 기대한 조건을 설명하는 예시다. 당시 실제 응답 기록에서도 같은 주요 조건을 확인했다.

```json
{
  "model": "셀토스",
  "fuel": "휘발유",
  "modelYear": 2026,
  "specificationTerms": ["1.6", "2WD"]
}
```

`model`은 모델명, `fuel`은 연료, `modelYear`는 모델 연식, `specificationTerms`는 세부 사양 목록이다. 모델명에 모든 표현을 합치지 않고 각각의 의미를 보존했다. 가솔린을 휘발유로 바꾸는 것은 같은 연료의 표현을 검색에 쓰는 값으로 통일한 것이다. 질문에 없는 업체나 주차위치를 추측해 추가하는 것은 허용하지 않았다.

기대는 “있어?”와 “차번호가 뭐야?”처럼 원하는 출력이 달라져도 같은 차량 조건을 추출하는 것이었다. 무엇을 검색할지 정하는 조건과 무엇을 답할지 정하는 출력 요구를 분리하려 했다. 이 설계는 두 질문을 각각 독립적으로 처리하면서 조건을 보존하려는 것이며, 이전 질문의 조건을 자동으로 이어받는 대화 기억 기능을 구현한 것은 아니다.

여기서 짧은 지침의 의미는 단순히 글자 수를 줄이는 데 있지 않았다. 조건 추출 단계가 어떤 판단에 집중해야 하는지를 제한했다. 전체 입력에는 항목별 설명을 담은 스키마도 포함되므로, 짧은 지침만 보고 전체 입력량이 작아졌다고 주장할 수는 없다.

## 서버 검색도 항목별 조건을 적용하도록 바꿨다

조건 추출을 나눠도 서버가 다시 모든 항목을 한 문자열로 비교하면 같은 문제가 남을 수 있었다. 서버에서는 모델명·연료·연식·사양을 각각 처리하도록 조회 계약과 검색 규칙도 확장했다. 조회 계약은 검색 프로그램이 받을 조건 항목과 그 의미를 정한 약속이다.

| 조건      | 적용한 검색 규칙                                                                         |
|-----------|------------------------------------------------------------------------------------------|
| 모델명    | 모델 검색어가 맞는지 검사한다. 여러 검색어 사이에 다른 표현이 끼어 있어도 각각 확인한다. |
| 연료      | 추출한 표준 연료 값과 차량의 연료를 비교한다.                                            |
| 모델 연식 | 지정된 연식과 정확히 같은 차량만 찾는다.                                                 |
| 세부 사양 | 요청된 사양을 각각 확인하고 모두 만족해야 한다.                                          |

예를 들어 `1.6`과 `2WD`는 차량명에서 서로 붙어 있을 필요가 없지만 둘 다 맞아야 한다. 숫자 사양은 단어 전체를 비교해 `1.6`이 `11.6`의 일부라는 이유로 일치하지 않게 했다. 연식이 2026이면 모델명이 같아도 2020년형을 정확 일치 결과에 포함하지 않았다.

이후 다른 사양 표기의 관련 후보를 안내하는 기능도 추가됐지만, 후보는 정확히 일치한 차량과 구분했다. 여기서 설명하는 조건 보존의 목표는 조건을 느슨하게 만들어 검색 건수만 늘리는 것이 아니었다.

서버는 필드의 자료형, 허용 값과 범위, 사양 항목의 형태를 검사했다. 예를 들어 연식은 네 자리 정수 범위로 받고, 사양 목록에는 문자열을 요구했다. 형식이나 범위가 잘못된 조건은 검색을 실행하기 전에 거부했다.

그러나 형식 검사가 원문의 모든 조건이 추출됐는지까지 증명하지는 않는다. 전체 차량처럼 일부 항목을 지정하지 않는 질문도 지원하므로 모든 필드를 필수로 요구하지 않았다. 따라서 원래 질문에 연식과 사양이 있어도 아래처럼 누락된 응답은 항목의 형태만 보면 유효할 수 있었다.

```json
{
  "model": "셀토스",
  "fuel": "휘발유"
}
```

이 경험에서 형식이 유효한 조건과 의미가 완전한 조건을 구분해야 한다는 점을 배웠다. 서버의 검사와 함께, 질문에 명시된 조건이 빠짐없이 보존됐는지를 실제 모델 평가에서 확인해야 했다.

## 조건과 결과를 연결해 최종 답변을 만들었다

변경된 대기 차량 조회는 다음 흐름으로 구성했다.

```text
모델 호출 1: 조회가 필요한지 선택한다.
모델 호출 2: 현재 질문에서 검색 조건만 추출한다.
서버 처리: 조건을 검사하고 차량 데이터를 검색한다.
모델 호출 3: 검증된 조건과 검색 결과를 바탕으로 답변한다.
```

조건 추출의 출력 계약에는 조회 선택이나 사용자에게 보여줄 답변을 포함하지 않았다. 모델의 조건 응답을 서버가 검사한 뒤 검색하고, 마지막 호출에는 실제 사용한 조건과 조회 결과를 함께 전달했다. 마지막 호출은 추가 조회를 선택하지 않고 결과를 설명하도록 했다.

정상 완료되는 대기 차량 조회의 모델 호출은 최대 두 번에서 세 번으로 늘었다. 일반 답변과 사진 조회에는 이 조건 추출 호출을 추가하지 않았다. 여러 호출과 조회는 하나의 전체 처리 시간 예산을 공유했다. 조건 추출이나 검증이 실패하면 검색을 실행하지 않았으며, 이를 차량이 없는 결과로 취급하지 않았다.

이 구성을 통해 검색 조건을 별도로 확인하고, 같은 조건에 대해 존재 여부와 차량번호를 다르게 설명할 수 있는 구조를 만들었다. 다만 실제 모델 호출이 하나 늘어난 만큼 입력·출력 사용량과 응답 시간을 함께 살펴야 했다. 조건 추출 분리만의 비용·시간 변화를 분리 측정한 결과는 없으므로 그 증가량이나 감소량을 수치로 단정하지 않는다.

## 실제 모델 평가와 서버 검색 검증을 나눴다

조건 추출과 답변을 평가할 때는 실제 Claude Sonnet 5.5를 사용하고, 서버가 반환할 차량 결과는 평가용으로 준비했다. 다음 세 질문을 확인했다.

| 질문                                | 추출과 답변에서 확인한 내용                                                |
|-------------------------------------|----------------------------------------------------------------------------|
| 2026년형 차량이 있는가              | 셀토스·휘발유·2026·1.6·2WD를 보존하고 준비된 차량 한 대가 있다고 안내한다. |
| 같은 2026년형의 차량번호는 무엇인가 | 같은 조건을 보존하고 준비된 차량번호를 안내한다.                           |
| 같은 사양의 2025년형이 있는가       | 연식만 2025로 바꾸고 결과가 없다고 안내한다.                               |

당시 요청·응답 기록에서 앞의 두 질문은 같은 모델명·연료·연식·사양으로 추출됐고, 세 번째는 다른 조건을 유지하면서 연식을 2025로 추출한 것을 확인했다. 세 질문은 조건 추출과 존재 여부·차량번호·0건 답변 검증을 통과했다. 평가에서는 질문에 없던 업체·차량번호·주차위치 같은 검색 조건을 만들지 않았는지도 검사했다.

이 결과는 실제 모델이 준비한 결과를 올바르게 설명했는지 확인한 것이다. 평가용 검색은 실제 회사 시스템에서 차량을 찾는 구현이 아니었으므로, 서버 검색은 별도로 검사했다. 실제 조회 구현에서는 연식을 정확히 비교했고, 검색 규칙 테스트에서는 이름 중간의 추가 표현, 사양 불일치, 비슷한 숫자 표기로 인한 오탐을 다뤘다.

이 경험에서 조건 추출, 서버 검색, 최종 답변을 서로 다른 확인 대상으로 다뤄야 한다는 점을 배웠다. 모델이 올바른 조건을 만들었다는 결과만으로 실제 검색이 정확하다고 할 수 없고, 검색 결과가 정확하다는 사실만으로 최종 설명이 적절하다고 할 수도 없었다. 세 질문의 합성 평가를 운영 질문 전체의 정확성으로 확대하지 않는다.

또한 문제 발생 당시 운영 모델은 Sonnet 5였고, 개선 평가에서는 Sonnet 5.5를 사용했다. 호출 분리, 조건 계약, 서버 검색 규칙과 모델 버전이 함께 달라졌으므로, 관찰한 성공을 호출 분리 하나의 효과로 해석할 수는 없다.

## 기능 확장 때 조건 추출의 책임을 다시 확인했다

실시간 조회를 확장하면서 차량 한 대의 주차위치나 배차불가 같은 상세 정보도 안내하려 했다. 처음에는 조건 추출 단계에서 상세 정보가 필요한지까지 함께 판단하게 했다.

그 구성으로 기존 합성 세 질문을 평가하자 두 질문에서 연식·사양이 누락됐다. 상세 정보 필요 여부 판단을 첫 번째 조회 선택 단계로 옮기고, 조건 추출에는 이전의 짧은 조건 전용 지침과 스키마를 유지했다. 수정 후에는 같은 세 질문이 모두 통과했다.

이 관찰에서 호출을 분리한 뒤에도 각 호출의 책임을 유지하고 확인해야 한다는 점을 배웠다. 새 기능을 기존 추출 단계에 추가할 때는 기존 조건이 보존되는지도 다시 평가해야 했다. 다만 작은 표본만으로 판단 추가가 실패의 단독 원인이라고 확정하거나, 짧은 지침이 언제나 더 정확하다고 결론 내리지는 않는다.

조건과 필요한 사실을 답하는 검증을 통과한 뒤에도 최종 문장에는 불필요한 비서 이름 설명과 닫는 기호 잔재가 남았다. 조건 추출을 개선한 결과와 전체 답변 문장의 품질을 구분해야 했다. 새 상세 정보 요청의 판단 정확도도 이 세 질문만으로 검증되지는 않았다.

## 이후 설계에 적용할 배움

먼저 같은 검색 대상을 표현하는 질문 변형을 준비하고, 어떤 조건이 같아야 하는지 정한다. 존재 여부와 차량번호처럼 출력 요구만 바꾸었을 때 검색 조건이 유지되는지 확인한다. 조건 자체를 바꾸는 질문도 함께 평가해, 다른 연식이나 사양을 잘못 포함하지 않는지 확인한다.

추출 단계에는 원문에서 무엇을 읽고 어떤 항목으로 반환해야 하는지 명확히 설명한다. 질문에 없는 조건을 생략하는 것과 질문에 있는 조건을 누락하는 것은 구분한다. 반환 형식과 범위의 검사만으로 이 구분까지 보장되지는 않는다.

추출 조건을 서버가 어떤 의미로 검색할지도 함께 정한다. 모델 출력과 서버 비교 규칙이 맞지 않으면 상세한 조건을 만들수록 검색이 실패할 수도 있다. 필요한 조건을 각각 보존하고, 검색 결과가 없다는 이유로 임의로 조건을 완화하지 않는다.

조건 추출의 성공, 서버 검색의 성공, 최종 답변의 성공을 따로 평가한다. 한 단계의 성공을 전체 흐름의 성공으로 해석하지 않으며, 새 기능을 추가할 때는 이미 확인했던 추출 조건도 다시 점검한다.

이번 설계는 모델이 검색 조건을 만드는 판단에 집중하도록 하고, 그 조건을 서버가 검사하고 적용할 수 있는 중간 결과로 만든 작업이었다. 그 효과를 이해하려면 호출 수와 지침 길이뿐 아니라 조건의 의미, 검색 계약, 실제 평가 결과를 함께 봐야 했다.
