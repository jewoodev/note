# 모델의 의미 해석과 서버의 검증 및 실행 책임을 나누며 배운 점

렌트카 회사의 업무 기록과 직원 질문을 이해하는 AI 비서를 만들면서, 모델이 해석한 결과를 서버가 어디까지 검사해야 하는지 고민했다. 처음에는 모델의 해석을 키워드와 정규식으로 다시 확인했다. 이후 문맥에 따른 의미 판단은 모델에 맡기고, 서버는 응답 구조와 근거를 검증하며 실제 조회와 집계를 수행하도록 책임을 조정했다.

그 과정에서 배운 것은 검증 항목마다 보장하는 사실이 다르다는 점이다. 인용이 원문에 있다는 검사는 의미 해석의 정확성을 보장하지 않는다. 검색 조건의 형식이 맞다는 검사도 그 조건이 사용자의 의도와 같다는 뜻은 아니다. 각 검사가 무엇을 확인하는지 명확히 해야 모델의 판단을 활용하면서 서버의 실행 결과도 설명할 수 있었다.

이 문서는 채권 기록 분석의 책임을 바꾼 과정과 차량 조회의 실행 구조를 함께 살펴본다. 설계 의도, 기대한 효과, 코드와 테스트에서 확인한 결과를 구분해 정리한다.

## 어떤 업무를 처리하는 시스템인가

비서는 두 종류의 자료를 다뤘다. 하나는 미납액과 입금 약속, 연락 내역 등을 기록한 스프레드시트다. 이를 읽어 담당 팀이나 경영자가 확인할 내용을 제안했다. 여기서 채권은 회사가 받아야 할 돈이며, 제안은 사람이 검토할 사항을 뜻한다.

다른 하나는 직원의 차량 조회 질문이다. 예를 들어 차종, 연료, 연식을 지정하면 현재 대기 차량 자료를 조회해 조건에 맞는 차량을 안내했다. 대기 목록에 있다는 사실과 실제 배차 가능 여부는 구분해야 했다.

모델은 자연어를 읽고 사건의 의미나 검색 조건을 구조화한다. 서버는 자료를 읽고 모델을 호출하며, 응답을 받아 검사하고 실제 조회·집계·보고서 생성을 수행한다. 이 사례에서 실행은 그런 프로그램 동작을 가리킨다. 채권 분석에 고객 연락이나 입금 처리 실행이 포함되는 것은 아니다.

이 경계를 정하려면 세 질문에 답해야 했다. 무엇을 모델이 해석하는가, 그 결과에서 서버가 직접 확인할 수 있는 것은 무엇인가, 어떤 조건이 충족돼야 다음 동작을 실행하는가.

## 처음에는 코드의 의미 검사로 모델의 오판을 걸러내려 했다

초기 채권 분석에는 모델 앞뒤로 의미를 판정하는 코드가 있었다. 호출 전에는 정규식에 맞는 짧은 표현을 사건 유형으로 분류했다. 모델 응답을 받은 뒤에는 해당 유형에 필요한 단어가 인용에 포함됐는지 확인했다.

예를 들어 입금 약속으로 분류한 결과에는 입금·송금 같은 표현과 예정·약속 같은 표현이 있는지 검사했다. 연락 제한으로 분류한 결과에는 연락·전화 같은 표현과 금지·중단 같은 표현을 요구했다. 질문, 취소, 철회 등을 나타내는 단어가 있는 문장은 모호하다고 취급하는 검사도 있었다.

이 코드에서 읽을 수 있는 의도는 모델이 근거 없이 사건을 만들어 내지 못하게 하려는 것이었다. 정해진 표현을 직접 확인하면 최소한의 근거를 강제할 수 있을 것으로 기대한 구조였다.

그러나 이 검사에는 “이 문장이 해당 사건을 뜻하는가?”라는 의미 판단이 들어 있었다. 모델이 원문을 읽은 뒤 서버가 제한된 어휘 목록으로 다시 해석하는 셈이었다. 입력 형식이나 출처를 확인하는 검사와는 성격이 달랐다.

## 문맥을 읽어야 하는 문제를 단어 검사로 다루기 어려웠다

아래 문장들은 당시 서버 테스트에 사용한 사례다. 기대한 해석은 테스트에 지정한 가짜 모델 응답이며, 실제 모델이 항상 같은 해석을 했다는 뜻은 아니다.

| 기록                                    | 문맥에서 구분해야 할 내용                                            |
|-----------------------------------------|----------------------------------------------------------------------|
| 본부장을 통해서만 진행할 것             | 연락·금지라는 단어 없이도 별도 경로를 요구하는 의미를 표현할 수 있음 |
| 입금 미확인, 내일 담당자가 확인 예정    | 입금 사실은 미확정이지만 예정된 확인 작업은 별도로 존재함            |
| 연락 금지 철회, 내일 담당자가 확인 예정 | 철회된 지시와 독립적인 후속 작업을 구분해야 함                       |
| 미입금인 경우 내일 담당자가 확인 예정   | 후속 작업의 조건까지 보존해야 함                                     |
| 시스템 입금 내역 확인 예정              | 시스템이라는 단어가 업무 자료를 가리키는 문맥일 수 있음              |

첫 문장의 인용을 연락 제한으로 반환하면 초기의 키워드 조건을 만족하지 못한다. 나머지 문장도 특정 단어의 존재만으로 문장 전체를 제외하면, 독립적인 후속 작업이나 그 조건을 잃을 수 있다.

부정 표현을 다루는 기준도 사건마다 달랐다. 취소된 입금 약속을 현재 약속으로 되살리면 안 되지만, 실패한 통화는 실제로 시도한 연락일 수 있다. 한 줄에 통화 실패와 문자 발송이 함께 있으면 각각의 수행 기록을 남길 수 있어야 했다.

이 때문에 단어 목록을 늘리는 방식만으로 원하는 의미 경계를 표현하기는 어려웠다. 검사 코드가 더 많은 문맥을 해석할수록, 모델과 서버에 업무 의미를 나누어 구현하는 부담도 생겼다.

## 설계 의도는 의미 판단의 책임을 모델에 모으는 것이었다

채권 분석에서는 호출 전 사건 분류와 응답 후 유형별 키워드 검사를 제거했다. 모델을 사용할 때는 양수 미납 행에서 추출한 전체 기록을 전달하고, 부정·취소·철회·조건과 독립된 사건의 관계를 모델이 해석하도록 했다.

모델이 없을 때는 원문·금액·출처를 보존하되 사건 유형을 미분류로 남겼다. 모델 응답이 없다는 이유로 이전 정규식 분류를 대신 적용하지 않았다. 이렇게 하면 어떤 결과가 모델의 해석인지, 어떤 자료가 해석되지 않았는지 구분할 수 있었다.

날짜도 같은 방향으로 바꿨다. 서버가 문장에서 날짜를 찾아 사건에 붙이던 처리를 제거하고, 모델이 날짜의 역할과 근거를 함께 반환하게 했다. 기록일, 사건 발생일, 입금 예정일은 한 문장 안에서도 서로 다를 수 있기 때문이다.

기대했던 효과는 자유로운 업무 표현을 전체 문맥에서 해석하고, 그 결과가 서버의 좁은 어휘 조건 때문에 거부되지 않게 하는 것이었다. 취소나 미확인 표현도 원문에 남겨 독립적인 사건과 함께 판단하도록 했다.

이 선택은 모델이 의미를 항상 올바르게 읽는다는 전제에 기초하지 않았다. 의미 해석의 품질은 실제 사례와 기대 답안으로 평가하고, 서버는 자신이 직접 확인할 수 있는 조건을 확실히 검사하도록 책임을 나눴다.

## 서버에는 구조와 근거를 확인하는 검사를 남겼다

서버는 모델이 보낸 응답을 그대로 보고서에 사용하지 않았다. 정해진 필드와 타입, 허용된 사건 유형, 길이와 개수 제한 등을 검사했다. 반환한 행과 기록 번호가 입력에 존재하는지, 인용이 해당 기록에 실제로 포함되는지도 확인했다.

인용 대조의 기준은 모델에 전달한 기록이었다. 이 기록은 셀의 원문을 추출하면서 공백 등을 정규화한 텍스트이고, 원래 셀과 줄의 출처를 함께 보관했다. 원문에 없는 문장을 인용하거나 다른 기록을 가리키는 결과는 정상 분석으로 처리하지 않았다.

예를 들어 모델이 입력에 없는 “입금 확인 완료”를 근거로 반환하면 서버가 거부할 수 있다. 하지만 입력 문장이 “입금 확인 완료 여부를 물어봄”이고, 모델이 그 안의 “입금 확인 완료”만 인용했다면 문자열 포함 검사는 통과할 수 있다. 이 예시는 검증의 한계를 설명하기 위한 가상 사례다. 질문을 완료 사건으로 잘못 해석했는지는 별도의 의미 판단 문제다.

검사마다 확인하는 사실을 나누면 다음과 같다.

| 검사 또는 판단   | 확인할 수 있는 것                           | 그것만으로 확인되지 않는 것                             |
|------------------|---------------------------------------------|---------------------------------------------------------|
| 응답 구조 검사   | 필요한 필드, 타입, 허용 값이 맞는지         | 사용자의 뜻이나 업무 의미를 올바르게 읽었는지           |
| 출처와 인용 검사 | 입력에 해당 기록과 인용이 존재하는지        | 인용 범위가 적절하고 사건 유형이 정확한지               |
| 모델의 문맥 해석 | 기록을 어떤 사건으로 해석했는지             | 실제 입금이나 고객 수신이 외부 자료로 확인됐는지        |
| 서버의 금액 집계 | 정해진 대상 행의 숫자를 규칙대로 합산했는지 | 시트의 금액이 은행·다른 업무 시스템의 잔액과 일치하는지 |

특히 모델이 기록을 입금으로 해석했다는 사실과 실제 입금이 확인됐다는 사실은 구분해야 했다. 고객의 입금 주장은 기록된 입금과 다르고, 개별 입금 확인은 채무 전체의 완납과도 다르다. 각 사건 유형이 무엇을 뜻하는지 업무적으로 정의한 뒤 평가해야 했다.

## 날짜 사례는 보존과 실행의 경계를 보여줬다

날짜 테스트에는 다음과 같은 기록을 사용했다.

> 4/8 기록: 4/7 통화에서 4/31 입금하기로 약속

이 문장에는 기록한 날짜, 통화한 날짜, 약속한 입금 날짜가 있다. 연도는 없으며 4월 31일은 달력에 없는 날짜다.

변경된 분석은 모델이 반환한 날짜 역할, 구성 요소, 근거 인용을 보존했다. 서버가 빠진 연도를 채우거나 4월 31일을 다른 날짜로 고치지 않았다. 당시의 날짜 검사는 필드·타입·허용 역할·개수·근거 인용에 집중했고 달력 유효성은 검사하지 않았다. 여러 날짜 중 하나를 골라 최신 조치로 확정하던 처리도 제거했다.

이 구조가 제공한 것은 기록의 표현과 모델의 해석을 남기는 기능이다. 잘못된 날짜까지 실행 가능한 일정으로 승인한 결과는 아니다. 당시 이 날짜는 분석과 보고서 표시에 쓰였다.

여기서 얻은 일반화 가능한 교훈은 다음 동작에 따라 필요한 검사가 달라진다는 점이다. 같은 결과를 향후 예약이나 알림 실행에 사용한다면, 그 실행 경계에서는 달력상 유효한 날짜인지, 연도와 시간대가 확정됐는지 등을 별도로 확인해야 한다. 이는 이 사례로부터 도출한 설계 원칙이며 당시 구현한 예약 기능을 설명하는 것은 아니다.

## 차량 조회에서는 모델의 해석을 서버가 실행 가능한 조건으로 바꿨다

차량 조회에서는 모델이 질문에서 검색 조건을 추출하고, 서버가 그 응답을 검사한 뒤 조회기를 호출했다. 조회기는 실제 차량 자료를 읽고 조건에 맞는 결과를 만드는 코드다.

예를 들어 “26년형 셀토스 가솔린 1.6 2WD가 있나?”라는 질문은 모델명, 모델 연식, 연료, 세부 사양을 구분해야 한다. 모델에는 가솔린을 휘발유로 표준화하고 문장에 없는 조건을 만들지 않도록 지시했다. 해석 결과의 예시는 다음과 같다. 실제 실행 결과를 인용한 것은 아니다.

```json
{
  "model": "셀토스",
  "modelYear": 2026,
  "fuel": "휘발유",
  "specificationTerms": ["1.6", "2WD"]
}
```

서버는 필드 이름이 허용 목록에 있는지, 연식이 정해진 범위의 정수인지, 연료가 허용 값인지, 사양 목록의 개수와 각 항목의 형식이 맞는지 검사했다. 문자열 앞뒤 공백 제거처럼 뜻을 추론할 필요가 없는 정규화도 수행했다.

연식을 문자열이나 소수로 반환하거나, 정의하지 않은 필드를 추가하면 실제 조회 전에 거부했다. 모델이 선택한 도구도 서버가 그 요청에 허용한 목록에 있는지 확인했다. 지원하는 조회 경로를 서버가 정하고, 모델의 출력은 그 범위 안에서만 처리했다.

그 뒤 서버는 검증한 조건을 실제 자료에 적용했다. 연식과 연료를 대조하고 모델명과 세부 사양의 검색어를 검사하며, 일치 건수와 반환 목록을 계산했다. 필요한 상세 정보가 없으면 상태를 미확인으로 남기거나 해당 조건을 확인할 수 없다는 오류를 반환했다. 예를 들어 배차불가 제외 조건을 적용해야 하는데 상세 정보를 확인하지 못했다면, 그 조건을 빼고 계산한 대수를 정상 결과로 내놓지 않았다.

이 구조에서는 세 가지 책임이 이어진다. 모델이 질문의 의미를 조건으로 표현하고, 서버가 조건의 형식과 실행 가능 여부를 검사하며, 조회 코드가 그 조건을 실제 자료에 적용한다.

다만 직원이 가솔린을 물었는데 모델이 허용 값인 경유를 반환하면 형식 검사는 통과할 수 있다. 서버는 잘못 추출된 조건에도 정확하게 검색을 수행할 수 있다. 따라서 조건 검증과 조회 실행의 정확성만으로 질문에 대한 답변 전체가 정확하다고 결론 내릴 수는 없다.

## 실행 책임에는 계산과 실패 처리도 포함됐다

채권 분석에서 모델은 사건 해석과 검토 제안을 반환했지만, 미납액 합계는 서버가 계산했다. 한 행에 여러 검토 사안이 나와도 그 행의 금액을 한 번만 더했다. 금액이 공란이거나 숫자로 확인되지 않으면 임의로 0원으로 해석하지 않았다.

차량 조회에서는 서버가 시간 예산과 조회 흐름을 관리했다. 조건이 유효하지 않으면 조회를 시작하지 않고, 지원하는 조회에서 실패가 나면 확인된 결과처럼 최종 모델 답변을 만들지 않도록 처리했다. 조회 결과가 0건인 경우와 조회 자체를 수행하지 못한 경우도 구분했다.

서버가 이런 조건을 직접 확인하는 이유는 모델에게 지시한 내용이 곧 실행 보장은 아니기 때문이다. 지침에 허용 조건을 적는 일과 코드가 허용 조건을 검사한 뒤 실행하는 일은 각각 필요했다.

## 확인한 결과와 당시 남아 있던 검증

채권 기록의 변경 이력에는 서버의 의미 분류를 제거한 뒤 로컬 테스트 74개 통과, 외부 연동 조건에 따른 5개 제외가 기록돼 있다. 날짜 해석을 모델로 옮긴 뒤에는 78개 통과, 5개 제외가 기록돼 있다. 서로 다른 변경 단계의 기록이며 두 수를 더해 평가 규모로 해석하지 않는다.

이 테스트에서는 문맥 전체를 모델에 전달하는지, 키워드가 없다는 이유로 모델의 분류를 거부하지 않는지, 존재하지 않는 인용과 출처를 거부하는지, 날짜 해석을 임의로 보완하지 않는지 등을 확인했다. 가짜 모델 응답을 사용한 검증이므로 실제 모델의 의미 해석 정확도를 입증한 결과는 아니다.

변경 이전 실제 모델 평가에는 취소된 약속을 현재 약속으로 추출한 사례와, 취소된 결제의 날짜를 새 약속의 인용에 포함한 사례가 남아 있다. 직접 평가와 별도의 연결 검증에서 인용 범위가 달라진 기록도 있었다. 이 이력은 구조나 원문 인용만 확인해서는 해석 품질을 보장할 수 없다는 점을 보여준다.

서버의 의미 분류 제거와 새 날짜 응답 구조에 대한 실제 모델 재평가는 해당 변경 기록 시점에 수행하지 않았다. 이전의 사건 유형·인용 점수를 새 날짜 역할 해석의 정확도로 가져오거나, 검사를 제거했으므로 앞선 문제가 해결됐다고 주장할 근거는 없었다.

차량 조회 코드에는 허용하지 않은 조건이 조회기에 도달하지 않는지, 상세 정보를 확인하지 못했을 때 미확정 상태를 유지하는지, 확인하지 못한 필터를 조용히 생략하지 않는지를 검사하는 테스트가 있다. 이 문서를 작성하면서는 해당 코드와 테스트를 확인했으며 테스트나 실제 모델 평가를 새로 실행하지 않았다.

## 이 과정을 통해 배운 것

### 검증이라는 이름보다 검사가 판정하는 내용을 봐야 한다

필드의 타입을 확인하는 검사와 문장에 특정 단어가 있는지 확인해 사건 유형을 승인하는 검사는 다른 일을 한다. 후자는 이미 업무 의미를 해석하고 있다.

모델의 자유로운 해석 뒤에 그런 검사를 붙이면 서버의 어휘 목록이 실질적인 최종 해석 기준이 될 수 있다. 어떤 의미 판단을 누가 맡을지 정하고, 코드의 각 검사가 그 책임과 맞는지 살펴봐야 했다.

### 서버의 책임은 직접 보장할 수 있는 사실로 설명해야 한다

서버는 인용의 존재, 출처 연결, 허용된 입력 형식, 조건을 적용한 조회, 중복 없는 금액 합산을 직접 검사하거나 수행할 수 있었다. 이런 보장은 의미 해석의 정확성과 구분해 설명해야 했다.

코드가 업무 규칙을 갖지 않아야 한다는 뜻은 아니다. 양수 미납 행을 분석 대상으로 고르고, 조회 가능한 기능을 제한하고, 확인되지 않은 상세 조건의 적용을 중단하는 것은 명시적인 업무·실행 규칙이었다. 자연어 문맥을 추측하는 검사와 실행 조건을 강제하는 검사를 구분한 것이 핵심이었다.

### 의미를 맡기려면 유형의 정의와 불확실성도 함께 설계해야 한다

연락을 성공한 통화로 볼지 시도한 행위로 볼지 정하지 않으면, 같은 실패 통화 기록을 두고 모델과 평가자가 다른 답을 기대할 수 있다. 고객의 주장, 확인된 기록, 완료 상태도 먼저 구분해야 했다.

모델은 정해진 업무 의미를 적용하도록 지시하고, 확정하지 못한 연도나 상세 상태는 결과에 남겼다. 이렇게 해야 불확실성을 서버가 임의로 채우거나 이후 출력에서 확정 사실처럼 사용하는 일을 줄일 수 있다.

### 다음 단계에서 사용할 목적이 검증의 강도를 결정한다

원문과 해석을 보여주는 보고서와 날짜에 맞춰 외부 동작을 실행하는 기능은 필요한 확실성이 다르다. 분석 결과가 구조 검사를 통과했다는 이유만으로 모든 후속 실행에 사용할 수 있는 것은 아니다.

각 실행 경계에서 필요한 조건을 다시 정의해야 한다. 이번 사례에서는 조회 전 입력 검증, 상세 필터 적용 전 자료 확인, 집계 전 대상과 숫자 확인이 그 역할을 했다.

### 해석 품질과 실행 정확성은 각각 검증해야 한다

모델이 엉뚱한 조건을 추출했어도 서버의 조회는 그 조건에 대해 정확할 수 있다. 모델의 해석이 적절해도 서버가 금액을 중복 합산하거나 원문 연결을 잘못하면 결과는 틀릴 수 있다.

따라서 모델 평가는 의미와 제안의 타당성을 다루고, 서버 테스트는 입력 검사·출처 연결·조회·집계·실패 처리를 다뤄야 했다. 어느 한쪽의 통과를 전체 시스템의 정확성으로 확대하지 않는 것이 책임을 나눈 뒤에도 남는 중요한 검증 원칙이었다.
