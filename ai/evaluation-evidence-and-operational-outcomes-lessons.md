# AX 테스트 통과와 실제 모델·운영 성과를 구분하며 배운 점

렌트카 회사의 AI 비서를 만들면서 차량 조회와 미납 메모 분석 기능을 검증했다. 테스트가 통과하고 모델이 정답을 맞혀도, 그것만으로 직원이 믿고 쓸 수 있다고 말하기는 어려웠다. 테스트에서 확인한 내용과 실제 업무에서 필요한 능력이 달랐기 때문이다.

어떤 때는 서버 코드만 검사했고, 어떤 때는 실제 모델에 질문했지만 차량 조회 결과는 미리 만들어 넣었다. 운영 서버가 답변을 만드는 것까지 확인하고도 채팅으로 보내지는 않은 경우도 있었다. 이 경험을 통해 평가할 때 어떤 질문을 해야 하는지 배웠다.

## 서버가 답을 잘 처리하는가, 모델이 좋은 답을 만드는가

미납 메모를 분석하는 기능을 바꾸면서 모델이 메모를 읽고, 담당자가 확인할 항목까지 함께 고르도록 했다. 변경 후 관련 테스트 92개 중 87개가 통과했다. 외부 연동에 필요한 조건을 갖추지 못한 5개는 실행하지 않았다.

이 테스트에서는 모델이 반환할 답을 미리 정해 두었다. 그 답을 받은 서버가 원문을 올바르게 연결하는지, 같은 미납 건의 금액을 여러 번 더하지 않는지, 잘못된 응답을 처리하는지 검사했다.

여기서 확인한 것은 서버 코드의 동작이었다. 실제 모델이 담당자에게 필요한 항목을 골라 주는지는 당시 다시 평가하지 않았다. 따라서 다음 두 질문을 나누어 봐야 했다.

- 모델이 답을 줬을 때 서버가 제대로 처리하는가?
- 실제 모델이 업무에 쓸 만한 답을 주는가?

모델에 새로운 판단을 맡길 때마다 두 번째 질문도 다시 해야 했다. 사건의 종류를 잘 구분하던 모델이라도, 날짜가 입금 예정일인지 기록 작성일인지 판단하거나 담당자의 확인이 필요한 항목을 고르는 일은 따로 평가해야 했다.

## 테스트가 통과했는데 답변은 엉뚱했다

일반적인 업무 절차를 물었을 때는 차량을 조회할 필요가 없다. 초기 평가에서는 모델이 정해진 답변 형식을 지키고 조회도 하지 않으면 통과로 처리했다.

그런데 실제 답변을 읽어 보니, 모델은 절차를 설명하는 대신 차량번호를 알려 달라고 했다. 검사한 조건은 모두 만족했지만 사용자의 질문에는 답하지 않은 셈이다. 반대의 경우도 있었다. 최종 답변은 적절했지만, 답하기 전에 불필요한 차량 조회를 수행했다.

이후에는 조회 여부와 횟수뿐 아니라 답변 내용도 함께 살폈다. **평가 기준은 코드가 검사하기 쉬운 항목만으로 정하면 안 됐다. 사용자가 기대한 일을 실제로 했는지 확인해야 했다.**

채점 코드도 같은 이유로 검사했다. 같은 사건을 두 번 반환해도 점수가 더 오르지 않아야 하고, 원문에 없는 문장을 근거로 제시하면 오답으로 처리해야 했다. 평가 프로그램이 정상 종료했다는 사실과 모델의 답변이 합격했다는 사실도 구분했다. 모델 호출이 실패해 답변을 받지 못한 실행은 오답이 아니라 평가 미완료로 남겼다.

## 정답을 정하지 못한 메모도 있었다

미납 메모에는 “입금했다고함”, “통화 입금확인”처럼 짧은 표현이 많았다. 앞의 문장은 고객이 입금했다고 주장했다는 뜻일 수 있다. 뒤의 문장도 입금을 확인했다는 것인지, 통화해서 확인할 예정이라는 것인지 작성 관행을 알아야 판단할 수 있었다.

모델의 답을 채점하기 전에 담당자와 메모의 뜻부터 확인했다. 실제 작성 방식을 참고하되 이름·금액·날짜 등을 바꾼 사례 중 10개는 정답을 정했고, 해석 방침을 정하지 못한 8개는 평가에서 보류했다.

보류한 메모에 ‘아무 사건도 없다’는 정답을 붙이지는 않았다. 뜻을 아직 모르는 것과 아무 일도 없었다는 것은 다르기 때문이다.

업무에서 쓰는 말의 뜻을 합의하면서 정답이 바뀐 경우도 있었다. ‘연락’에 성공한 통화뿐 아니라 연락을 시도한 기록도 포함하기로 한 뒤에는, 실패한 통화와 문자 발송도 모델이 찾아야 할 사건으로 추가했다.

여기서 배운 것은 **모델을 평가하려면 사람이 먼저 무엇을 정답으로 볼지 합의해야 한다**는 점이다. 정답을 바꿀 때도 모델이 틀렸기 때문인지, 업무상 정의가 바뀌었기 때문인지 이유를 남겨야 했다.

## 틀린 사례를 고쳐서 만점을 받아도 평가가 끝나지는 않았다

정답을 정한 메모 10개로 모델을 평가했더니 처음에는 9개를 맞혔다. 틀린 사례에서는 통화 실패 뒤에 문자를 보낸 기록을 놓쳤다. 이를 빠뜨리지 않도록 지침을 추가했는데, 다음 평가에서는 오히려 6개만 맞혔다. 다른 메모에서 사건을 잘못 찾거나 필요한 근거를 누락한 것이다.

지침을 더 고치며 같은 10개를 다시 평가했고, 결과는 9개, 9개, 마지막에는 10개 정답이었다. 이 과정에서 한 가지 오류를 고친 지침이 다른 답변을 망가뜨릴 수도 있다는 것을 확인했다. 수정한 사례만 다시 봐서는 부족했다.

마지막의 10개 정답은 의미 있는 개선이었다. 다만 틀린 답을 보고 지침을 고친 뒤, 바로 그 메모들로 다시 시험한 결과였다. 처음 보는 메모에도 잘 답하는지는 아직 확인하지 못했다.

한 번 모두 맞혔다고 다음 호출에서도 같은 답을 내는 것은 아니었다. 이후 연락의 뜻을 합의한 뒤 직접 평가에서는 다시 10개를 모두 맞혔지만, 같은 메모를 분석 서비스에 넣어 모델을 다시 호출하자 취소된 결제의 날짜를 새 약속에 붙이는 문제가 재발했다. 이때도 실제 원본 시트 대신 이름 등을 바꾼 메모와 가상 금액을 사용했다.

그래서 평가 목적을 세 가지로 나눌 필요가 있었다.

- 기존 메모를 다시 평가해 발견한 오류가 고쳐졌는지, 다른 답변을 망가뜨리지는 않았는지 확인한다.
- 지침을 고칠 때 참고하지 않은 새 메모로 다른 표현도 이해하는지 확인한다.
- 같은 지침으로 여러 번 실행해 결과가 얼마나 일관적인지 확인한다.

당시의 지침별 점수를 합쳐 하나의 성공률로 계산하는 것도 적절하지 않았다. 매번 다른 지침을 시험했기 때문이다.

## 모델 호출, 실제 조회, 채팅 수신은 각각 확인해야 했다

차량 조회 평가에서는 실제 모델에 질문하되, 차량 목록과 사진 링크는 미리 만든 결과를 반환하도록 했다. 이렇게 하면 모델이 조회가 필요한 질문을 구분하고, 주어진 목록으로 답하는지 볼 수 있었다.

2026년 9월 27일에는 주요 질문 8종을 세 번씩, 표현을 바꾼 질문 4건을 한 번씩 실행했다. 총 28건에서 기대한 처리 방식을 선택했다. 이 평가는 모델의 선택을 확인한 것이고, 운영 차량 자료를 읽거나 채팅을 보내는 과정은 포함하지 않았다.

운영 서버의 동작은 따로 확인했다. 9월 18일에는 배포된 서버에 준비한 질문을 보내 실제 저장 자료와 모델을 연결했다. 답변에 나온 차량 200대가 조회한 자료의 대수와 일치했다. 조회 전후에도 같은 자료를 사용했음을 확인했다. 다만 답변을 채팅으로 보내지는 않았다.

사용자의 채팅 수신은 9월 15일에 별도로 확인한 기록이 있었다. 일반 답변 두 건과 지원 불가 안내 한 건이 같은 방에 도착했다고 사용자가 확인했다. 하지만 이때는 로컬에서 실행한 서버를 사용했다.

이 두 기록을 합쳐 “운영 서버에서 사용자 수신까지 확인했다”고 할 수는 없었다. **전체 과정을 확인하려면 같은 실행에서 어떤 서버가 자료를 읽고 답변을 만들었는지, 그 답변이 사용자에게 도착했는지를 이어서 봐야 했다.**

## 다음 평가에서는 무엇을 확인할 것인가

이후 평가를 기록할 때는 ‘통과’라는 말 옆에 실행한 내용과 남은 확인 사항을 적어야겠다고 생각했다. 예를 들면 다음과 같다.

> 미리 만든 모델 응답으로 서버 테스트 87개가 통과했다. 외부 연동 테스트 5개는 실행하지 않았다. 원문 연결과 금액 집계는 확인했으며, 실제 모델이 담당자에게 필요한 검토 항목을 고르는지는 추가 평가가 필요하다.

결과를 비교할 때는 코드와 모델, 지침, 평가에 쓴 자료와 정답 기준도 남겨야 한다. 무엇이 달라졌는지 알아야 점수 변화의 의미를 판단할 수 있기 때문이다.

비용도 마찬가지였다. 불필요한 조회는 줄었지만, 바로 답하는 경우의 첫 입력은 이전보다 약 1,012토큰 늘었다. 반면 대기 차량을 조회하는 두 번의 호출에서는 합산 입력이 평균 7,056토큰에서 6,638.3토큰으로 줄었다. 지침과 응답 형식 등 여러 조건이 함께 바뀌었으므로, 어떤 변경 덕분에 얼마나 절약됐는지는 별도 비교가 필요했다. 토큰 수만으로 실제 청구액을 확인한 것도 아니었다.

마지막으로 남은 질문은 직원의 일이 실제로 나아졌는가였다. 제안을 검토하는 시간이 줄었는지, 잘못된 제안을 고치는 일이 늘지는 않았는지, 중요한 미납 건을 놓치지는 않았는지 살펴봐야 한다. 여기까지 기록한 테스트와 모델 평가는 그 업무 성과를 측정한 결과는 아니다. 다음에는 직원이 사용한 결과를 바탕으로 이 질문에 답해야 한다.
