# AI 비서의 처리 결정을 응답 구조로 표현하며 배운 점

렌트카 회사의 AI 비서를 개발하면서, 모델이 자연스러운 답변을 만들더라도 그 답변에 이르는 과정에서 불필요한 조회를 선택할 수 있다는 문제를 경험했다. 업무 범위와 예시를 지침에 보강한 뒤에도 문제가 남아, 첫 모델 응답에 답변·거절·조회 중 어떤 처리를 선택했는지 명시하도록 바꿨다.

이 글은 그 설계의 의도와 기대, 실제 평가에서 관찰한 결과, 그 경험에서 얻은 배움을 정리한다. 처리 결정을 프로그램이 읽을 수 있는 형태로 표현하고, 서버가 그 결정에 따라 다음 작업을 수행하는 방식에 집중한다.

2026년 9월 27일에 구현·평가한 변경을 바탕으로 2026년 10월 5일에 정리했다. 호출 단계와 검색 조건을 추가로 분리한 이후의 설계와는 구분하며, 아래의 결과는 당시 평가 범위에 한정된다.

## 어떤 질문을 어떻게 처리해야 했나

이 시스템은 렌트카 회사의 질문에 한국어로 답하는 AI 비서다. 이름은 카비이고, 문장을 이해하고 답변을 만드는 언어 모델로 Claude를 사용한다. 일반적인 렌트 절차를 설명하고, 연결된 조회 기능으로 차량 사진이나 대기 차량 정보를 찾아 안내한다. 대기 차량은 회사 시스템의 현재 대기 목록에 올라온 차량을 뜻하며, 목록에 있다는 사실만으로 실제 배차 가능 여부까지 확정하지는 않는다.

당시에는 실제 예약 변경·취소나 개별 계약 조회를 실행할 수 없었다. 따라서 비슷한 단어를 사용한 질문이라도 다음처럼 처리 방법이 달라야 했다.

| 사용자 요청 | 필요한 처리 |
| --- | --- |
| 예약 변경은 보통 어떻게 하나요? | 일반 절차를 설명한다. |
| 제 예약을 변경해 주세요. | 직접 처리할 수 없다고 안내한다. |
| 대기 중인 K5가 있어요? | 회사의 차량 데이터를 조회한다. |
| 차량 사진을 보여 주세요. | 어떤 차량인지 알 수 있도록 차량번호를 먼저 묻는다. |

모델은 질문의 의도를 해석하고 답변이나 조회 요청을 만든다. 서버는 모델 응답을 검사하고 실제 데이터를 검색하는 프로그램이다. 모델이 조회를 선택하는 것과 서버가 조회를 실행하는 것은 이어지는 두 과정이다. 여기서는 서버가 실행하는 사진·차량 조회 기능을 도구라고 부른다.

모델 호출은 지침과 데이터를 보내고 응답을 받는 한 번의 요청이다. 조회가 필요한지 판단한 뒤 검색 결과를 설명하게 하려면, 검색 전과 검색 후에 모델을 각각 호출할 수 있다.

## 지침을 보강했지만 불필요한 조회가 남았다

처음에는 AI 서비스가 제공하는 도구 호출 기능을 사용했다. 서버가 조회 기능과 입력 항목을 모델에게 설명하면, 모델이 일반 답변을 반환하거나 정해진 도구 호출 형식으로 조회를 요청하는 방식이었다. 이 방식도 조회 이름과 조건을 구조화해서 표현했다. 이번 변경은 처음으로 모든 조회를 구조화한 작업이 아니라, 답변·거절·조회를 하나의 처리 선택 계약으로 묶은 작업이었다.

모델이 일반 질문이나 지원하지 않는 업무에 무관한 조회를 선택하는 문제를 줄이려고 지침을 보강했다. 예약 변경·계약 조회와 일반 절차 설명을 구분하고, 사진 요청에 차량번호가 없으면 조회 없이 확인 질문을 하도록 예시를 넣었다.

최종 지침 후보의 실제 모델 평가에서는 예약 변경·계약 조회·취소 9건을 모두 조회 없이 거절했다. 그러나 차량을 받을 때의 준비 사항을 묻는 일반 인수 안내 3건 중 2건에는 불필요한 도구 선택이 남았다.

한 건은 사진 조회를 선택한 뒤 질문과 무관한 차량번호 확인 질문을 했다. 다른 한 건은 대기 차량 데이터를 조회한 뒤 일반 인수 절차를 안내했다. 후자의 최종 문장은 질문에 맞았지만, 그 문장을 만들기 위해 필요하지 않은 조회와 모델 호출을 거쳤다.

이 결과를 통해 답변 내용만 확인하면 처리 과정의 문제를 놓칠 수 있음을 배웠다. 개선하려던 대상은 사용자에게 전달할 문장과 함께, 그 문장을 만들기 위해 어떤 작업을 선택했는가였다.

## 처리 방법을 첫 응답의 명시적인 결정으로 만들었다

새 설계에서는 모델에게 답변·거절·조회 중 하나를 선택하고, 그 선택을 같은 응답 형식에 담도록 했다. 서버는 처리 방법 항목을 읽어 다음 동작을 결정하고, 답변 문장 항목은 사용자에게 전달할 내용으로 사용한다.

이를 위한 응답 계약은 모델이 반환해야 하는 항목과 형식을 정한 약속이다. 당시 첫 응답에는 세 항목을 요구했다.

| 항목 | 의미 |
| --- | --- |
| `status` | 답변, 지원하지 않는 업무 안내, 조회 중 선택한 처리 방법이다. |
| `answer` | 사용자에게 전달할 문장이다. 조회를 선택한 경우에는 빈 문자열이다. |
| `lookup` | 조회 작업과 조건이다. 답변이나 거절을 선택한 경우에는 조회 없음이라는 뜻의 `null`이다. |

아래는 당시 응답 계약에 맞춰 구성한 설명용 예시다. 실험에서 수집한 응답 원문은 아니다. JSON은 프로그램이 항목 이름과 값을 읽을 수 있는 데이터 형식이며, `null`은 해당 항목에 값이 없다는 뜻이다.

일반 절차를 설명한다면 답변을 선택한다. `ANSWER`는 안내와 확인 질문을 모두 포함한다.

```json
{
  "status": "ANSWER",
  "answer": "예약 변경은 보통 변경 가능한 일정과 조건을 확인하는 절차로 진행돼요.",
  "lookup": null
}
```

실제 예약 변경 요청이라면 지원하지 않는 업무 안내를 선택한다. `UNABLE_TO_ANSWER`는 당시 시스템의 처리 결정 이름이며, 아래 사례에서는 직접 실행할 수 없는 업무라는 뜻이다.

```json
{
  "status": "UNABLE_TO_ANSWER",
  "answer": "예약 변경 처리는 제가 직접 도와드릴 수 없어요. 양해 부탁드려요.",
  "lookup": null
}
```

대기 차량 데이터가 필요하다면 조회를 선택한다. `LOOKUP`은 조회 요청이며, `search_waiting_vehicles`는 서버에 등록된 대기 차량 검색 기능의 이름이다. 이 단계의 빈 `answer`는 조회 결과를 받기 전에 최종 안내를 만들지 않는다는 뜻이다.

```json
{
  "status": "LOOKUP",
  "answer": "",
  "lookup": {
    "name": "search_waiting_vehicles",
    "input": {
      "model": "K5"
    }
  }
}
```

기대는 모델이 조회 실행을 요청하는 경우뿐 아니라, 조회하지 않고 답하거나 거절하는 경우도 명확한 선택으로 표현하게 하는 것이었다. 다만 세 가지 선택을 명시하면 판단 정확성이 반드시 높아진다고 전제하지는 않았다. 실제 질문으로 선택과 실행 결과를 확인하기로 했다.

## 별도 분류 호출을 추가하지 않고 다음 작업을 정했다

처리 방법을 명시하려고 질문 분류만 하는 모델 호출을 새로 만들지는 않았다. 기존 첫 호출에서 처리 방법과 직접 답변을 함께 반환하도록 했다. 서버의 별도 키워드 규칙으로 예약·계약 요청을 분류하는 방식도 추가하지 않았다.

이 설계에는 처리 결정을 명확히 하면서 기존 호출 수를 유지하려는 의도가 있었다. 직접 답할 수 있는 질문은 첫 응답에서 안내를 끝내고, 조회가 필요한 질문만 서버 작업으로 이어지게 했다.

```text
첫 모델 응답
  ├─ 답변·확인 질문: 문장을 전달하고 종료
  ├─ 지원하지 않는 업무 안내: 문장을 전달하고 종료
  └─ 조회: 서버가 검사하고 선택된 작업 실행
       ├─ 사진 조회: 서버가 사진 링크 안내를 만들어 종료
       └─ 대기 차량 조회: 두 번째 모델 호출이 결과를 안내
```

당시 일반 답변·거절·사진 조회는 모델 한 번, 대기 차량 조회는 최대 두 번이었다. 조회 결과를 전달한 두 번째 호출에는 최종 상태와 답변 문장만 허용했다. 추가 조회 선택은 그 단계에서 받지 않았다.

이 경험에서 처리 결정을 명시하는 일을 반드시 별도의 분류 단계로 만들 필요는 없다는 점을 배웠다. 첫 호출이 직접 안내와 다음 작업 선택을 함께 담당하게 할 수 있었다. 그 구성이 실제로 효과적인지는 응답 형식과 경로별 평가로 확인해야 했다.

## 응답 형식과 실행 조건은 서버에서도 검사했다

모델이 정해진 형식으로 응답하도록 JSON Schema를 제공했다. 스키마는 허용하는 항목, 자료형, 선택 값을 정의하는 규칙이다. 그러나 모델에 제공한 형식 규칙만으로 서버의 검사를 대체하지는 않았다.

서버는 답변·거절이면 조회가 없어야 하고, 조회이면 답변이 비어 있어야 한다는 조합 규칙도 검사했다. 당시 제공한 스키마는 각 항목의 형태와 선택 값을 제한했지만, 이 모든 조합 규칙을 표현하지는 않았다. 아래 응답처럼 답변을 선택하면서 조회 요청도 넣으면 서버가 거부했다.

```json
{
  "status": "ANSWER",
  "answer": "차량을 안내할게요.",
  "lookup": {
    "name": "search_waiting_vehicles",
    "input": {}
  }
}
```

조회 결정이 일관되더라도 허용된 작업인지, 입력 조건이 유효한지 다시 검사했다. 조회를 허용하지 않는 요청 경로에는 조회 선택을 제공하지 않았다. 사진 요청의 차량번호가 사용자 입력에 실제로 포함됐는지 확인하는 기존 검사와, 조회 데이터가 유효한지 확인하는 규칙도 유지했다.

구현 중에는 모델 서비스의 제약도 확인했다. 당시 API는 기존 조회 정의의 숫자 최솟값·최댓값 제약을 응답 스키마에 넣은 요청을 거절했다. 해당 범위를 설명으로 옮기고 서버에서는 운전자 나이 0~120, 목록 건수 1~20의 검사를 유지했다. 이는 당시 요청에서 확인한 호환 문제이며, API의 현재 지원 범위를 설명하는 주장은 아니다.

이 경험에서 다음 세 가지를 각각 확인해야 한다는 점을 배웠다.

- 응답 형식이 맞는가: 항목과 자료형이 규칙에 맞는지 확인한다.
- 결정과 실행 조건이 일관되는가: 답변과 조회가 동시에 선택되지 않았는지, 작업과 조건이 허용되는지 확인한다.
- 질문에 필요한 작업을 골랐는가: 일반 절차 질문에 차량 조회를 선택하지 않았는지 평가한다.

첫 두 검사를 통과해도 세 번째 판단은 틀릴 수 있다. 일반 인수 절차 질문에 허용된 차량 조회를 올바른 형식으로 요청했다면, 형식과 실행 조건은 맞아도 업무 선택은 잘못된 것이다. 이를 응답 스키마만으로 해결했다고 볼 수는 없었다.

## 실제 평가에서는 처리 경로가 개선됐다

변경 후에는 실제 모델에 평가용 질문과 가상의 조회 결과를 제공했다. 가상의 조회 결과는 실제 회사 데이터를 조회하는 대신 평가자가 준비한 차량 목록과 사진 링크다. 따라서 모델의 처리 선택과 결과 안내를 확인하는 평가였으며, 실제 회사 데이터 조회나 사용자에게 메시지가 도착하는 과정까지 검증한 것은 아니다.

주요 질문 8종을 각각 세 번 평가하고 표현을 바꾼 질문 4건을 추가해 총 28건을 확인했다. 예약 변경·취소·계약 조회, 일반 절차, 차량번호 확인 질문, 사진 조회, 대기 차량 조회를 포함했다. 당시 모델은 Claude Sonnet 5였으며, 전후의 주요 질문 평가에서 같은 모델과 설정을 사용했다.

28개 사례는 모두 기대한 처리 경로를 충족했다. 다음은 주요 질문별 결과다.

| 질문 유형 | 사례 수 | 모델 호출과 조회 결과 |
| --- | ---: | --- |
| 실제 예약 변경·취소·개별 계약 조회 | 9 | 각각 모델 한 번, 조회 없이 거절 안내 |
| 일반 인수·예약 변경 절차 | 6 | 각각 모델 한 번, 조회 없이 설명 |
| 차량번호가 없는 사진 요청 | 3 | 각각 모델 한 번, 조회 없이 확인 질문 |
| 전체 차량번호를 제공한 사진 요청 | 3 | 각각 모델 한 번, 사진 조회 선택과 서버 안내 |
| 대기 총대수 질문 | 3 | 각각 모델 두 번, 대기 차량 조회 후 결과 안내 |

위 24건에 추가한 표현 변형 4건도 기대한 경로를 충족했다. 총 28건의 모델 호출은 31회였고, 대기 차량 질문 3건에만 후속 호출이 있었다.

이전 지침 후보에서 일반 인수 안내는 3건 중 2건에 불필요한 도구 선택이 남았지만, 구조화된 처리 선택에서는 3건 모두 조회 없이 답했다. 이는 동일한 주요 질문을 사용한 작은 표본의 관찰이다. 운영 실패율이 얼마만큼 감소했는지 추정한 결과는 아니다.

이 결과에서 처리 선택을 응답 계약에 드러낸 설계가 평가 표본의 목적을 충족했다는 점을 확인했다. 다만 지침, 출력 스키마, 메시지 구성을 함께 바꿨으므로 효과를 한 요소로 분해할 수는 없다. 기존 도구 호출 방식보다 항상 우수하다는 일반적인 결론도 내리지 않는다.

## 호출 수를 유지해도 입력량은 달라졌다

별도 분류 호출을 추가하지 않았지만 모델에 보내는 내용은 바뀌었다. 처리 선택 규칙과 응답 스키마도 입력에 포함되므로, 호출 수가 같다고 입력 비용까지 같은 것은 아니다.

토큰은 모델이 텍스트를 나누어 처리하는 단위다. 아래 수치는 시스템 지침만의 길이가 아니라 질문·지침·응답 형식 등을 포함한 입력 사용량이며, 대기 조회에서는 두 호출의 입력을 합산했다.

| 비교 대상 | 이전 도구 호출 방식의 최종 지침 후보 | 구조화된 처리 선택 |
| --- | ---: | ---: |
| 예약 변경 질문의 첫 호출 입력 평균 | 3,393토큰 | 4,405토큰 |
| 대기 총대수 질문의 두 호출 합산 입력 평균 | 7,056토큰 | 6,638.3토큰 |

직접 답하는 예약 변경 경로에서는 입력이 늘었고, 대기 조회 경로에서는 합산 입력이 줄었다. 후속 호출의 스키마와 데이터 전달 형식이 달라진 영향도 포함되므로, 단일 원인으로 해석하지 않는다. 실제 청구 금액은 확인하지 않았다.

이 경험에서 호출 수와 입력·출력량을 함께 봐야 한다는 점을 배웠다. 처리 결정을 명확히 하는 설계가 입력을 늘릴 수도 있고, 경로에 따라 변화가 다를 수도 있었다. 평가에서 관찰한 입력량 변화와 실제 비용 절감 주장은 구분해야 했다.

## 이후 설계에 적용할 배움

모델 응답을 다음 작업의 입력으로 사용할 때는, 서버가 어떤 항목을 읽어 어떤 동작을 할지 먼저 정한다. 사용자가 읽는 답변 문장과 서버가 실행할 결정을 함께 담되, 서로 모순되는 조합을 허용하지 않는다.

직접 답변·확인 질문·지원하지 않는 업무 안내도 처리 선택의 일부로 다룬다. 조회가 필요한 경우만 강조하면 조회하지 않아야 하는 질문의 경로를 충분히 검증하지 못할 수 있다. 필요한 작업을 실행했는지와 불필요한 작업을 실행하지 않았는지를 함께 확인한다.

응답 규칙을 제공한 뒤에도 서버의 형식·조합·허용 범위 검사를 유지한다. 그 검사와 별도로 실제 모델이 질문에 맞는 작업을 골랐는지 평가한다. 형식이 유효하다는 사실을 업무 판단의 정확성으로 확대하지 않는다.

이번 설계는 첫 모델 응답을 서버가 다음 작업을 결정할 수 있는 명시적인 입력으로 만들려는 시도였다. 기존 호출 수를 유지하면서 평가 표본의 처리 경로를 개선했지만, 의미상 올바른 선택과 비용의 변화는 별도로 확인해야 했다.
