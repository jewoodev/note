# 민감한 원문을 기록하지 않고 처리 과정을 관찰하며 배운 점

차량 조회를 수행하는 AI 비서를 만들면서, 사용자에게 보인 답변만으로는 문제가 어느 단계에서 생겼는지 알기 어려웠다. 모델이 조회를 선택하지 않았을 수도 있고, 검색 조건이 잘못됐거나, 조회 자료를 읽지 못했거나, 조회 후 답변을 만드는 과정에서 실패했을 수도 있었다.

그래서 실제 사용한 검색 조건, 조회 건수, 자료 식별자와 처리 단계를 기록했다. 질문·답변 원문, 원본 모델 입력, 차량 목록, 차량번호 조건 값은 진단 로그에서 제외했다. 처리 전체의 결과와 중간 조회 결과는 같은 식별자로 연결했다.

이 설계를 통해 배운 것은 원문을 더 많이 저장하는 것보다 구분하고 싶은 상황을 먼저 정하는 일이 중요하다는 점이다. 어떤 단계까지 성공했는지와 무엇을 확인하지 못했는지를 남기면, 민감한 자료의 복제를 줄이면서 다음 조사 범위를 좁힐 수 있었다. 다만 이런 로그만으로 모델의 의미 해석이나 최종 답변의 정확성까지 판정할 수 있는 것은 아니었다.

## 어떤 시스템에서 필요한 관찰이었나

렌트카 회사의 직원이 차종, 회사, 연식 같은 조건으로 대기 차량을 물으면 비서가 데이터를 조회해 답했다. 모델은 질문을 해석하고 답변을 작성했으며, 서버는 조건을 검사하고 실제 자료를 읽었다.

처음에는 모델이 조회와 조건을 선택한 뒤 서버가 조회하고, 모델을 다시 호출해 답하는 흐름이었다. 이후 조건 추출을 별도 호출로 나누면서 처리 방법 선택, 조건 추출, 서버 조회, 최종 답변의 단계가 됐다.

조회 자료도 발전했다. 초기에는 특정 시점의 차량 목록을 파일로 수집해 둔 스냅샷을 읽었고, 이후에는 외부 업무 사이트의 실시간 목록을 읽었다. 스냅샷은 저장된 자료 묶음이며, 실시간 조회는 요청 시점에 새로 확인한 결과다.

여기서 관찰이란 원문 전체를 재생하는 기능이 아니라, 처리 과정의 상태와 결과를 나중에 확인할 수 있도록 진단 정보를 남기는 것을 뜻한다. 이 문서는 서버의 차량 조회·모델 처리 진단을 다루며, 시스템 전체의 모든 저장 경로에서 민감정보가 제거됐다고 보장하는 문서는 아니다.

## 기존 결과 로그만으로는 조회 과정을 설명하기 어려웠다

기존에도 모델 이름, 사용량, 지연 시간, 최종 처리 결과, 실패 단계와 호출 차수 등을 기록하고 있었다. 그러나 해당 처리에서 어떤 검색 조건이 실제로 적용됐고, 몇 건을 찾았으며, 어느 시점의 자료를 읽었는지 연결할 정보는 부족했다.

예를 들어 “조회할 수 없다”는 안내 응답이 정상적으로 만들어지면 전체 결과는 답변 성공으로 남을 수 있다. 반대로 차량 조회는 끝났는데 후속 모델 응답의 형식이 잘못돼 전체 처리가 실패할 수도 있다. 전체 성공·실패 하나로는 두 경우를 구분하기 어려웠다.

원문을 저장하면 질문과 응답을 직접 볼 수 있지만, 질문에는 차량번호나 업무 정보가 들어갈 수 있다. 외부 응답과 예외 메시지에도 원문이나 인증정보가 섞일 수 있었다. 따라서 먼저 다음과 같은 진단 질문을 정했다.

- 조회가 선택됐고 실행 단계까지 도달했는가?
- 서버가 검사한 뒤 실제로 적용한 조건은 무엇인가?
- 조회 결과가 0건인가, 조회 자체를 수행하지 못한 것인가?
- 조건에 맞는 전체 건수와 실제 반환한 목록 길이는 각각 얼마인가?
- 어떤 자료를 읽었으며 그 자료는 얼마나 오래됐는가?
- 조회 실패인가, 조회 뒤 모델 호출이나 응답 검사 실패인가?

기대했던 효과는 이 질문에 필요한 정보만으로 원인의 범위를 좁히는 것이었다. 모델이 왜 그런 조건을 추출했는지까지 원문 없이 완전히 재구성하려는 목표는 아니었다.

## 한 번의 처리 안에서 중간 결과와 최종 결과를 연결했다

사용자 요청을 처리하기 시작할 때 `call_id`를 새로 만들었다. 이름에 call이 들어가지만, 이 값은 개별 모델 HTTP 요청마다 바뀌는 식별자가 아니다. 한 사용자 요청을 처리하는 동안 여러 모델 호출과 서버 조회를 연결하는 식별자다.

대화를 찾는 `conversation_id`도 함께 기록했다. 같은 대화에 여러 질문이 이어지면 대화 식별자만으로는 각각의 처리 결과를 구분하기 어려우므로, 한 번의 처리를 연결할 때는 `call_id`를 사용했다.

| 로그 종류 | 담는 정보 |
| --- | --- |
| `waiting_lookup` | 대기 차량 조회의 도달 상태, 검증한 조건, 건수와 자료 식별 정보 |
| `ai_call` | 요청 처리의 답변 결과, 사용량·지연, 실패 시 단계와 모델 호출 차수 |
| `ai_lookup` | 예상하지 못한 조회 예외의 분류 |

조회 상태와 전체 답변 결과는 서로 덮어쓰지 않았다. 조회를 성공한 뒤 최종 응답 해석이 실패하면 조회 상태는 성공으로 남고, 전체 결과에는 실패 단계와 호출 차수를 기록했다.

또한 모든 단계에서 각각 로그를 찍는 방식은 아니었다. 처리 중 메모리에 진단 상태를 갱신하고, 마지막에 조회 진단을 한 번 출력했다. 따라서 이 로그는 단계별 전체 시간순 이력이 아니라 종료 시점까지 확인한 상태의 요약이다.

## 상태 이름은 다음에 확인할 범위를 가리키게 했다

조회 진단에는 다음 상태를 사용했다. 조건 추출 단계가 추가되면서 `extracting`도 생겼다.

| 상태 | 코드에서 나타내는 지점 |
| --- | --- |
| `not_requested` | 대기 조회 처리 분기에 진입한 기록이 없음 |
| `extracting` | 별도의 검색 조건 추출 단계에 들어감 |
| `invalid_input` | 조회 입력 검증을 아직 통과하지 못한 상태 |
| `started` | 조건 검증을 마치고 조회 실행을 준비하거나 진행하는 상태 |
| `success` | 조회 결과 객체를 정상적으로 받음. 0건도 포함 |
| `failed` | 조회 또는 추출에서 분류한 실패를 기록함 |

일부 상태는 다음 단계로 넘어가기 전에 미리 설정했다. 예를 들어 입력 검증 전 `invalid_input`을 설정하고, 검증에 성공하면 `started`로 바꿨다. 검증 과정에서 예외가 나더라도 통과하지 못한 상태가 남게 한 것이다.

따라서 상태 하나만으로 모든 원인을 확정하지 않았다. `not_requested`는 사용자가 조회를 원하지 않았다는 뜻까지 보장하지 않는다. 최초 모델 응답을 읽다가 실패해 조회 분기에 도달하지 못했을 수도 있다. 모델 응답의 처리 단계와 호출 차수를 함께 봐야 했다.

실패 진단에는 응답 바깥 구조 읽기, 답변 JSON 읽기, 답변 필드 검사, 조회 입력 검사 등의 단계를 남겼다. 실패한 위치를 나타내는 코드이며 원문을 출력할 필요는 없었다. 호출 구조가 두 번에서 세 번으로 바뀌었으므로 호출 차수도 당시 흐름과 함께 해석해야 했다.

## 실제 사용한 조건을 허용 목록으로 기록했다

모델이 반환한 원본 조회 입력을 통째로 기록하지 않았다. 서버가 필드·타입·허용 범위를 검사하고 공백 정리와 기본값 적용을 마친 뒤, 조회에 사용할 조건에서 지정한 항목만 진단 객체로 옮겼다.

| 정보 | 기록 방식과 목적 |
| --- | --- |
| 회사·모델·차종·연료 등 | 어떤 검색 조건을 적용했는지 확인 |
| 주차위치·운전자 나이·배차불가 제외 여부 | 추가 필터가 결과에 영향을 줬는지 확인 |
| 연식·세부 사양·상세 조회 여부 | 이후 확장된 조회 조건을 확인 |
| 목록 제한 | 전체 일치 건수와 반환 목록 길이의 차이를 설명 |
| 차량번호 조건 | 실제 값 대신 `plate_present`로 사용 여부만 기록 |
| 질문·답변 원문, 원본 도구 입력, 차량 목록 | 진단 객체에 포함하지 않음 |

이렇게 하면 “모델이 보낸 입력”과 “서버가 실제로 적용한 조건”을 구분할 수 있다. 유효하지 않은 원본 입력은 조건 기록에 들어오지 않았다. 다만 검증을 통과한 조건도 사용자의 의도와 다를 수 있으므로, 이 기록만으로 조건 추출이 정확했다고 판단할 수는 없다.

진단 객체는 한 줄 JSON으로 직렬화했다. 조건 문자열에 줄바꿈이나 따옴표가 있어도 로그의 레코드 경계를 깨뜨리지 않도록 하기 위해서였다. JSON 이스케이프는 문자열을 안전한 형식으로 표현하는 처리이며 개인정보를 지우는 처리는 아니다.

이 설계의 민감정보 제외 범위도 정확히 이해해야 한다. 차량번호 필드의 값은 기록하지 않지만, 회사·모델·주차위치처럼 허용한 문자열에는 값이 남는다. 다른 필드에 민감한 문자열이 잘못 들어왔을 때 이를 찾아 모두 제거하는 범용 비식별 처리는 아니었다. 이 구현에서 보장하는 것은 지정한 원문과 차량번호 필드를 진단 객체에서 제외하는 경계다.

## 조회 건수는 각 숫자가 의미하는 지점을 나눴다

결과에 차량 목록이 비어 있다고 해서 조회 실패로 처리하지 않았다. 자료를 정상적으로 확인했지만 조건에 맞는 차량이 없는 경우는 조회 성공 0건이다. 자료를 읽지 못하거나 검증하지 못한 경우와 구분해야 했다.

건수도 하나로 합치지 않았다. 조건에 맞는 조회 대상 수, 명시적으로 배차불가인 수, 추가 필터 적용 후 전체 수, 목록 제한을 적용해 실제 반환한 수를 구분했다. 반환 목록이 생략됐는지도 따로 남겼다.

예를 들어 필터 적용 후 15대가 있고 목록 제한 때문에 10대만 반환했다면, 답변이 참고할 전체 대수는 15대다. 이 숫자는 설명용 예시이며 실제 운영 결과가 아니다. 서로 다른 건수를 기록하면 목록 제한 때문에 일부만 보낸 상황과 실제로 조건에 맞는 차량이 적은 상황을 구분할 수 있다.

조회 실패에는 성공 건수를 채우지 않았다. 특히 실패를 0건으로 바꾸면 자료를 못 읽은 상황이 차량이 없는 상황처럼 보일 수 있었다. 이후 실시간 조회에서는 배차불가 정보를 확인하지 못한 경우도 0으로 바꾸지 않고 미확인 값으로 보존했다.

## 뒤에서 실패해도 앞에서 확인한 사실을 남겼다

조회 진단은 성공 경로에서만 출력하지 않고, 정상 반환과 일반적인 예외 처리 모두에서 실행되는 `finally` 구간에 뒀다. 최종 답변 생성이 실패해도 이미 확인한 조회 조건과 결과를 잃지 않기 위해서였다. 다만 프로세스 강제 종료나 로그 전송 장애까지 기록을 보장하는 영속 저장 장치는 아니다.

다음은 초기 스냅샷 조회 구조를 설명하기 위해 만든 가상 예시다. 실제 로그에서 필요한 필드만 추려 JSON으로 표현했으며 운영 원문은 아니다. 같은 `call_id`를 가진 두 기록을 연결해서 읽는다.

```json
[
  {
    "event": "ai_call",
    "call_id": "11111111-1111-4111-8111-111111111111",
    "outcome": "failed",
    "reason": "INVALID_RESPONSE",
    "round": 2,
    "stage": "ANSWER_JSON"
  },
  {
    "event": "waiting_lookup",
    "call_id": "11111111-1111-4111-8111-111111111111",
    "diagnostics": {
      "outcome": "success",
      "snapshot_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "filtered_count": 15,
      "returned_count": 10,
      "truncated": true
    }
  }
]
```

여기서 확인되는 것은 조회 결과를 받았고, 두 번째 모델 호출의 답변 JSON 해석 단계에서 실패했다는 것이다. 다음 조사는 조회 실행 자체보다 후속 응답 처리부터 시작할 수 있다. 다만 그 조회 조건이 질문에 맞았는지, 모델이 왜 잘못된 응답을 만들었는지는 이 기록만으로 알 수 없다.

조회 진단은 마지막에 출력되므로 실제 로그 줄 순서에서는 전체 실패 기록 뒤에 조회 성공 기록이 올 수 있다. 로그 출력 순서를 업무 실행 순서로 해석하지 않고 식별자와 단계 정보를 이용해야 했다. 조건 추출이 추가된 이후에는 같은 최종 응답 단계가 세 번째 모델 호출에 해당했다.

## 예외에서도 확인한 식별자와 안전한 분류만 보존했다

스냅샷 조회에서는 먼저 최신 자료를 가리키는 작은 파일을 읽고 자료 식별자를 확인했다. 식별자가 정해진 형식인지 검사한 뒤, 그 자료의 본문을 읽거나 검증하다 실패하면 이미 확인한 식별자를 예외에 포함했다.

이렇게 하면 실패 시점에 어떤 자료를 읽으려 했는지 추적할 수 있었다. 반면 최신 자료의 식별자조차 확인하지 못했다면 값을 비워 뒀다. 검증되지 않은 경로나 임의 문자열을 자료 식별자처럼 기록하지 않았다.

예외 출력에서도 메시지와 스택 추적 전체를 남기지 않았다. 예외 메시지에는 파싱 중이던 원문이나 공급자 응답, 인증 관련 정보가 들어갈 수 있기 때문이다. 대신 실패 분류, 처리 단계, 호출 차수와 예외 클래스 이름을 기록했다. 원인 예외를 따라갈 때도 클래스 이름만 제한된 개수로 남겼다.

이 선택은 예외 원문을 보지 않고도 모든 원인을 알아내겠다는 뜻은 아니었다. 운영 로그에서는 연결 실패인지, 입력 검사 실패인지, 응답 파싱 실패인지 범위를 좁히고, 구체적인 재현은 통제한 자료와 별도의 검증 과정으로 다룰 수 있게 했다.

## 조회 방식이 바뀌면서 식별자와 관찰 항목도 바꿨다

실시간 조회로 바뀐 뒤에는 성공 결과에 조회 식별자, 데이터 출처, 조회 시각을 기록했다. 과거의 스냅샷 식별자를 실시간 결과의 의미로 그대로 사용하지 않았다.

스냅샷 식별자는 저장된 자료 묶음을 가리키지만, 실시간 조회 식별자는 해당 조회를 구분하는 값이다. 식별자가 있다고 해서 그때의 원문 자료를 다시 읽을 수 있는 것은 아니다. 재현 가능한 저장 자료와 처리 식별자의 역할을 구분해야 했다.

목록 조회와 상세 조회의 결과도 나눠 기록했다. 목록은 얻었지만 개별 차량의 상세 정보는 확인하지 못할 수 있기 때문이다. 상세 상태와 실패 분류, 목록·상세 조회 시간, 재인증 여부를 추가했다. 정확히 일치하는 결과가 없을 때 관련 후보를 찾는 기능에는 후보 검색 수행 여부, 후보 건수, 적용한 규칙 이름을 남겼고 후보 차량 목록은 남기지 않았다.

시간 필드 역시 측정 범위를 구분해야 했다. 전체 `ai_call` 지연은 서버의 처리 시작부터 끝까지여서 여러 모델 요청과 조회 시간이 포함된다. 개별 목록·상세 요청의 시간과 같은 측정치로 해석해서는 안 됐다.

## 코드와 테스트에서 확인한 결과

진단 설계의 효과는 기록된 필드를 보는 것과 함께, 기록하면 안 되는 값이 빠지는지를 검사하는 방식으로 확인했다. 아래는 해당 변경과 후속 구현에 있는 가짜 모델·HTTP 응답 및 조회 자료 기반 테스트의 검증 항목이다.

| 검증 항목 | 확인하는 경계 |
| --- | --- |
| 유효하지 않은 조건은 조회하지 않고 입력 실패 상태를 남김 | 조건 검증과 실행을 구분 |
| 조회 0건을 성공으로 기록함 | 빈 결과와 조회 실패를 구분 |
| 최종 응답 파싱 실패 뒤에도 조회 성공·건수·자료 ID가 남음 | 중간 결과가 후속 실패에 덮이지 않음 |
| 조회 로그와 전체 결과 로그의 처리 식별자가 같음 | 한 처리의 기록을 연결 가능 |
| 질문·답변·차량번호 테스트 값이 로그에 없음 | 지정한 원문 필드의 비기록 경계 |
| 예외 클래스는 기록하지만 예외 객체와 공급자 원문은 남기지 않음 | 오류 경로의 우회 노출 방지 |
| 줄바꿈이 포함된 조건이 한 줄 JSON으로 기록됨 | 레코드 구조 보존 |
| 확인한 스냅샷 ID는 실패에도 남고, 잘못된 ID는 남지 않음 | 검증한 자료 위치만 보존 |

이 테스트는 서버가 특정 상황에서 어떤 진단을 남기는지 확인한다. 실제 모델의 조건 추출 정확도, 답변 품질, 운영 장애의 해결 시간을 측정한 결과는 아니다. 테스트용 민감 문자열이 없다는 확인 역시 가능한 모든 입력에서 민감정보가 사라진다는 증명은 아니다.

이 문서를 작성하면서는 당시 커밋과 후속 코드·테스트를 확인했다. 운영 로그를 새로 조회하거나 테스트를 다시 실행하지 않았으므로, 현재 배포 적용 상태나 실제 장애 감소를 확인한 결과로 확대하지 않는다.

## 이 설계를 통해 배운 것

### 남길 데이터보다 답할 진단 질문을 먼저 정해야 했다

조회 여부, 실제 조건, 건수, 자료 시점, 실패 단계를 구분하려면 원문 전체가 꼭 필요한 것은 아니었다. 필요한 사실을 먼저 정의하니 기록할 필드와 제외할 필드를 함께 정할 수 있었다.

대신 질문의 정확한 의미나 최종 문장의 타당성을 평가하는 데에는 한계가 남았다. 진단 로그가 답할 수 있는 질문과 별도의 평가가 필요한 질문을 명확히 하는 것이 관찰 설계의 일부였다.

### 중간 성공과 전체 성공을 따로 보존해야 했다

조회 성공 뒤에도 모델 호출이나 응답 검증은 실패할 수 있었다. 반대로 조회 실패를 안내하는 문장을 정상적으로 만들 수도 있었다.

조회 결과와 답변 결과를 별도로 남기고 같은 식별자로 연결하니 이 상황들을 구분할 수 있었다. 답변이 생성됐다는 사실을 조회 성공이나 의미적 정확성의 증거로 사용하지 않게 하는 구조였다.

### 0과 미확인 그리고 생략은 다른 상태였다

조회해서 0건인 경우, 조회하지 못해 건수를 모르는 경우, 전체 결과 중 일부만 반환한 경우는 달랐다. 상세 정보를 확인하지 못한 상태도 배차불가가 0대라는 뜻은 아니었다.

숫자와 상태를 함께 설계해야 이런 차이가 로그에 남았다. 후보 검색을 수행하지 않은 경우와 수행했지만 후보가 없는 경우도 같은 원칙으로 구분했다.

### 민감정보 제외는 실패 경로까지 포함해야 했다

정상 로그에서 원문을 빼도 예외 메시지나 스택 추적을 그대로 출력하면 원문이 다시 나타날 수 있었다. 허용한 필드로 진단 객체를 만들고, 예외 출력도 분류와 클래스 이름으로 제한하는 두 경계가 필요했다.

검증한 조건은 실행 가능성이 확인된 조건이지 비식별화가 끝난 자료는 아니다. 허용한 문자열 필드에 무엇이 들어갈 수 있는지까지 이해해야 로그의 보호 범위를 정확히 설명할 수 있었다.

### 관찰 설계도 업무 흐름의 변화에 맞춰 갱신해야 했다

조건 추출 호출이 추가되면 호출 차수의 의미가 달라지고, 스냅샷에서 실시간 조회로 바뀌면 자료 식별자의 의미도 달라졌다. 오래된 단계 번호나 필드 설명을 그대로 사용하면 로그가 있어도 잘못된 원인을 추정할 수 있었다.

이번 경험에서 얻은 기준은 각 필드가 어느 처리 지점에서 만들어지고 무엇을 보장하는지 코드와 함께 관리하는 것이다. 그래야 중간 과정을 남기는 로그가 다음 확인을 결정하는 근거로 쓰일 수 있었다.
