# AI 비서의 지침과 호출 단계를 설계하며 배운 점

AI 비서를 개발하는 과정 속에서 모델에게 업무 규칙을 설명하는 방법과 여러 판단을 나누어 맡기는 방식을 바꿔갔다. 처음에는 지침을 명확히 정리하면 필요한 조회를 올바르게 선택할 것으로 기대했다. 이후에는 처리 방법을 명시적으로 선택하게 하고, 차량 검색 조건을 추출하는 판단에 별도 단계를 만들었다.

이 글은 각 설계의 의도와 기대, 실제로 관찰한 결과, 그 경험에서 얻은 배움을 정리한다. 핵심은 모델이 각 단계에서 무엇에 집중하도록 만들고, 그 결과를 다음 단계에 어떻게 전달할지 설계하는 일이었다.

2026년 9월 27일부터 10월 4일까지의 설계와 평가 기록을 바탕으로 2026년 10월 5일에 정리했다. 결과는 당시 평가 범위에 한정되며, 배운 점은 그 관찰을 바탕으로 정리한 설계 판단이다.

## 어떤 일을 하는 AI 비서인가

이 시스템은 렌트카 회사의 질문에 한국어로 답하는 AI 비서다. 문장을 이해하고 답변을 만드는 언어 모델로 Claude를 사용한다. 일반적인 렌트 절차를 설명하고, 회사가 연결한 조회 기능으로 차량 사진이나 대기 차량 정보를 찾아 안내한다. 여기서 대기 차량은 회사 시스템의 현재 대기 목록에 올라온 차량을 뜻한다. 목록에 있다는 사실만으로 실제 배차 가능 여부까지 확정하지는 않는다.

당시 지원 범위에서는 예약 변경·취소나 개별 계약 조회를 실행할 수 없었다. 따라서 “예약 변경은 보통 어떻게 하나요?”에는 절차를 설명하고, “제 예약을 변경해 주세요”에는 직접 처리할 수 없다고 안내해야 했다. “대기 중인 셀토스가 있어?”에는 회사 데이터를 조회해야 했다.

역할은 모델과 서버가 나누어 맡는다. 모델은 사용자의 문장에서 의도를 해석하고 필요한 검색 조건이나 답변을 만든다. 서버는 프로그램으로 응답을 검사하고, 허용된 조회 기능을 실행해 실제 데이터를 가져온다. 모델이 조회를 요청하는 것과 실제 조회가 실행되는 것은 서로 이어지는 두 과정이다.

예를 들어 차량 존재 여부에 답하는 흐름은 다음과 같다. 세부 판단을 몇 번의 모델 요청에 담을지는 뒤에서 설명하는 설계 변경의 대상이었다.

```text
사용자 질문
  → 모델이 필요한 작업과 검색 조건을 판단
  → 서버가 조건을 검사하고 차량 데이터를 조회
  → 모델이 조회 결과를 바탕으로 답변
```

모델 호출은 지침과 데이터를 보내고 모델 응답을 받는 한 번의 요청을 뜻한다. 검색을 서버가 한 번 실행했다고 해서 모델 호출도 한 번인 것은 아니다. 검색 전 판단과 검색 후 답변 생성을 각각 요청하면 모델은 두 번 호출된다.

지침은 모델에게 역할, 업무 범위, 판단 기준, 답변 규칙을 설명하는 문장이다. 응답 계약은 모델이 반환해야 하는 항목과 형식을 정한 약속이다. 예를 들어 서버가 조회를 실행하려면, 모델 응답에서 조회 작업과 조건을 읽을 수 있어야 한다. 이 글에서는 서버가 실행하는 사진·차량 조회 기능을 도구라고 부른다.

## 업무별 지침으로 처리 경계를 명확히 하려 했다

먼저 해결하려던 문제는 비슷한 질문을 다르게 처리해야 한다는 점이었다. 일반 절차는 설명하고, 지원하지 않는 실제 업무는 거절하며, 실제 데이터가 필요한 질문에만 조회를 사용해야 했다. 차량번호가 없는 사진 요청이라면 바로 조회하는 대신 어떤 차량인지 먼저 물어야 했다.

이를 위해 일반 안내, 사진 조회, 대기 차량 조회의 지침을 역할별로 정리해 조합했다. 말투나 답변 형식처럼 여러 기능에 공통으로 적용되는 규칙은 마지막에 한 번만 넣었다. 예약 변경 요청과 변경 절차 질문, 차량번호가 없는 사진 요청처럼 혼동하기 쉬운 사례에는 예시도 추가했다.

기대는 업무 경계와 예시를 명확히 제공하면 모델이 질문의 의도를 구분하고 필요한 조회만 선택할 것이라는 것이었다. 모델 호출 수와 실제 조회 기능은 유지하면서 지침으로 선택 품질을 개선하려 했다.

실제 모델을 사용한 최종 지침 후보 평가에서는 예약 변경·계약 조회·취소 9건을 모두 조회 없이 거절했다. 그러나 일반 인수 안내 3건 중 2건에는 불필요한 도구 선택이 남았다. 일반 인수 안내란 렌트 차량을 받을 때의 준비 사항이나 절차를 설명하는 것으로, 개별 차량 데이터를 조회할 필요가 없는 질문이었다.

한 실패는 사진 조회를 선택해 질문과 무관한 차량번호 확인 질문을 한 경우였다. 다른 실패는 대기 차량을 조회한 뒤 인수 절차를 안내한 경우였다. 후자의 최종 문장은 질문에 맞았지만, 그 문장을 만들기까지 불필요한 조회와 모델 호출을 거쳤다.

이 경험에서 업무 범위를 지침으로 명확히 설명하는 일은 필요하지만, 그 설명만으로 처리 경로까지 안정된다고 기대할 수는 없다는 점을 배웠다. 최종 문장이 자연스럽고 주제에 맞는지와 함께, 어떤 작업을 선택하고 실행했는지도 확인해야 했다. 여러 지침 변경을 함께 적용했으므로, 이 결과를 지침 분리 하나의 효과로 해석하지는 않는다.

## 첫 응답에서 처리 방법을 명시적으로 선택하게 했다

지침 수정 후에도 불필요한 조회가 남아, 첫 모델 응답에 처리 방법을 명시하게 했다. 기존 AI API의 도구 호출 방식에서는 조회 요청을 도구 호출로 표현했다. 새 방식은 조회를 하지 않는 답변과 거절까지 포함해 다음 세 가지 선택을 같은 응답 형식으로 표현했다.

| 모델의 선택             | 서버의 후속 처리                              |
|-------------------------|-----------------------------------------------|
| 답변 또는 확인 질문     | 모델이 만든 문장을 사용자에게 전달한다.       |
| 지원하지 않는 업무 안내 | 모델이 만든 거절 안내를 사용자에게 전달한다.  |
| 데이터 조회             | 지정된 조회 작업과 조건을 검사한 뒤 실행한다. |

서버가 이 결정을 읽을 수 있도록 응답 항목과 형식을 정했다. 모델이 조회를 선택하면 조회 작업과 조건을 요구하고, 답변이나 거절을 선택하면 조회 요청을 함께 넣지 못하게 했다. 조회 후에는 최종 답변만 허용해 추가 조회 선택을 막았다.

지침도 기본 역할, 공통 응답 규칙, 처리 방법 선택, 최종 답변 형식으로 나누었다. 이때 기대는 기존 첫 호출 안에서 처리 방법을 명확히 선택하게 하면서 별도 분류 호출을 추가하지 않는 것이었다.

일반 답변과 거절은 모델 응답을 바로 사용하므로 한 번만 호출했다. 사진 조회도 첫 판단 이후 서버가 사진 링크 안내를 만들어 한 번으로 끝냈다. 대기 차량 조회는 서버가 가져온 차량 정보를 모델이 문장으로 안내하므로 최대 두 번 호출했다.

변경 후 실제 모델에 평가용 질문과 가상의 조회 결과를 제공한 28개 사례는 모두 기대한 처리 경로를 충족했다. 일반 안내는 조회 없이 응답했고, 대기 차량 조회만 후속 모델 호출로 이어졌다. 여기서 가상의 조회 결과란 실제 회사 데이터 대신 평가자가 준비한 차량 정보다. 이 평가는 모델의 선택과 답변 흐름을 확인했으며, 실제 조회 서비스와 운영 질문 전체의 정확성을 입증한 것은 아니다.

입력량도 달라졌다. 토큰은 모델이 텍스트를 나누어 처리하는 단위이며, 지침뿐 아니라 질문과 응답 형식 설명도 입력 토큰에 포함된다. 이전 방식과 비교하면 예약 변경 사례의 첫 호출 입력은 3,393토큰에서 4,405토큰으로 늘었다. 반면 대기 차량 조회의 두 호출 합산 입력은 평균 7,056토큰에서 6,638.3토큰으로 줄었다. 실제 청구 금액은 확인하지 않았다.

여기서 처리 결정을 응답 계약에 직접 드러내는 설계가 평가 표본에서 효과를 보였다는 점을 배웠다. 호출 수를 유지해도 지침과 응답 형식, 주고받는 데이터가 바뀌면 입력량은 달라졌다. 또한 응답 형식을 제한하는 일과 의미상 올바른 작업을 선택하게 하는 일은 각각 확인해야 했다. 형식에 맞게 차량 조회를 요청했어도, 그 질문에 차량 조회가 필요했는지는 별도의 문제였다.

## 검색 조건만 추출하는 단계에 집중하도록 했다

처리 방법을 명시적으로 선택하게 한 뒤에도 검색 결과의 일관성 문제가 나타났다. 다음 두 질문은 같은 차량 조건을 묻지만, 첫 질문에는 차량이 있다고 답하고 두 번째 질문에는 없다고 답했다.

> 대기 중인 가솔린 셀토스 1.6 2WD 26년형 있어?

> 대기 중인 가솔린 셀토스 1.6 2WD 26년형 차번호가 뭐야?

셀토스는 차량 모델명이고, 가솔린은 연료다. `1.6`과 `2WD`는 이 사례에서 배기량과 구동방식을 가리키는 사양 표기이며, `26년형`은 2026년형을 뜻한다. 두 질문에서 달라진 것은 답변으로 원하는 정보다. 검색 대상 차량의 조건은 같아야 했다.

조사에서는 서버 검색 방식의 취약점을 확인했다. 당시 서버는 차량명 안에 모델이 만든 검색어가 같은 순서로 연속해서 들어 있는지를 검사했다. 실제 차량명은 `디 올뉴셀토스 1.6 가솔린 터보 2WD 트렌디`였기 때문에, `셀토스 1.6 2WD`라는 검색어는 맞지 않았다. 검색어의 `1.6`과 `2WD` 사이에는 공백만 있지만, 실제 차량명에는 `가솔린 터보`가 들어 있기 때문이다. 연식도 별도 검색 조건으로 표현하지 못했다.

이는 실제 차량을 놓칠 수 있는 검색 취약점이었다. 다만 당시 두 요청에서 모델이 어떤 조건을 만들었는지는 기록되지 않아, 이 취약점이 답변 불일치의 직접 원인이었다고 확정하지는 못했다.

새 설계에서는 조회 선택 뒤에 검색 조건만 추출하는 모델 호출을 넣었다. 위 질문은 다음과 같이 항목별 조건으로 표현하도록 했다.

| 조건 항목 | 추출할 값                                                   |
|-----------|-------------------------------------------------------------|
| 모델명    | 셀토스                                                      |
| 연료      | 휘발유. 질문의 가솔린을 검색에 쓰는 표준 표현으로 변환한다. |
| 모델 연식 | 2026                                                        |
| 세부 사양 | 1.6과 2WD를 각각 보존한다.                                  |

이 단계에는 조건 추출만 맡기고 조회 실행이나 사용자 답변 생성은 맡기지 않았다. 질문에 없는 조건은 추측하지 않도록 했다. 서버도 이 항목들을 검사하고 각각의 조건에 맞춰 검색하도록 바꿨다. 최종 답변을 만드는 모델 호출에는 검증된 조건과 조회 결과를 함께 전달했다.

기대는 사용자가 존재 여부를 원하든 차량번호를 원하든 같은 차량 조건을 보존하는 것이었다. 변경된 흐름에서는 모델이 다음 세 판단을 각각 수행한다.

```text
모델 호출 1: 조회가 필요한지 선택한다.
모델 호출 2: 질문에서 검색 조건만 추출한다.
서버 처리: 조건을 검사하고 차량 데이터를 검색한다.
모델 호출 3: 조건과 검색 결과를 바탕으로 답변한다.
```

정상 완료되는 대기 차량 조회의 모델 호출은 최대 두 번에서 세 번으로 늘었다. 일반 답변과 사진 조회에는 조건 추출 호출을 추가하지 않았다. 각 호출이 별도의 제한 시간을 모두 사용하는 대신, 전체 처리에 허용된 시간을 함께 나누어 썼다.

서로 다른 판단에 각각 집중하고 중간 결과를 확인할 수 있는 구조가 필요하다는 점을 배웠다. 특히 답변의 출력 요구가 달라져도 검색 조건은 보존되어야 했다. 호출 분리와 함께 조건을 표현하는 방식, 서버의 검사와 검색 방식도 바꿨으므로, 호출을 한 번 추가한 것만으로 문제가 해결됐다고 설명할 수는 없다.

## 새 판단을 추가하면서 기존 단계의 책임을 다시 확인했다

이후 실시간 조회 기능을 확장하면서, 차량 목록뿐 아니라 한 차량의 주차위치나 배차불가 같은 상세 정보도 안내하려 했다. 목록 검색과 상세 검색은 서로 다른 조회였으므로 사용자가 어느 정보를 원하는지 판단해야 했다. 예를 들어 “조건에 맞는 차량이 있어?”와 “이 차량이 어디에 주차돼 있어?”는 필요한 데이터가 다르다.

처음에는 검색 조건을 읽는 단계에서 상세 정보가 필요한지도 함께 판단하게 했다. 조건과 상세 여부를 한 번에 얻으면 필요한 조회를 결정할 수 있을 것으로 기대한 구성이었다.

그런데 기존 평가용 3문항 중 2문항에서 연식·사양이 누락됐다. 이어 상세 정보 필요 여부 판단을 첫 번째 조회 선택 단계로 옮겼다. 두 번째 단계는 이전의 짧은 조건 전용 지침과 응답 형식으로 복원했다. 수정 후에는 같은 3문항이 모두 통과했다.

세 문항은 같은 조건의 존재 여부, 차량번호 요청, 차량이 없는 연식의 존재 여부였다. 실제 모델을 사용하되 서버 검색 결과는 평가용으로 준비했다. 조건 추출과 답변을 확인한 평가이며, 실제 사이트의 검색 정확도나 새로 추가한 상세 정보 요청의 판단 정확도까지 확인한 결과는 아니다.

이 경험에서 호출을 나눈 뒤에도 각 호출에 맡긴 책임을 유지해야 한다는 점을 배웠다. 새로운 판단을 기존 단계에 넣으면 그 단계가 이미 수행하던 판단에도 영향을 줄 수 있었다. 기능을 확장할 때는 새 기능뿐 아니라 기존 판단이 유지되는지도 다시 확인해야 했다.

다만 작은 표본만으로 판단 추가가 실패의 단독 원인이었다거나, 짧은 지침이 언제나 더 정확하다고 결론 내리지는 않는다. 관찰한 사실은 상세 여부 판단을 옮기고 조건 전용 지침과 응답 형식을 복원한 뒤 기존 평가가 통과했다는 것이다.

평가를 통과한 뒤에도 최종 문장에는 사용자가 묻지 않은 비서 이름 설명이나 불필요한 문장 부호가 남았다. 조건을 정확히 추출하고 필요한 사실을 답했다는 결과를 전체 답변 품질의 해결로 확대할 수는 없었다.

## 이후 설계에 적용할 배움

모델을 호출할 때는 그 단계에서 결정해야 하는 것, 사용할 입력, 반환할 결과, 서버가 다음 단계 전에 확인할 항목을 구체적으로 정한다. 예를 들어 조건 추출 단계의 성공 여부는 자연스러운 답변 문장보다 모델명·연료·연식·사양이 보존됐는지로 확인한다.

새 기능이 생기면 어느 단계가 그 판단을 맡아야 하는지 검토한다. 기존 단계에 지침과 응답 항목을 추가한 경우에는 그 단계가 수행하던 판단도 다시 평가한다. 이미 호출을 나눴다는 사실만으로 각 단계의 책임이 계속 명확하게 유지되지는 않는다.

설계 효과는 최종 답변과 중간 처리 결과를 함께 보고 판단한다. 불필요한 조회 없이 작업을 선택했는지, 조건을 보존했는지, 서버가 정확히 검색했는지, 결과를 적절히 안내했는지를 각각 확인한다. 호출 수와 함께 입력·출력량과 전체 소요 시간도 비교한다.

이 경험에서 지침과 호출의 구성은 모델이 집중할 일을 정하는 설계였다. 지침을 명확히 하고 판단을 나누는 이유를 구체화할 수 있었지만, 기대한 효과가 나타났는지는 실제 입력과 중간 결과를 통해 확인해야 했다.

## 근거와 확인 범위

본문을 이해하는 데 아래 자료를 먼저 읽을 필요는 없다. 설계 변경과 수치를 확인할 때 사용할 수 있도록 당시 기록과 코드 변경을 연결했다. 코드 변경 제안과 병합 기록은 GitHub의 PR에, 발견한 문제와 조사 내용은 이슈에 보관돼 있다.

- [업무별 지침 수정과 실제 모델 평가](https://github.com/icar-mobility/icar-ai-secretary/blob/c96a925d0513e6c72134c28c5e5c7dc92010d125/docs/tool-routing-prompt-validation.md): 예약·계약 거절 9건과 일반 인수 안내의 불필요한 도구 선택 2건을 포함한 당시 관찰.
- [처리 방법을 구조화한 뒤의 평가](https://github.com/icar-mobility/icar-ai-secretary/blob/c96a925d0513e6c72134c28c5e5c7dc92010d125/docs/structured-lookup-validation.md): 합성 28개 사례의 경로 검증과 입력 토큰 비교.
- [처리 선택과 지침 분리 구현 PR #27](https://github.com/icar-mobility/icar-ai-secretary/pull/27): 기본 역할·공통 규칙·선택·출력 지침을 나누고, 첫 응답을 답변·거절·조회 선택으로 변경한 작업.
- [후속 요청의 맥락 보존 PR #39](https://github.com/icar-mobility/icar-ai-secretary/pull/39): 조회 전후 규칙을 첫 요청에 함께 전달하고 후속 요청의 시스템 지침과 기존 대화를 보존한 작업. 이 작업에서 모델 호출 수를 늘리지는 않았다.
- [같은 조건의 두 질문이 다른 결과를 반환한 이슈 #42](https://github.com/icar-mobility/icar-ai-secretary/issues/42): 당시 데이터 대조, 연속 문자열 검색의 취약점, 직접 원인으로 확정할 수 없었던 범위.
- [조건 추출 분리와 실시간 조회 구현 PR #44](https://github.com/icar-mobility/icar-ai-secretary/pull/44), [해당 변경 반영 후 조회 설계](https://github.com/icar-mobility/icar-ai-secretary/blob/c96a925d0513e6c72134c28c5e5c7dc92010d125/docs/waiting-vehicles-query.md#현재-구현): 최대 세 번의 모델 호출과 서버 검색으로 구성된 흐름.

상세 여부 판단을 옮기기 전후의 3문항 평가는 2026년 10월 4일의 로컬 설계·평가 기록과 당시 결과 파일을 대조해 확인했다. 두 문항의 실패와 수정 후 세 문항의 통과라는 수치는 그 로컬 기록을 근거로 하며, PR 본문에서 직접 확인할 수 있는 수치와 구분한다.

평가에서는 지침, 응답 형식, 검색 조건과 서버 구현을 함께 바꾼 경우가 있다. 따라서 관찰한 개선을 하나의 변경 효과로 분해하지 않는다. 실제 모델을 사용한 합성 평가와 실제 데이터 조회 검증, 운영에서의 질문 처리 성공도 각각 다른 확인 범위다.
