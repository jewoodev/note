# AI 호출을 여러 단계로 나누고 판단 단계를 분리하며 배운 점

렌트카 회사의 AI 비서를 개발하면서, 차량 검색 조건을 추출하는 일을 별도 모델 호출로 분리했다. 이후 상세 조회 기능을 추가하면서 그 호출에 새로운 판단을 함께 맡겼는데, 기존 평가 질문에서 연식과 사양이 누락되는 현상을 관찰했다.

이미 호출을 나누었어도 기능을 확장하는 과정에서 한 단계가 맡는 일이 다시 달라질 수 있었다. 이 글은 새 판단을 추가한 의도와 기대, 실제 결과, 판단을 다른 단계로 옮긴 뒤의 변화, 그 경험에서 얻은 배움을 정리한다.

2026년 10월 4일의 설계와 실제 모델 평가 기록을 바탕으로 2026년 10월 5일에 정리했다. 관찰한 실패와 수정 후 통과를 설명하되, 작은 평가 표본만으로 원인이나 일반적인 모델 특성을 확정하지 않는다.

## 어떤 시스템과 호출을 확장하려 했나

이 시스템은 렌트카 회사의 질문에 한국어로 답하는 AI 비서다. 이름은 카비이며, 사용자 문장을 이해하고 답변을 만드는 언어 모델로 Claude를 사용한다. 차량 데이터는 모델이 직접 소유하지 않는다. 모델이 필요한 조회와 조건을 정하면 서버 프로그램이 회사 시스템에서 실제 데이터를 검색하고, 모델이 그 결과를 설명한다.

예를 들어 “대기 중인 가솔린 셀토스 1.6 2WD 26년형이 있어?”라는 질문에는 모델명·연료·연식·사양에 맞는 차량을 찾아야 한다. 대기 차량은 회사 시스템의 현재 대기 목록에 올라온 차량이다. 그 목록에 있다는 사실만으로 실제 배차 가능 여부까지 확정하지는 않는다.

모델 호출은 지침과 데이터를 보내고 모델 응답을 받는 한 번의 요청이다. 당시 대기 차량 조회는 최대 세 번의 모델 호출과 서버 검색으로 구성돼 있었다.

```text
모델 호출 1: 조회가 필요한지 선택한다.
모델 호출 2: 질문에서 차량 검색 조건만 추출한다.
서버 처리: 조건을 검사하고 차량 데이터를 검색한다.
모델 호출 3: 검색 조건과 결과를 바탕으로 답변한다.
```

여기서 조건 추출은 사용자의 문장을 모델명·연료·연식·세부 사양 같은 항목별 값으로 만드는 일이다. 두 번째 호출에는 현재 질문, 조건 추출 전용 지침, 반환할 항목과 형식을 정의한 스키마를 제공했다. 조회 실행이나 사용자에게 보여줄 답변 생성은 맡기지 않았다.

이 구성이 기대한 일은 출력 요구가 달라져도 차량 조건을 보존하는 것이었다. 같은 사양의 차량에 대해 “있어?”와 “차번호가 뭐야?”라고 물으면 답변은 달라도 검색 조건은 같아야 했다.

## 상세 조회 여부도 함께 판단하게 하려 했다

새로 추가하려던 기능은 차량 한 대의 상세 정보를 안내하는 것이었다. 기본 목록에서는 차량명·연료·연식 같은 정보를 얻고, 주차위치나 명시적인 배차불가 정보는 별도의 상세 조회로 확인했다. 따라서 사용자가 어떤 정보를 원하는지에 따라 필요한 데이터 조회가 달라졌다.

| 사용자 요청의 예                | 필요한 정보                    |
|---------------------------------|--------------------------------|
| 조건에 맞는 차량이 있어?        | 조건에 맞는 차량의 목록과 건수 |
| 조건에 맞는 차량의 번호가 뭐야? | 목록에서 확인한 차량번호       |
| 이 차량이 어디에 주차돼 있어?   | 해당 차량의 상세 정보          |

위 질문들은 기능의 차이를 설명하기 위한 예시다. 당시 조건 평가에서 사용한 세 질문은 뒤에서 따로 설명한다.

처음에는 두 번째 조건 추출 호출에 상세 정보가 필요한지 판단하는 항목과 지침을 추가했다. 이미 그 단계에서 차량을 찾기 위한 문장을 읽고 있었으므로, 필요한 상세 조회 여부도 함께 얻으려는 구성이었다. 검색 조건과 상세 조회 필요 여부를 한 응답에서 받아 서버 조회에 사용할 수 있을 것으로 기대했다.

겉으로는 기존 호출에 항목 하나를 더하는 변경처럼 보였지만, 모델에게 맡기는 판단은 달라졌다. 원문에 적힌 차량 조건을 추출하는 일에 더해, 사용자가 원하는 정보가 별도의 상세 조회를 요구하는지 판단하게 했다.

이 경험을 정리하면서 새 응답 항목을 추가하는 일을 단순한 형식 변경으로만 볼 수 없다는 점을 배웠다. 그 항목을 채우기 위해 어떤 판단이 추가되는지, 기존 단계가 그 판단을 함께 맡는 것이 적절한지를 검토해야 했다.

## 기존 질문에서 연식과 사양이 누락됐다

기능 확장 후에는 실제 Claude Sonnet 5.5를 사용해 기존 세 질문을 평가했다. 서버가 반환하는 차량 정보는 평가용으로 준비했다. 이 방식은 모델의 조건 추출과 답변을 확인하면서 실제 회사 데이터나 사이트 상태에 영향을 받는 부분을 분리하기 위한 것이었다.

| 평가 질문                            | 유지돼야 하는 검색 조건과 답변                                                   |
|--------------------------------------|----------------------------------------------------------------------------------|
| 가솔린 셀토스 1.6 2WD 26년형이 있어? | 모델명·연료·2026년형·두 사양을 보존하고 준비된 차량이 있다고 답한다.             |
| 같은 26년형의 차번호가 뭐야?         | 같은 조건을 보존하고 준비된 차량번호를 답한다.                                   |
| 가솔린 셀토스 1.6 2WD 25년형이 있어? | 다른 조건은 유지하고 연식만 2025로 추출하며, 준비된 결과에 차량이 없다고 답한다. |

두 번째 질문은 표에서 간단히 표현했지만, 실제 입력에는 첫 질문과 같은 모델명·연료·연식·사양을 모두 적었다. 앞선 대화에서 조건을 이어받는 기능을 평가한 것은 아니다. 셀토스는 모델명, 가솔린은 연료이며, `1.6`과 `2WD`는 이 사례에서 배기량과 구동방식을 가리키는 사양 표기다.

첫 평가에서는 세 질문 중 두 질문에서 연식·사양이 누락됐다. 결과 파일에는 존재 여부를 묻는 두 질문에서 연식이 각각 2026과 2025여야 했지만 값이 없었다는 검사 실패가 남았다. 이 실패는 최종 문장이 기대한 표현과 달랐다는 수준이 아니라, 검색에 사용할 조건 자체가 빠졌다는 문제였다.

조건이 누락되면 서버가 원래 질문과 다른 범위로 검색할 수 있다. 어떤 연식이든 포함하거나, 세부 사양을 확인하지 않은 결과를 반환할 수 있기 때문이다. 마지막 모델 호출이 자연스럽게 설명하더라도 그 전에 검색한 대상이 달라졌다면 사용자가 요청한 차량에 대한 답이 되지 않을 수 있다.

이 관찰을 통해 새 기능을 추가할 때는 새 항목이 반환되는지만 확인해서는 부족하다는 점을 배웠다. 기존에 보존되던 조건이 계속 유지되는지까지 다시 확인해야 했다.

## 형식 검사만으로는 조건 누락을 막을 수 없었다

조건 추출 응답은 서버가 읽을 수 있는 JSON 형식으로 받았다. JSON은 항목 이름과 값을 표현하는 데이터 형식이며, 스키마는 허용하는 항목과 자료형을 정한 규칙이다. 서버에서도 연식의 숫자 범위나 사양 목록의 형태를 검사했다.

그러나 질문마다 지정하는 조건이 다르므로 모든 조건 항목을 필수로 요구할 수는 없었다. 전체 차량을 묻는 질문에는 모델명이나 연식이 없을 수도 있다. 따라서 연식·사양이 빠진 응답이 형식상 유효할 가능성은 남아 있었다.

다음은 위 사례에서 기대한 조건을 설명하는 예시다. 실험 응답 원문을 그대로 옮긴 것은 아니다.

```json
{
  "model": "셀토스",
  "fuel": "휘발유",
  "modelYear": 2026,
  "specificationTerms": ["1.6", "2WD"]
}
```

`model`은 모델명, `fuel`은 연료, `modelYear`는 모델 연식, `specificationTerms`는 세부 사양 목록이다. 가솔린은 서버 검색에 쓰는 휘발유라는 표현으로 통일했다.

반면 아래 응답은 항목의 형태는 맞더라도, 연식과 사양을 명시한 원래 질문에 대해서는 불완전하다.

```json
{
  "model": "셀토스",
  "fuel": "휘발유"
}
```

여기서 형식이 올바른 응답과 질문의 의미를 보존한 응답을 구분해야 한다는 점을 배웠다. 실제 모델 평가에서는 응답을 읽을 수 있는지만 확인하지 않고, 원문에 명시된 각 조건이 보존됐는지를 검사해야 했다.

## 상세 조회 판단을 조회 선택 단계로 옮겼다

수정에서는 상세 정보가 필요한지 판단하는 일을 첫 번째 조회 선택 단계로 옮겼다. 두 번째 조건 추출 단계는 이전의 짧은 조건 전용 지침과 스키마로 복원했다. 네 번째 모델 호출을 추가하지 않았으며, 기존 세 호출 안에서 맡기는 판단을 재배치했다.

| 구성                     | 첫 번째 호출                              | 두 번째 호출                              | 세 번째 호출 |
|--------------------------|-------------------------------------------|-------------------------------------------|--------------|
| 상세 기능 추가 전        | 조회 필요 여부 선택                       | 검색 조건 추출                            | 결과 안내    |
| 상세 기능을 넣은 첫 구성 | 조회 필요 여부 선택                       | 검색 조건 추출과 상세 정보 필요 여부 판단 | 결과 안내    |
| 수정한 구성              | 조회 필요 여부와 상세 정보 필요 여부 선택 | 검색 조건만 추출                          | 결과 안내    |

첫 번째 호출이 반환한 상세 조회 필요 여부와 두 번째 호출이 반환한 검색 조건은 서버에서 결합했다. 실제 상세 조회를 실행할 수 있는지는 서버가 검색 결과를 바탕으로 결정했다. 당시 정책은 조건에 맞는 차량이 정확히 한 대인 경우에만 그 차량의 상세 정보를 추가 조회하는 것이었다. 여러 대라면 한 대를 지정하도록 안내했다.

이 설계는 사용자가 어떤 종류의 정보를 원하는지 판단하는 일을 조회 선택 단계에 두고, 어떤 차량을 찾을지 정하는 조건 추출은 그대로 유지하려는 선택이었다. 상세 조회 대상이 실제로 한 대인지 확인하는 일까지 모델에게 추측하게 하지는 않았다.

이 경험에서 새 기능을 구현할 때는 기존 단계에 판단을 보태는 방법과, 전체 흐름에서 그 판단을 맡을 위치를 다시 정하는 방법을 함께 검토해야 한다는 점을 배웠다. 호출 수를 늘리지 않으면서도 단계의 역할을 조정할 수 있었다.

## 수정 후 기존 평가는 통과했지만 새 기능 검증은 남았다

판단을 옮긴 뒤 같은 세 질문을 다시 평가했고, 조건 추출과 존재 여부·차량번호·0건 답변 검증이 모두 통과했다. 전후 결과는 다음과 같이 정리할 수 있다.

| 평가 대상            | 상세 판단을 조건 추출에 넣은 구성 | 판단을 조회 선택으로 옮긴 구성 |
|----------------------|-----------------------------------|--------------------------------|
| 2026년형 존재 여부   | 연식·사양 누락으로 실패           | 조건과 존재 여부 검증 통과     |
| 같은 조건의 차량번호 | 검증 통과                         | 검증 통과                      |
| 2025년형 존재 여부   | 연식·사양 누락으로 실패           | 조건과 0건 답변 검증 통과      |

이 평가는 기존 조건 추출 기능이 유지되는지 확인한 결과다. 새로 추가한 “주차위치를 알려 줘” 같은 상세 정보 요청에서 모델이 상세 조회 필요 여부를 정확히 선택하는지는 이 세 질문만으로 확인할 수 없었다. 상세 조회 정책과 실제 데이터 조회는 별도의 서버 테스트와 실제 사이트 조회로 검사했지만, 그것도 모델의 새로운 의도 판단 정확성을 대신하지는 않는다.

또한 세 질문이 통과한 뒤에도 최종 문장에는 불필요한 비서 이름 설명이나 닫는 기호 잔재가 남았다. 조건과 필요한 사실을 확인한 평가의 통과를 전체 답변 품질의 해결로 해석할 수는 없었다.

여기서 기존 기능의 유지, 새 판단의 정확성, 실제 조회 동작, 답변 문장의 품질은 각각 확인해야 한다는 점을 배웠다. 어느 한 평가를 통과했다고 나머지까지 확인된 것은 아니었다.

## 관찰한 결과와 원인 설명을 구분했다

전후 기록에서 확인한 것은 상세 판단을 추가한 구성에서 기존 조건이 누락됐고, 그 판단을 옮기면서 조건 전용 지침과 스키마를 복원한 구성에서는 기존 평가가 통과했다는 사실이다.

하지만 단순히 “모델이 맡은 일이 많아져 집중력이 떨어졌다”라고 원인을 확정할 수는 없다. 지침과 스키마가 함께 바뀌었고, 표본은 세 질문뿐이었다. 모델의 내부 처리 과정이나 어떤 변경 요소가 실패를 유발했는지를 따로 측정한 실험도 아니었다.

따라서 이 사례에서 얻은 설계 판단은 한 호출에 새 판단을 추가하면 기존 결과에도 영향을 줄 수 있으므로 다시 평가해야 한다는 것이다. 짧은 지침이 언제나 정확하거나, 한 호출에는 반드시 하나의 판단만 맡겨야 한다는 보편적인 규칙을 입증한 것은 아니다. 수정한 첫 번째 호출도 조회 필요 여부와 상세 정보 필요 여부를 함께 판단한다.

이 경험은 호출의 개수만으로 책임 분리가 유지됐는지 판단할 수 없다는 점을 보여줬다. 실제로 바뀐 입력·지침·출력 항목과 각 단계에서 요구하는 판단을 함께 살펴야 했다.

## 이후 설계에 적용할 배움

기능을 추가할 때는 새 응답 항목뿐 아니라 그 항목을 만들기 위해 필요한 판단을 적는다. 검색 조건을 읽는 일인지, 사용자가 원하는 정보 종류를 선택하는 일인지, 실제 데이터로 실행 가능성을 확인하는 일인지 구분하고 적절한 단계에 배치한다.

기존 단계의 지침이나 스키마를 바꾸면 이전에 통과했던 질문도 다시 평가한다. 항목의 형식과 함께 원문에 적힌 조건이 보존되는지 확인하고, 출력 요구만 다른 질문과 조건 자체가 다른 질문을 함께 준비한다.

기존 질문의 재검증과 새 기능 평가도 나눠 준비한다. 이 사례에서는 조건 추출이 유지되는지 확인하는 세 질문과, 상세 정보 요청을 올바르게 선택하는 질문이 각각 필요했다. 서버의 상세 조회 성공과 모델의 상세 의도 판단도 별도로 확인해야 했다.

수정 후 결과가 좋아졌더라도 관찰한 범위를 넘어서 원인을 일반화하지 않는다. 이번 경험의 핵심은 이미 분리한 호출도 확장 과정에서 역할이 달라질 수 있으며, 그 변화를 실제 입력과 중간 결과로 다시 확인해야 한다는 점이었다.

이 문항별 결과와 최종 문장에 남은 문제는 로컬 기록을 근거로 하며, 공개 PR 본문에서 직접 확인할 수 있는 수치와 구분한다. 이 글을 작성하면서 모델 평가나 운영 배포를 새로 실행하지는 않았다.
