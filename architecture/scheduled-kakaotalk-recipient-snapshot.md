# 예약한 뒤 채팅방을 등록 해제하면, 그 예약은 누구에게 가야 할까?

월요일 오후에 내부 업무 시스템인 ERP에서 공지를 작성하고 화요일 오전 9시로 전송을 예약했다고 해보자. 이때 등록된 수신 채팅방은 A방과 B방이다. 예약을 마친 뒤 동료가 B방을 등록 해제하고 C방을 추가했다. 화요일 아침, 카카오톡을 전송하는 별도 서비스인 비서는 어느 방에 공지를 보내야 할까?

이 기능에서는 **월요일에 확정한 A방과 B방이 기존 예약의 대상**이다. C방은 이후 등록 목록을 바탕으로 만드는 새 예약에 포함된다. 그래서 ERP에서 ‘채팅방 등록 해제’와 ‘이미 확정한 예약의 변경’은 서로 다른 동작이 됐다.

## 현재 목록으로 전송하면 예약 이후에도 수신자가 바뀐다

전송 직전에 등록 목록을 읽는 방식은 간단하다. 비서가 A방과 C방을 읽고 그대로 보내면 된다. 이 방식은 등록 해제를 기존 예약에도 즉시 반영해야 하는 서비스라면 맞을 수 있다. 우리 기능에서는 담당자가 예약을 확정할 때 정해진 수신 대상을 이후에도 알 수 있어야 했다. 특히 예약 후에 새로 등록한 방이 과거 공지를 받으면, 그 방에 보낼 의사가 있었는지 확인할 방법이 없다.

그래서 ERP는 담당자가 예약을 누를 때 비서에게 **현재 등록된 전체 목록을 새로 조회**한다. 화면에 열린 채팅방 관리 목록은 화면을 띄운 시점의 정보일 수 있다. 예약에는 그때 다시 받은 전체 목록을 검증해 사용한다. 등록된 방이 없거나 재확인이 필요한 방이 하나라도 있으면 예약을 중단하고, 담당자가 목록을 정리한 뒤 다시 예약하도록 안내한다.

이렇게 한 번 정해진 목록을 **예약 확정본**이라고 부른다. 이후 등록을 해제하는 것은 그 방을 앞으로 만들 예약의 목록에서 제외하는 일이다. 이미 확정한 예약에서 수신 대상을 바꾸려면, 실행이 허가되기 전에 그 예약을 취소하고 다시 만든다.

## 예약을 증명하는 데이터와 실제 방을 찾는 데이터

| 저장하는 곳 | 보관하는 정보 | 쓰는 시점 |
| --- | --- | --- |
| ERP | 예약 본문과 당시의 수신 대상 목록. 대상별 등록 ID·대상 버전·표시 이름, 발신 계정 범위 | 이 예약에 어떤 방이 포함됐는지 확인할 때 |
| 비서 | 발신 계정 범위와 등록 ID·대상 버전으로 실제 카카오톡 방 ID를 찾을 수 있는 정보 | 예약에 포함된 방을 기기에서 다시 열 때 |

여기서 **대상 버전**은 비서가 등록 과정에서 확인한 방의 식별 정보를 가리킨다. 표시 이름은 사람이 예약 목록을 읽을 때 쓰고, 실제 전송할 방은 저장한 식별자로 찾는다. 그래서 비서가 B방을 활성 목록에서 빼더라도 이미 만들어진 예약에 필요한 과거 식별 정보는 보존해야 한다. 이름이 같은 다른 방을 발견하거나 과거 식별 정보로 방을 확인할 수 없으면 해당 방의 전송을 중단한다.

예약별 전체 목록의 원본은 ERP에 둔다. 실행이 허가되면 비서가 ERP에서 확정본을 읽고, 기기로 넘겨야 할 본문과 대상 참조를 실행 작업에 임시로 저장한다. 임시 작업은 완료 후 정리한다. ERP의 예약 원본, 비서의 방 식별 정보, 실행 작업은 각각 필요한 기간이 다르다. 이 차이를 구분하니 ‘등록 해제하면 어떤 데이터를 지워도 되는가’도 따로 설명할 수 있었다.
