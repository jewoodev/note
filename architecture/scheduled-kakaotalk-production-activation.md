# 하나의 기능에 대한 배포 대상이 여러 곳이면 어떻게 설계할 것인가?

일일 카카오톡 예약 기능을 개발하고 나니 배포할 곳이 여럿이었다. 담당자가 예약을 만드는 내부 업무 시스템인 ERP, 정해진 시각에 신호를 보내는 AWS 스케줄러, 그 신호를 받는 큐, 그리고 큐를 읽고 안드로이드 기기에서 카카오톡을 보내는 비서 서비스가 함께 움직여야 했다. ERP에 예약 버튼이 먼저 열리면, 담당자는 공지가 제때 나갈 것이라 기대하고 일정을 등록할 수 있다.

그래서 **실행에 필요한 자원을 준비하는 시점과 담당자가 새 예약을 만들 수 있는 시점**을 설정으로 나눴다. 그 사이에 비서가 ERP 실행 API에 인증할 수 있게 만드는 단계도 따로 뒀다.

## 세 가지를 따로 켤 수 있게 한 이유

| 설정 | 켜면 생기는 변화 |
| --- | --- |
| 예약 인프라 준비 | 전용 스케줄러 그룹, 작업 큐와 실패 큐, IAM 권한, 실행 토큰을 보관할 Secret을 준비한다. |
| ERP 실행 API 인증 | ERP 서버에 실행 토큰을 넣고 해당 Secret을 읽을 권한을 준다. 비서는 이 토큰을 제시해 실행 권한을 요청한다. |
| 사용자 예약 | ERP가 사용자의 새 예약을 받고 스케줄러에 일정을 등록할 수 있다. |

처음에는 사용자 예약을 켜야 ERP 서버에 실행 토큰도 들어갔다. 그러면 비서가 운영 ERP에 인증할 수 있는지 확인하려는 작업과 사용자가 새 예약을 만들 수 있게 하는 작업이 묶인다. 토큰 주입 여부를 별도 설정으로 옮겨, 새 예약을 닫은 채로 두 서비스의 인증을 연결할 수 있게 했다.

세 설정을 독립적으로 다룰 수 있어도 선행 조건은 있다. 실행 API를 켜려면 예약 인프라와 비서 연동 설정이 필요하고, 사용자 예약을 켜려면 실행 API도 켜져 있어야 한다. Terraform이 이 조건을 검사하도록 했다.

## Terraform으로 적용한 설정이 실행 중인 서버에 들어가기까지

이 프로젝트에서 Terraform은 ERP 컨테이너가 읽을 환경 변수와 Secret 참조를 담은 **ECS 태스크 정의**를 만든다. 태스크 정의는 컨테이너를 띄울 때 사용할 설정이다. 실행 중인 ERP 서비스에 어떤 태스크를 배포할지는 배포 파이프라인이 관리한다. 파이프라인은 Terraform의 기준 태스크 정의와 배포할 애플리케이션 이미지를 합쳐 새 리비전을 등록하고, ECS 서비스의 실행 태스크를 교체한다.

그래서 활성화할 때는 Terraform 적용 결과를 확인한 뒤 백엔드 배포를 따로 실행했다. 그리고 ECS 서비스가 새 태스크로 안정화됐는지, 그 태스크에 사용자 예약 설정과 실행 토큰 참조가 들어갔는지 확인했다. 비서 쪽도 운영 백엔드의 큐 소비 설정, 같은 Secret 참조, 안드로이드 실행 워커의 기동을 각각 확인했다.

## 실제 운영에서 확인한 범위

운영에서는 인프라와 비서의 작업 환경을 먼저 준비했다. 이후 ERP 실행 API 인증과 사용자 예약 설정을 **같은 ERP 배포에서** 활성화했다. 플래그를 나눠 두면 두 단계를 별도로 배포해 확인할 수 있고, 준비 상태에 따라 함께 켤 수도 있다.

당시 별도 테스트 발송은 생략했다. 스케줄러와 큐가 있고, 양쪽 서버 설정이 들어갔으며, 기기 워커가 기동했다는 사실까지 확인했다. 팀에 공유할 수 있는 건 “운영 ERP에서 예약 기능을 사용할 수 있다”는 점이었다. 실제 카카오톡 수신 여부는 운영 예약이 실행된 뒤에 확인할 수 있다.

이 경험에서 얻은 건 배포 완료를 보고할 때 **어떤 설정을 바꿨는지보다, 어떤 상태를 직접 확인했는지**를 적는 편이 다음 사람이 판단하기 쉽다는 점이다.
