# 프론트엔드 테스트와 배포 개선에서 배운 비용 분석과 책임 분리

**테스트를 빠르게 만들려면 무엇이 느린지 먼저 측정하고, 각 검증에 필요한 실행 환경을 선택해야 한다. 배포를 단순하게 만들려면 준비 작업의 책임을 한 곳에 모으고, 외부 시스템에 접근하기 전에 소스 상태를 다시 확인해야 한다.**

이 글은 React·TypeScript 프론트엔드의 테스트와 배포를 정리한 PR #281을 바탕으로 한다. 대상은 금융계약 등을 관리하는 업무 화면과 별도의 브랜드 웹사이트다. 프로젝트를 몰라도 적용할 수 있도록 개념, 실제 변경, 남은 검증 범위를 함께 설명한다.

## 1. 필요한 배경

| 개념 | 의미 |
| --- | --- |
| CI | 변경한 코드의 테스트와 빌드를 자동 실행하는 과정 |
| Vitest | 이 사례에서 사용한 JavaScript·TypeScript 테스트 도구 |
| Node 환경 | 브라우저 화면 없이 JavaScript를 실행하는 환경 |
| jsdom | DOM 등 브라우저의 일부 기능을 제공하는 테스트 환경. 실제 브라우저와 같지는 않다. |
| 캐시 | 서버에서 받은 데이터를 화면에서 재사용하기 위해 보관한 상태 |
| revision | 사용자가 편집 중인 데이터가 몇 번째 상태인지 구별하는 버전 |
| 멱등성 키 | 같은 등록 요청의 재시도로 데이터가 중복 생성되지 않도록 요청을 식별하는 값 |
| clean worktree | Git이 감지하는 미커밋 변경이 없는 작업 디렉터리 |

당시 배포는 AWS CodeBuild에서 소스를 준비한 뒤 셸 스크립트로 프론트엔드를 빌드하고 S3·CloudFront에 게시하는 구조였다. CodeBuild 설정과 배포 스크립트 양쪽에 의존성 설치가 있어 `npm ci`가 중복 실행됐다.

테스트 측면에서는 순수 입력 검증을 확인할 때도 React 화면을 렌더링하고 클릭하는 경우가 있었다. 반대로 `.test.ts` 파일이어도 브라우저 API를 사용하는 테스트가 있어 전부 Node로 옮길 수는 없었다.

## 2. 전체 시간을 단계별로 나눠 본다

당시 작업 기록에 남은 변경 전 CodeBuild 관측값은 전체 약 4분 27초, 테스트 70.83초, `DOWNLOAD_SOURCE` 112초였다. 이 값은 과거 조사 기록이며 이번 문서 작성에서 AWS 로그를 다시 조회한 결과는 아니다.

이 기록은 “CI가 느리다”와 “테스트가 주된 병목이다”가 같은 말이 아님을 보여 준다. 소스 다운로드, 의존성 설치, 테스트, 빌드, 업로드, CDN 반영 대기를 나눠 봐야 어느 변경이 전체 시간에 영향을 주는지 판단할 수 있다.

또한 측정 구간의 포함 관계를 확인해야 한다. 예를 들어 배포 스크립트 시간이 설치·테스트·빌드를 포함한다면 각각의 시간을 단순히 더하면 중복 계산이 된다.

PR #281에서 코드로 확인되는 개선은 중복 설치 제거와 테스트 실행 환경 분리다. 변경 후 전체 CodeBuild가 몇 초로 줄었는지는 PR 본문에 제시돼 있지 않다. 따라서 테스트 개수 감소를 전체 배포 시간의 개선 수치로 바꿔 설명하지 않는다.

## 3. 파일 확장자보다 실행 환경 의존성을 기준으로 나눈다

변경 후 Vitest 설정은 두 프로젝트로 나뉜다.

| 프로젝트 | 포함 범위 | 실행 환경 |
| --- | --- | --- |
| `node` | 기본적으로 `.test.ts`, 브라우저 의존 파일은 제외 | Node |
| `jsdom` | `.test.tsx`와 명시한 브라우저 의존 `.test.ts` | jsdom, 공통 화면 테스트 설정 |

브라우저 의존 예외 목록에는 인증 API, 스프레드시트 초안·파서, PDF 전처리 테스트가 들어갔다. 당시 실험 기록에는 일괄 Node 실행 중 `Storage is not defined`, `FileReader is not defined`가 발생했다고 남아 있다. 이 실패는 실행 환경의 경계를 구분하는 근거였다.

React를 사용하지 않는다고 브라우저 의존성이 없는 것은 아니다. 파일을 읽는 방법이나 저장소 접근 때문에 브라우저 API가 필요할 수 있다. 반대로 날짜 비교나 요청 객체 생성은 화면을 렌더링하지 않아도 검증할 수 있다.

당시 설정은 `maxWorkers: 2`로 워커 수도 제한했다. 이는 이 변경에서 선택한 실행 설정이지, 모든 머신과 테스트 구성에서 2개가 최적이라는 결론은 아니다.

## 4. 업무 판단과 UI 연결을 분리하면 검증 비용을 다르게 배분할 수 있다

기존 `FinanceContractActions` 컴포넌트에는 입력 정리, 이자율 검증, 중도상환일 판단, 오류 안내 선택이 함께 있었다. 이번 변경에서는 이를 `financeContractActionPolicy.ts`로 추출했다.

정책 함수는 다음 형태의 결과를 반환한다.

```typescript
type PreparedRequest<T> =
  | { ok: true; request: T }
  | { ok: false; message: string };
```

예를 들어 중도상환 요청 준비 함수는 현재 상태, 만기일, 입력한 상환일, `today`를 인수로 받는다. 테스트는 화면의 날짜 입력 칸을 매번 조작하지 않고 입력 조합에 따른 결과를 확인한다. 오늘 날짜도 인수로 받으므로 시간 조건을 명시적으로 구성할 수 있다.

| 정책 테스트에서 확인 | UI 테스트에서 확인 |
| --- | --- |
| 필수값 누락과 잘못된 이자율 | 오류가 화면에 표시되고 API 요청이 차단되는지 |
| 날짜 조건과 검증 우선순위 | 입력값이 실제 요청으로 전달되는지 |
| 공백 제거와 요청 객체 생성 | 응답이 목록·상세 캐시에 반영되는지 |
| API 오류 코드별 안내 선택 | 오류 안내와 입력 상태가 화면에서 유지되는지 |

정책 테스트가 통과해도 컴포넌트가 그 함수를 호출하지 않으면 화면은 잘못 동작할 수 있다. 따라서 대표적인 잘못된 입력의 API 미호출 검증은 UI에 남겼다. 반대로 날짜 조합마다 똑같은 렌더링·입력·클릭 과정을 반복할 필요는 줄였다.

여기서 분리한 정책은 프론트엔드의 요청 준비와 안내 정책이다. 서버의 최종 업무 검증을 대체하는 것은 아니다.

## 5. 테스트를 줄일 때는 개수보다 검증 책임의 이동을 확인한다

당시 PR은 등록, 캐시 반영, revision 무효화, 경고 확인, 멱등성 회귀를 유지했다고 설명한다. 실제 초안 화면 테스트에는 다음 시나리오가 남아 있었다.

- 사용자가 수정한 뒤에는 이전 검증 결과로 등록하지 못한다.
- 검증 요청 이후 편집 버전이 바뀌면 늦게 도착한 응답을 무시한다.
- 경고를 확인해야 검증된 버전을 등록할 수 있다.
- 여러 차량을 등록하면 반환된 계약들을 캐시에 반영한다.
- 등록 결과가 불확실할 때 같은 멱등성 키를 사용하는 흐름을 확인한다.

이들은 단일 함수의 반환값만으로는 충분히 확인하기 어려운 상태 연결이다. 네트워크 요청, 편집 상태, 캐시 사이의 관계가 검증 대상이기 때문이다.

한편 별도 계약 분류 선택 컴포넌트 테스트는 삭제했지만, 그룹·선택지·현재 값 확인은 상위 액션 화면 테스트에 포함했다. 어떤 검증을 없앴는지 판단하려면 파일 삭제 여부뿐 아니라 해당 assertion이 어디로 이동했는지 확인해야 한다.

재사용할 수 있는 판단 기준은 “비싸니까 삭제한다”가 아니라 **같은 결함을 잡는 중복인지, 더 작은 경계로 옮길 수 있는지, 고유한 연결 검증인지**를 구별하는 것이다.

## 6. 실제 파일 테스트 제거는 별도의 검증 손실로 평가한다

PDF 관련 변경은 업무 규칙의 Node 이동과 다르게 읽어야 한다. 삭제한 코드는 `VOLKSWAGEN_PDF_DIR`가 설정됐을 때 실제 PDF 6개를 읽어 총 360개 상환 행과 일부 알려진 값을 확인하는 하나의 테스트였다. 환경변수가 없으면 건너뛰는 구조였다.

따라서 이를 “실제 PDF 테스트 6개를 없애 항상 CI가 그만큼 빨라졌다”고 설명하면 부정확하다. 여섯 개는 입력 파일 수이며, 해당 검증은 조건부 실행이었다.

변경 후에도 PDF.js를 사용하는 텍스트 레이어 없는 PDF와 손상된 PDF의 실패 분류 테스트는 남았다. 하지만 두 실패 테스트가 실제 문서에서 모든 상환 행을 정확히 추출한다는 증거를 대신하지는 않는다.

이 사례에서 얻을 교훈은 테스트 축소의 이익과 잃는 증거를 구분하는 것이다. 다른 프로젝트에서 같은 결정을 한다면 실제 파일 검증을 별도 통합 테스트나 릴리스 점검으로 옮길지 검토할 수 있다. PR #281이 그런 대체 실행 경로까지 마련했다고 확인된 것은 아니다.

## 7. 배포 준비는 하나의 실행 경로가 책임지게 한다

변경 전후 준비 과정은 다음과 같다.

```text
변경 전
CodeBuild: npm ci → npm test → 배포 스크립트 호출
배포 스크립트: npm ci → npm run build → 게시

변경 후
CodeBuild: 배포 스크립트 호출
배포 스크립트: npm ci → npm test → npm run build → 게시
```

이렇게 하면 CodeBuild에서 배포해도, 스크립트를 직접 호출하는 운영 경로에서도 같은 준비 순서를 거친다. 의존성 설치가 중복되지 않고, 직접 호출하는 경로에서도 테스트가 실행된다.

스크립트는 `FRONTEND_PROJECT_DIRECTORY`로 업무 프론트엔드와 브랜드 웹사이트를 선택한다. 회귀 테스트도 두 경로 각각에 대해 `ci`, `test`, `run build` 호출 목록이 기대 순서와 정확히 일치하는지 확인했다.

“한 번씩 실행한다”는 것은 이 세 npm 명령의 호출에 관한 말이다. npm의 `pretest`, `prebuild`에 공통 생성기가 들어 있다면 생성기는 두 번 실행될 수 있다. 실제 브랜드 웹사이트는 두 훅에서 콘텐츠 생성기를 호출했다. 상위 명령 중복 제거와 내부 작업의 중복 제거를 구분해야 한다.

## 8. 시작할 때 깨끗했던 소스도 빌드 후 달라질 수 있다

기존 배포 스크립트에는 시작 시 `git status --porcelain` 검사와 소스 커밋 SHA 확인이 있었다. 이번 변경은 설치·테스트·빌드가 끝난 뒤 같은 검사를 한 번 더 수행하도록 했다.

```text
최초 소스 상태 확인
  → 소스 커밋 확인
  → 의존성 설치
  → 테스트
  → 빌드
  → 소스 상태 재확인
  → 릴리스 자산 존재 확인
  → 배포 스크립트의 AWS 접근·게시
```

빌드 과정에는 코드 생성이나 콘텐츠 동기화가 포함될 수 있다. 생성된 파일이 Git 추적 대상이면 빌드가 성공해도 커밋에 없던 소스로 산출물이 만들어질 수 있다. 커밋 SHA를 배포 버전으로 기록하는 서비스에서는 이 차이가 중요하다.

두 번째 검사는 테스트나 빌드가 저장소를 변경하면 배포 스크립트의 AWS 접근 전에 실패하도록 한다. 처음부터 변경이 있던 경우와 준비 과정이 변경을 만든 경우를 각각 잡는 것이다.

다만 clean worktree는 완전한 재현 가능 빌드의 증거가 아니다. Git에서 무시하는 파일, 환경변수, 외부 데이터, 도구 버전까지 같다는 것을 입증하지 않는다. 또한 이 순서 검증은 스크립트 자체의 AWS 호출에 관한 것이며, 임의의 npm 훅이 외부에 접근하지 않는다는 보장은 아니다.

## 9. 배포 스크립트 테스트는 순서와 부작용 경계를 검증한다

이번 변경의 셸 회귀 테스트는 `PATH` 앞에 가짜 명령을 둬 `git`, `npm`, `aws` 등을 대체했다. 실제 배포 없이 실행 순서와 중단 조건을 관찰하기 위한 방식이다.

추가한 핵심 시나리오는 다음과 같다.

1. 가짜 `npm`이 빌드가 끝난 뒤 소스 변경 표시를 남긴다.
2. 가짜 `git status`가 변경된 파일이 있다고 응답한다.
3. 실제 배포 스크립트가 실패해야 한다.
4. 실행 전후 AWS 호출 로그의 줄 수가 같아야 한다.

단순히 “오류가 발생했다”를 확인하는 것보다 **게시 대상 시스템에 접근하기 전에 거절했다**는 사실을 확인하는 편이 요구사항에 가깝다. 정상 흐름에서는 npm 명령 전체 목록을 비교해 순서뿐 아니라 중복 실행도 검사했다.

이 테스트는 실제 npm 설치나 S3·CloudFront의 동작을 검증하지 않는다. 스크립트의 제어 흐름과 명령 인수가 관심사다. 실제 배포 검증과 서로 다른 증거로 취급해야 한다.

기존 스크립트의 공개 버전 확인과 롤백 흐름은 이번 변경 이전에도 있었다. 이를 PR #281에서 새로 만든 성과로 포함하지 않는다.

## 10. 다음 개선에 적용할 질문

- 전체 실행 시간을 겹치지 않는 구간으로 측정했는가?
- 브라우저 API가 필요한 테스트와 순수 로직 테스트를 구분했는가?
- 규칙을 작은 함수로 옮기면서 UI 연결을 확인할 대표 시나리오는 남겼는가?
