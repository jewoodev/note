# 마이그레이션 테스트에서 배운 실행 비용과 상태 격리의 분리

**비용이 큰 실행 환경은 재사용하고, 테스트 결과에 영향을 주는 상태는 매번 초기화한다.** 데이터베이스 마이그레이션 테스트를 개선한 이번 사례의 핵심이다. 속도를 높이면서도 이전 스키마와 데이터를 재현하는 검증은 유지했다.

이 글은 Kotlin·Spring Boot·MySQL을 사용하는 업무 시스템의 PR #276을 바탕으로 한다. 프로젝트의 기능보다 테스트 설계에 초점을 맞춰, 다른 서비스에서도 판단 기준으로 사용할 수 있도록 정리했다.

## 1. 마이그레이션 테스트는 무엇을 검증하는가?

서비스가 발전하면 테이블과 컬럼, 제약 조건뿐 아니라 기존 데이터의 표현도 바뀐다. 예를 들어 계약에 저장하던 회사 이름을 별도 회사 테이블의 식별자로 바꾸거나, 여러 불리언 값을 하나의 계약 분류 코드로 통합할 수 있다.

이러한 DB 변경을 순서대로 실행하는 스크립트가 마이그레이션이다. 이 사례에서는 Flyway가 버전별 SQL 파일을 실행하고 적용 이력을 관리했다.

| 용어 | 이 글에서의 의미 |
| --- | --- |
| 스키마 | 테이블, 컬럼, 제약 조건 등 DB의 구조 |
| Flyway | 버전별 DB 변경을 순서대로 적용하고 이력을 관리하는 도구 |
| Testcontainers | 테스트용 MySQL 등을 컨테이너로 실행하는 도구 |
| 백필(backfill) | 기존 데이터를 바탕으로 새 컬럼이나 테이블의 값을 채우는 작업 |
| JdbcTemplate | SQL 실행과 결과 조회에 사용하는 Spring의 JDBC 보조 도구 |
| 상태 격리 | 앞선 테스트가 남긴 데이터나 구조 때문에 다음 테스트의 결과가 달라지지 않게 하는 것 |

빈 DB에 최신 테이블을 만드는 데 성공했다고 해서 기존 고객의 데이터도 올바르게 업그레이드된다는 보장은 없다. 마이그레이션 테스트는 **이전 버전의 구조와 데이터에서 출발해, 변경 후 보존해야 할 사실과 새 제약을 확인**한다.

## 2. 문제: 매번 필요한 것은 새 DB 상태였는데 컨테이너까지 다시 만들었다

변경 전 테스트는 각 시나리오에서 MySQL 컨테이너를 시작하고, Flyway를 설정하고, 연결을 열고 닫는 코드를 반복했다. 테스트가 끝나면 컨테이너도 종료했다.

PR #276은 다음 6개 마이그레이션 테스트 클래스를 공통 기반으로 옮겼다.

- 사용자 초기 역할 배정
- 계약에서 회사 기준정보 백필
- 기존 계약 분류 변환
- 금융계약 등록 정보 분리와 연결
- 정비 테이블 추가
- 차량 테이블 추가

6개는 테스트 **클래스 수**다. 계약 분류 클래스처럼 여러 테스트 메서드를 가진 경우도 있으므로 컨테이너 시작 횟수나 테스트 시나리오 수와 같다고 보면 안 된다.

당시 PR에는 전체 통합 테스트 97개를 유지하면서 실행 시간이 64초에서 약 30초로 줄었다고 기록돼 있다. 이 개선에서 배울 점은 단순히 공통 코드를 추출했다는 사실보다, 반복해서 지불하던 자원 생성 비용과 반드시 초기화해야 할 상태를 구분했다는 점이다.

## 3. 컨테이너 수명과 DB 상태의 수명을 다르게 둔다

새 `MigrationITBase`는 하나의 MySQL 컨테이너를 공유하고 테스트 실행 전에 Flyway `clean()`을 수행한다. 각 테스트는 필요한 이전 버전까지 마이그레이션한 뒤 데이터를 넣는다.

```text
공통 MySQL 컨테이너 시작
  ├─ 테스트 A: clean → 이전 버전 구성 → 기존 데이터 준비 → 마이그레이션 → 검증
  ├─ 테스트 B: clean → 이전 버전 구성 → 기존 데이터 준비 → 마이그레이션 → 검증
  └─ 테스트 C: clean → 이전 버전 구성 → 기존 데이터 준비 → 마이그레이션 → 검증
```

당시 기반 클래스의 핵심 코드는 다음과 같다. 읽기에 필요한 부분만 발췌했다.

```kotlin
@BeforeEach
fun cleanDatabase() {
    Flyway.configure()
        .dataSource(mysql.jdbcUrl, mysql.username, mysql.password)
        .cleanDisabled(false)
        .load()
        .clean()
}

protected fun migrate(target: String? = null) {
    val configuration = Flyway.configure()
        .dataSource(mysql.jdbcUrl, mysql.username, mysql.password)
        .locations("classpath:db/migration")
    target?.let(configuration::target)
    configuration.load().migrate()
}
```

컨테이너는 기반 클래스의 `companion object`에서 `mysql:8.4.11` 이미지와 `migration_test` 데이터베이스로 시작한다. 이 공유 범위는 같은 테스트 JVM·클래스 로더 안이다. 개발 머신 전체나 여러 CI 실행에 걸친 전역 공유를 구현한 것은 아니다.

또한 `JdbcTemplate`은 각 테스트 인스턴스가 같은 공유 DB에 연결하도록 제공한다. 하나의 JDBC 연결을 모든 테스트가 계속 붙잡고 있는 구조는 아니다.

정리하면 재사용 대상은 **MySQL 프로세스**, 초기화 대상은 **테스트 스키마와 데이터, 적용 이력**이다. 단순히 데이터 행만 지우면 변경된 테이블 구조나 Flyway 이력이 남으므로 이전 버전부터 다시 시작할 수 없다.

## 4. 공통화할 것은 실행 기반이고, 드러내야 할 것은 시나리오다

공통 기반은 컨테이너, SQL 접근, 초기화, 버전 지정 마이그레이션을 제공한다. 각 테스트에는 다음 흐름이 그대로 남는다.

```kotlin
// 흐름을 설명하기 위한 의사 코드
migrate("18")
insertLegacyVehicle()

migrate()

assertLegacyVehiclePreserved()
assertNewMaintenanceTablesEmpty()
assertVehicleCanStillBeInserted()
```

실제 정비 테스트는 버전 18의 DB에 차량을 저장한 뒤 마이그레이션했다. 이후 차량 ID, 회사 참조, 차량번호가 유지되는지, 새 정비 테이블들이 비어 있는지, 버전 19의 성공 이력이 있는지, 차량을 추가로 저장할 수 있는지 확인했다.

테스트를 읽는 사람은 “무엇을 재현했는지”와 “무엇을 보존해야 하는지”를 함께 볼 수 있다. 이를 모두 범용 헬퍼 안에 숨기면 코드 줄 수는 줄어도 실패를 해석하기 어려워진다.

여기서 `migrate()`는 특정 버전 하나가 아니라 실행 시점의 최신 마이그레이션까지 적용한다. 기존 데이터가 전체 변경 경로를 통과하는지 확인할 수 있지만, 나중에 추가된 마이그레이션 때문에 오래된 테스트가 실패할 수도 있다. 특정 한 단계만 검증할지 최신까지의 경로를 검증할지는 테스트 목적에 따라 구분해야 한다.

## 5. 과거 스키마의 데이터는 SQL로 직접 준비하는 것이 자연스럽다

일반 업무 테스트에서는 공개 유스케이스로 데이터를 준비하면 내부 저장 구조에 덜 결합할 수 있다. 하지만 마이그레이션 테스트는 **과거의 저장 구조 자체**가 검증 대상이다.

예를 들어 현재 모델에 없는 `is_lease`, `is_operating_funds` 컬럼을 채워야 이전 계약 분류를 재현할 수 있다. 최신 엔티티나 서비스로 데이터를 준비하면 과거의 컬럼과 규칙을 표현하기 어렵다.

이번 변경은 네이티브 SQL과 `JdbcTemplate`으로 접근 방식을 통일했다. 마이그레이션 기반 클래스에는 `@SpringBootTest`가 없다. 최신 애플리케이션 전체를 시작하지 않고 Flyway와 실제 MySQL을 직접 연결한다.

SQL에 변수를 끼워 넣는 방식도 바인딩 파라미터로 바꿨다.

```kotlin
// 변경 방향을 보여 주는 축약 예시
jdbcTemplate.update(
    "INSERT INTO companies (company_type, name) VALUES (?, ?)",
    companyType,
    companyName,
)
```

실제 회사 백필 테스트에서는 회사명과 차량번호를 SQL 문자열에 보간하던 코드를 `?`와 인수 목록으로 바꿨다. 계약 분류 테스트의 불리언 값도 같은 방식으로 전달했다. 이는 SQL 구조와 테스트 입력값을 분리하고 따옴표 등의 값을 SQL 문법과 혼동하지 않도록 한다.

고정된 테스트 상수까지 모두 바인딩한 것은 아니다. 핵심은 동적으로 전달하는 값을 문자열 결합으로 SQL에 삽입하지 않는 데 있다.

## 6. 성공 여부를 넘어 데이터와 제약의 의미를 확인한다

마이그레이션이 예외 없이 끝났다는 사실은 필요한 검증의 시작일 뿐이다. 이 PR은 기존 테스트의 다음 관찰 지점을 유지했다.

| 시나리오 | 확인한 사실 | 다른 프로젝트에 적용할 질문 |
| --- | --- | --- |
| 계약 분류 변환 | 지원하는 기존 불리언 조합이 기대하는 코드로 변환됨 | 이전 표현의 모든 지원 조합이 새 표현으로 정확히 대응되는가? |
| 지원하지 않는 계약 분류 | 특정 제약 조건 때문에 마이그레이션이 실패함 | 해석할 수 없는 데이터를 임의로 바꾸지 않고 중단하는가? |
| 회사 백필 | 기존 회사와 새 회사가 기대 목록으로 남고 이름의 앞뒤 공백이 정리됨 | 기존 참조와 신규 기준정보를 함께 보존하는가? |
| 등록 정보 분리 | 기존 등록 키·해시가 보존되고 키가 없던 계약에도 연결 정보가 생성됨 | 기존 데이터의 서로 다른 상태를 모두 이관하는가? |
| 스키마 변경 | 새 연결 컬럼이 NOT NULL이고 이전 컬럼이 사라짐 | 데이터 값뿐 아니라 목표 구조도 완성됐는가? |
| 사용자 역할 | 지정한 사용자에게만 초기 역할이 배정되고 알 수 없는 역할 코드 INSERT가 실패함 | 과도한 권한 부여와 허용되지 않은 저장을 차단하는가? |
| 차량·정비 테이블 추가 | 기존 계약 참조·차량이 보존되고 기존 형태의 일부 INSERT가 계속 성공함 | 새 구조가 추가돼도 보존해야 할 기존 쓰기가 가능한가? |

계약 분류의 실패 테스트는 `FlywayException`만 확인하지 않고 원인 체인에 예상한 제약 이름이 있는지도 검사했다. 아무 이유로 실패해도 통과하는 테스트가 되지 않도록 실패 원인을 좁힌 것이다.

다만 이 검증이 실패 후 모든 DDL과 데이터가 원상복구됐다는 증거는 아니다. 기존 형태의 INSERT가 성공한다는 검사도 구버전 서버를 실제로 띄워 전체 업무 흐름을 검증한 것과는 다르다. 테스트가 관찰한 범위만 결론으로 삼아야 한다.

## 7. 공유 상태를 선택하면 실행 방식도 설계의 일부가 된다

공유 DB를 매번 초기화하는 구조는 순차 실행에서 이해하기 쉽다. 두 테스트가 동시에 같은 DB를 사용하면 다음과 같은 충돌이 가능하다.

```text
테스트 A: 이전 스키마 구성 → 데이터 INSERT → 결과 조회
테스트 B:                         clean → 다른 스키마 구성
```

A가 검증하는 중에 B가 스키마를 지울 수 있다. 당시 Gradle 설정에는 `maxParallelForks = 1`이 있었고 별도의 JUnit 병렬 실행 설정 파일은 확인되지 않았다. 그러나 Gradle의 JVM 개수 제한만으로 향후 JUnit 내부 병렬 실행까지 보호하는 것은 아니다.

이 방식을 다른 곳에 적용할 때는 공유 DB를 사용하는 테스트의 병렬 실행을 막거나, 동시에 실행되는 단위마다 별도 데이터베이스를 제공하는 식으로 격리 범위를 다시 정해야 한다. PR #276이 병렬 실행용 잠금이나 테스트별 DB 분리를 구현한 것은 아니다.

또한 당시 일반 애플리케이션 통합 테스트의 `MySqlITBase`는 별도 컨테이너와 `icar_erp_test` DB를 사용했다. 최신 스키마로 애플리케이션을 실행하는 테스트와 스키마를 지웠다 다시 만드는 테스트의 기반을 분리한 것이다. 이름만 비슷하다고 두 기반을 합치면 초기화의 영향 범위가 달라진다.

`cleanDisabled(false)`는 Testcontainers가 만든 폐기 가능한 DB 연결에 사용됐다. 외부 설정으로 임의의 DB 주소를 받는 범용 초기화 코드로 옮길 때는 이 전제가 유지되는지 확인해야 한다.

## 8. 성능 수치는 검증 범위와 함께 읽는다

PR 본문과 커밋 메시지에는 전체 통합 테스트 실행 시간이 64초에서 약 30초로 줄었다고 기록돼 있다. 보고된 값으로 계산하면 약 34초, 약 53%의 감소다.

이 수치는 **마이그레이션 테스트만의 실행 시간**이 아니라 당시 전체 통합 테스트의 기록이다. 또한 테스트 개수 97개가 같다는 사실만으로 모든 검증이 보존됐다고 단정할 수는 없다. 기존 데이터 준비, 실패 조건, 결과 검증이 변경 후에도 남았는지 diff를 함께 읽어야 한다.

컨테이너 시작을 반복하지 않도록 바꾼 것은 코드로 확인된다. 다만 컨테이너 시작, SQL 실행, 다른 테스트의 실행 시간이 각각 얼마나 기여했는지에 대한 상세 측정은 확인하지 않았다. 다른 머신이나 이미지 캐시 상태에서도 같은 비율로 빨라진다고 일반화할 근거는 없다.

이번 문서 작성에서는 테스트를 다시 실행하지 않았다. 당시 PR에 보고된 성능과 현재 코드 검토로 확인한 설계 근거를 구분해 기록했다.

## 9. 다음 테스트 기반 개선에 적용할 질문

- 느린 원인이 실제 검증인가, 실행 환경을 반복 생성하는 비용인가?
- 재사용해도 되는 자원과 테스트마다 초기화해야 할 상태는 무엇인가?
- 데이터뿐 아니라 스키마와 마이그레이션 이력도 초기화되는가?
- 공유 범위가 테스트 인스턴스, JVM, CI 작업 중 어디까지인가?
- 병렬 실행을 켜면 다른 테스트의 상태를 지울 수 있는가?
- 과거 스키마의 데이터를 최신 애플리케이션 모델 없이 재현할 수 있는가?
- 지원하는 입력과 중단해야 할 입력을 모두 검증하는가?
- 기존 값 보존, 새 제약, 기존 쓰기 가능 여부를 필요한 범위에서 확인하는가?
- 성능 비교가 같은 테스트 범위에서 이뤄졌으며, 수치의 측정 조건을 설명할 수 있는가?
