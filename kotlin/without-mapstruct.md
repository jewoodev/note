# 코틀린에서 MapStruct가 없어져서 좋은 이유

자바에서 코틀린으로 전환하면서 MapStruct를 제거했을 때의 장점은 매핑 자체가 사라졌다는 데 있지 않다. **매핑을 직접 작성하는 비용이 낮아져서, 단순한 변환을 위해 별도의 도구와 규칙을 유지할 필요가 줄었다는 데 있다.**

이 문서는 특정 프로젝트의 제거 이력이나 성능 측정 결과가 아니라, 언어 기능과 유지보수 관점에서 그 이유를 설명한다.

## MapStruct가 해결하던 문제

애플리케이션에서는 도메인 객체를 API 응답용 DTO로 바꾸는 일이 자주 생긴다. DTO는 외부로 전달할 데이터를 담는 객체다. 매핑은 원본의 값을 골라 대상 객체의 필드에 연결하는 작업이다.

자바에서 이를 직접 작성하면 생성자에 인수를 순서대로 나열하거나, 여러 setter를 호출하는 코드가 반복되기 쉽다. 생성자 인수가 많고 같은 타입이 반복되면 각각의 값이 무엇을 의미하는지도 읽기 어려워진다.

MapStruct는 선언한 매핑 규칙을 바탕으로 컴파일 시점에 변환 구현 코드를 생성한다. 반복적인 복사 코드를 줄이는 대신, 개발자는 매핑 어노테이션과 자동 매핑 규칙, 코드 생성 설정을 관리하게 된다.

## 코틀린에서는 직접 작성해도 충분히 읽기 쉽다

코틀린은 이름 있는 인수와 표현식 함수를 제공한다. 확장 함수를 사용하면 변환을 호출하는 쪽도 자연스럽게 표현할 수 있다.

```kotlin
data class Customer(val name: String)

data class Vehicle(val number: String)

data class Rental(
    val id: Long,
    val customer: Customer,
    val vehicle: Vehicle,
)

data class RentalResponse(
    val id: Long,
    val customerName: String,
    val vehicleNumber: String,
)

fun Rental.toResponse() = RentalResponse(
    id = id,
    customerName = customer.name,
    vehicleNumber = vehicle.number,
)
```

왼쪽에는 대상 필드가, 오른쪽에는 원본 값이 드러난다. 같은 타입의 인수가 여러 개 있어도 위치를 외워서 읽을 필요가 없다. 이 간결함의 핵심은 이름 있는 인수와 함수 문법이며, `data class`가 매핑을 자동으로 해 주는 것은 아니다.

## 별도의 매핑 규칙을 해석할 필요가 줄어든다

직접 작성한 함수에서는 어떤 값이 어디로 이동하는지가 코드에 드러난다. 필드 이름을 바탕으로 한 자동 매핑이나 어노테이션 설정을 해석하지 않아도 된다.

매핑에 조건이나 변환이 필요할 때도 일반적인 코틀린 표현식으로 작성할 수 있다. 개발자가 알아야 할 지식이 언어 안에 머무르는 것이다.

MapStruct 역시 명시적인 설정과 생성 코드 확인을 지원한다. 차이는 변환 의도를 파악할 때 도구의 규칙과 생성 과정을 추가로 따라가야 하는 정도에 있다.

## 필수 필드의 누락이 컴파일 오류로 드러난다

위의 `RentalResponse` 생성자에 기본값이 없는 필수 인수를 추가하면, 기존 `toResponse()`는 해당 값을 전달하도록 수정해야 한다. 일반적인 생성자 호출 규칙만으로 누락이 드러난다.

MapStruct에서도 매핑되지 않은 대상 필드를 오류로 처리하도록 설정할 수 있다. 코틀린 직접 매핑의 장점은 이 검사를 위해 별도의 매퍼 정책을 알아야 할 필요가 줄어든다는 것이다.

다만 생성자 매핑이 모든 오류를 잡아 주는 것은 아니다.

- 기본값이 있는 인수는 생략할 수 있으므로 필드 추가가 반드시 컴파일 오류로 이어지지는 않는다.
- 같은 타입의 잘못된 값을 전달해도 컴파일은 성공할 수 있다.
- 원본 객체에 필드가 추가되어도 대상에 복사해야 하는지는 컴파일러가 판단하지 못한다.

따라서 컴파일러가 보장하는 것은 생성자 호출의 유효성이다. 변환의 업무적 의미까지 보장하지는 않는다.

## 디버깅과 리팩터링이 일반 함수 작업이 된다

직접 작성한 매핑 함수에는 중단점을 걸고, 호출 지점을 찾고, IDE로 이름을 바꾸는 일반적인 개발 도구를 그대로 사용할 수 있다. 생성된 구현체와 선언부를 오가며 동작을 확인하는 단계가 줄어든다.

MapStruct도 일반 코드를 생성하므로 디버깅이 가능하다. 제거했을 때 얻는 이점은 디버깅 가능 여부가 아니라, 읽고 수정하는 코드와 실제 실행되는 코드 사이의 거리가 짧아진다는 것이다.

## 빌드와 의존성 관리가 단순해진다

MapStruct를 제거하면 그 도구에 필요한 의존성과 어노테이션 처리 설정을 제거할 수 있다. 코드 생성 결과나 프로세서 연동 문제를 살펴볼 일도 줄어든다.

다른 라이브러리가 어노테이션 처리를 사용한다면 처리 기반 전체를 없앨 수 있는 것은 아니다. 또한 실제 빌드 시간 개선 폭은 프로젝트마다 다르므로 측정 없이 단정할 수 없다.

## 필드 복사가 명시적인 선택이 된다

직접 매핑에서는 개발자가 외부에 내보낼 값을 하나씩 선택한다. 자동으로 연결되는 필드를 추론하기보다, 코드 리뷰에서 전달할 값을 바로 확인할 수 있다.

이는 API 응답처럼 외부에 노출할 정보를 의도적으로 선택해야 하는 경계에서 유용하다. 다만 명시적으로 작성했다는 사실만으로 잘못된 데이터 노출을 방지하는 것은 아니며, 필드 선택에 대한 검토는 여전히 필요하다.

확장 함수를 사용하더라도 도메인 객체가 응답 DTO를 알도록 만들 필요는 없다. 위의 `toResponse()`는 웹 계층에 두고 도메인 타입을 가져와 정의할 수 있다. 문법적 편의와 계층의 의존 방향은 별도로 판단해야 한다.

## 언제나 제거하는 것이 정답은 아니다

대규모의 반복 매핑이 이미 안정적으로 관리되고 있거나, 팀이 공통 매핑 설정을 적극적으로 활용하고 있다면 MapStruct를 유지하는 편이 나을 수 있다. 자바 코드가 많이 남아 있는 프로젝트에서도 장점이 유지될 수 있다.

직접 매핑을 선택해도 필드가 많으면 반복 코드는 늘어난다. 또 요금 계산이나 계약 상태 판단 같은 업무 규칙은 단순한 변환 함수에 쌓기보다, 해당 규칙을 책임지는 도메인이나 애플리케이션 로직에서 처리해야 한다.

결국 판단 기준은 코드 줄 수만이 아니다. **변환을 읽고 수정하는 비용, 도구의 규칙을 이해하는 비용, 빌드를 유지하는 비용을 함께 비교해야 한다.** 코틀린에서는 직접 매핑이 충분히 간결해지기 때문에, 많은 단순 변환에서 별도의 매핑 프레임워크를 유지할 이유가 줄어든다.
