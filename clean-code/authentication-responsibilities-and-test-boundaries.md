# 인증 모듈 리팩토링에서 배운 책임 분리와 테스트 경계 설계

인증 기능의 구조를 정리하면서 얻은 가장 큰 교훈은 **코드와 테스트 모두 자신이 책임지는 질문이 분명해야 한다**는 것이다. 파일을 나누는 기준은 독립적으로 사용하는 계약이고, 테스트를 나누는 기준은 검증하려는 동작과 실제로 연결해야 하는 범위다.

이 글은 Kotlin·Spring Boot 기반 업무 시스템의 인증 모듈을 리팩토링한 사례를 바탕으로 한다. 프로젝트를 모르는 독자도 다른 서비스에 적용할 수 있도록 문제, 판단 기준, 구체적인 검증 예제를 함께 정리했다.

## 1. 사례를 이해하는 데 필요한 배경

대상 시스템은 차량, 정비, 회사, 금융계약 등을 관리하는 웹 애플리케이션이다. 사용자는 로그인한 뒤 자신에게 허용된 업무 API에 접근한다. 서버는 세션으로 로그인 상태를 유지하고, 사용자에게 부여된 역할과 권한으로 접근을 판단한다.

여기서 구분해야 할 개념은 다음과 같다.

| 개념 | 의미 | 예시 |
| --- | --- | --- |
| 인증 | 요청한 사용자가 누구인지 확인 | 로그인한 사용자인가? |
| 인가 | 그 사용자가 해당 작업을 할 수 있는지 판단 | 차량 조회 권한이 있는가? |
| 세션 | 여러 요청에 걸쳐 로그인 상태를 이어 주는 서버 측 상태 | 로그인 후 받은 쿠키로 다음 요청 수행 |
| 애플리케이션 포트 | 업무 기능을 호출하거나 외부 기능을 요구하는 인터페이스 | 로그인 실행, 사용자 조회, 세션 무효화 |
| 웹 슬라이스 테스트 | 웹 요청 처리에 필요한 구성만 연결하는 테스트 | 컨트롤러와 보안 필터를 연결하고 업무 포트는 mock으로 대체 |
| 통합 테스트 | 관심 있는 실제 구현들을 연결해 상호작용을 검증하는 테스트 | 비밀번호 초기화 후 기존 세션 사용이 차단되는지 확인 |

변경 전에는 두 가지 문제가 있었다.

- 인증 명령, 포트, 조회 결과 타입, 예외가 여러 타입을 묶은 파일에 있어 파일 이름만으로 책임과 사용처를 찾기 어려웠다.
- `AuthenticationSessionIT`가 로그인과 세션 수명 주기뿐 아니라 차량·정비·회사·금융 API의 접근 제어와 CORS까지 검증했다. 실패한 테스트를 보고 어느 기능의 어느 경계가 깨졌는지 파악하기 어려웠다.

리팩토링의 목표는 공개 API와 기존 업무 동작을 유지하면서 이 책임들을 구분하는 것이었다.

## 2. 파일은 독립적으로 사용하는 계약을 기준으로 나눈다

Kotlin은 한 파일에 여러 타입을 선언할 수 있다. 이 사례에서 문제가 된 것은 문법이 아니라, 서로 독립적으로 사용되는 타입들이 포괄적인 이름 아래 모여 있었다는 점이다.

예를 들어 `AuthenticationProviders.kt`에는 로그인, 비밀번호 변경, 세션 사용자 조회, 사용자 관리 인터페이스가 함께 있었다. 변경 후에는 각 인터페이스를 이름이 같은 파일로 분리했다.

```text
application/
  command/
    AuthenticateUserCommand.kt
    ChangePasswordCommand.kt
  provided/
    AuthenticateUserProvider.kt
    ChangePasswordProvider.kt
    LoadSessionUserProvider.kt
    ManageAppUserProvider.kt
  required/
    AppUserRepository.kt
    AppUserSessionInvalidator.kt
  query/
    AuthenticatedUser.kt
    AppUserAccess.kt
  exception/
    AuthenticationFailedException.kt
    InvalidPasswordException.kt
    ...
```

위 구조는 변경 당시의 일부 타입을 발췌한 것이다. 로그인 호출자는 로그인 계약을, 세션 무효화 구현자는 세션 무효화 계약을 바로 찾을 수 있다.

이 원칙을 모든 타입이나 메서드에 기계적으로 적용할 필요는 없다. 당시 규칙에도 하나의 계약을 이루며 함께 읽고 변경하는 보조 타입은 같은 파일에 둘 수 있다고 명시했다. 사용자 관리 인터페이스 역시 여러 관련 작업을 가진 채 유지했다.

**파일 분리와 서비스 분리는 서로 다른 판단이다.** 리팩토링 과정에서 서비스의 주요 변경은 예외 import 정리였다. 파일을 나눴다는 이유만으로 서비스까지 메서드별로 쪼개지는 않았다. 서비스는 함께 변경되는 업무 규칙과 유스케이스를 기준으로 판단해야 한다.

## 3. 포트의 방향과 예외의 소유권을 드러낸다

`provided`와 `required`는 애플리케이션을 기준으로 읽는다.

| 위치 | 책임 | 이 사례의 예시 |
| --- | --- | --- |
| `application/provided` | 호출자에게 제공하는 업무 기능 | 인증, 비밀번호 변경, 세션 사용자 조회 |
| `application/required` | 업무를 수행하기 위해 필요한 외부 기능 | 사용자 저장소, 사용자의 모든 세션 무효화 |
| `adapter/in/web` | HTTP 입력과 응답 처리 | 요청 변환, 예외를 HTTP 응답으로 변환 |
| `adapter/out` | 요구 포트의 기술적 구현 | DB 접근, 세션 저장소 접근 |

이 구분은 테스트에서 무엇을 대체할지도 알려 준다. 웹 접근 제어가 관심사라면 업무 포트를 대체하고, 업무 서비스와 저장소의 연결이 관심사라면 그 구현을 실제로 연결할 수 있다.

예외에도 같은 기준을 적용했다. `AuthenticationFailedException` 등은 `application/service`의 묶음 파일에서 `application/exception`의 개별 파일로 이동했다. 인증 실패는 특정 서비스 구현의 내부 사정만이 아니라 호출자가 처리할 수 있는 업무 실패이기 때문이다.

실패를 HTTP 응답으로 바꾸는 책임은 기존 웹 예외 처리기에 남겼다. 이 변경에서 해당 처리기는 예외 import 경로만 바뀌었다. 예외의 의미와 외부 응답 계약은 유지했다.

이렇게 하면 구조 변경과 응답 계약 변경을 별도로 검토할 수 있다. 오류 응답 형식 개선, 사용자 관리 API 변경, 잠금 구현 개선 등은 후속 작업으로 분리했다.

## 4. 테스트는 검증하려는 질문에 필요한 구현을 연결한다

인증과 관련 있다는 이유만으로 모든 검증을 로그인 통합 테스트에 넣으면, 차량 접근 권한을 확인할 때도 계정 준비와 로그인 과정에 의존하게 된다.

이번 변경은 테스트를 다음과 같이 구분했다.

| 검증하려는 질문 | 배치한 테스트 | 실제로 연결하는 핵심 범위 |
| --- | --- | --- |
| 차량·회사·정비·금융 API가 미인증 요청이나 권한 없는 요청을 차단하는가? | 기능별 `*SecurityTest` | 웹 컨트롤러와 실제 보안 설정·필터 |
| 허용한 출처에만 CORS 응답을 제공하는가? | `CorsSecurityTest` | 실제 웹·보안 구성 |
| 로그인 후 비밀번호 변경, 역할 변경, 로그아웃이 세션에 반영되는가? | `AuthenticationSessionIT` | 실제 인증·사용자 관리 흐름과 세션 처리, H2 기반 저장소 구성 |
| Spring Session이 MySQL에 저장되고 로그아웃 시 삭제되는가? | `AuthenticationSessionPersistenceIT` | 실제 HTTP 처리와 MySQL 세션 영속성 |

특히 **정해진 권한을 가진 요청의 접근 결과**와 **권한 변경이 기존 세션에 반영되는 과정**을 구분하는 것이 중요했다.

첫 번째는 사용자 조회 결과를 지정한 뒤 실제 필터가 요청을 허용하는지 확인하면 된다. 두 번째는 로그인하고 역할을 부여·회수한 다음 같은 세션으로 다시 요청해야 검증할 수 있다. 조회 결과를 mock으로 바꾸기만 하면 실제 역할 변경과 세션의 연결을 확인할 수 없다.

세션 통합 테스트에서 업무 API 호출이 모두 사라진 것도 아니다. 기존 세션의 권한 반영을 관찰하는 데 필요한 호출은 남아 있다. 테스트 분류는 호출한 URL보다 **그 호출로 무엇을 입증하려는가**에 달려 있다.

## 5. 보안 슬라이스에서는 보안 판단을 실제로 실행한다

새로 만든 `SecurityWebTestSupport`는 실제 `SessionSecurityConfiguration`, 보안 오류 작성기, 요청 로깅 필터를 포함한다. 세션 사용자 조회와 감사 기록 등 애플리케이션 포트는 mock으로 대체한다. 각 기능 테스트에서는 해당 기능의 업무 포트도 대체한다.

사용자 준비에는 애플리케이션이 사용하는 principal 타입인 `AuthenticatedAppUser`를 사용했다. 또한 세션에 로그인 시각을 넣고, 사용자 조회 포트가 해당 사용자를 반환하도록 설정했다.

이 준비가 필요한 이유는 실제 필터가 이 상태들을 읽기 때문이다. 로그인 시각이 없으면 절대 세션 만료 필터에서 거절될 수 있고, 사용자 조회가 실패하면 계정 사용 불가로 거절될 수 있다. 권한 테스트가 의도한 지점까지 도달하려면 그 앞 단계의 조건도 충족해야 한다.

따라서 공통 지원 코드는 정상적인 인증 요청을 만드는 데 필요한 준비를 제공한다. 어떤 경로에서 어떤 권한을 요구하는지는 기능별 테스트에 남긴다.

이 슬라이스가 입증하는 것은 주어진 사용자 상태에서의 웹 보안 동작이다. 실제 로그인 성공이나 DB의 사용자 조회 정확성, MySQL 세션 저장까지 입증하는 것은 아니다.

## 6. 거절 응답과 업무 로직 미호출을 함께 검증한다

보안 테스트에서 `403 Forbidden`만 확인하면 어떤 조건에 의해 차단됐는지 충분히 설명하지 못할 수 있다. 또한 보호하려는 업무 로직이 실행되기 전에 차단됐는지도 확인할 필요가 있다.

금융계약 검증 API 테스트는 같은 불완전한 요청 본문 `{}`에 대해 다음 조건을 비교했다.

| 사용자 조건 | CSRF 조건 | 기대 결과 | 확인하는 경계 |
| --- | --- | --- | --- |
| 다른 관리 권한만 보유 | 유효한 토큰 제공 | 403 | 해당 업무 권한이 없어 접근 차단 |
| 금융계약 관리 권한 보유 | 유효한 토큰 제공 | 400 | 보안 단계를 통과한 뒤 입력 검증에서 거절 |

두 요청 모두 마지막에 `verifyNoInteractions(validation)`으로 업무 검증 포트가 호출되지 않았음을 확인했다. 다른 테스트에서는 금융계약 등록 권한이 있어도 CSRF 토큰이 없으면 403이고, 등록 포트가 호출되지 않는지 검증했다.

CSRF 토큰은 브라우저의 로그인 상태를 악용한 요청을 막기 위한 검증 수단이다. 권한 부족을 검증할 때는 유효한 토큰을 제공해야 CSRF 실패가 의도한 검증을 가리지 않는다.

이 사례에서 일반화할 수 있는 테스트 작성 순서는 다음과 같다.

1. 실패시키려는 조건을 하나 정한다.
2. 그 조건보다 앞에서 요청을 차단할 수 있는 다른 조건들은 충족시킨다.
3. 기대하는 응답을 확인한다.
4. 보호 대상인 업무 포트의 호출 여부도 확인한다.

차량 보안 테스트는 여기서 더 나아가 401·403·200·404 응답의 요청 식별자와 완료 로그도 확인했다. 업무 컨트롤러에 도달하기 전에 실패한 요청도 추적할 수 있어야 한다는 계약을 보안 경계와 함께 검증한 것이다.

## 7. DB 상태와 연결 자체를 검증하는 테스트는 따로 유지한다

MySQL 세션 테스트에서는 로그인 전후 세션 쿠키 값이 달라지는지, 보안 쿠키 속성이 설정되는지, 로그인 후 `SPRING_SESSION` 행이 하나 존재하는지, 로그아웃 후 그 행이 삭제되는지 확인했다.

이 검증에는 SQL 조회가 자연스럽다. 테스트의 질문 자체가 실제 세션 저장소의 상태에 관한 것이기 때문이다. 반대로 업무 유스케이스의 결과를 확인하는 테스트마다 SQL로 내부 상태를 준비하고 읽으면 저장 구조에 불필요하게 결합된다.

당시 백엔드 규칙에는 다음 기준을 기록했다.

- 애플리케이션 통합 테스트는 실제 서비스와 저장소를 연결하되 준비·실행·검증을 공개 유스케이스로 수행한다.
- 저장소나 SQL, 트랜잭션 헬퍼를 직접 사용하는 검증은 영속성 어댑터 통합 테스트에 둔다.
- 실제 커밋, 잠금, 독립 트랜잭션, 동시성이 관심사라면 테스트 전체를 트랜잭션으로 감싸지 않는다.

마지막 규칙은 테스트가 실제로 관찰해야 할 커밋 경계를 하나의 테스트 트랜잭션으로 가리지 않도록 하기 위한 판단 기준이다. 이번 PR이 잠금 구현이나 동시성 문제까지 개선했다는 뜻은 아니다.

또한 MySQL 테스트는 이번에 새로 만든 것이 아니라 이름을 `AuthenticationSessionPersistenceIT`로 바꿔 관심사를 드러낸 것이다. 기존 검증의 이름 변경과 새로운 검증의 추가를 구별해서 읽어야 한다.

## 8. 리팩토링 결과를 팀의 판단 기준으로 남긴다

이번 작업에서는 코드 변경과 함께 `backend/AGENTS.md`에 패키지, 파일 분리, 예외, 테스트 경계 규칙을 기록했다. 규칙은 다음 변경에서도 같은 결정을 내릴 수 있을 정도로 구체적이어야 한다.

예를 들어 “테스트를 잘 나눈다” 대신 “경로별 보안 테스트에는 실제 보안 설정과 필터를 포함하고 애플리케이션 포트만 대체한다”라고 적었다. 또한 도메인·웹 슬라이스는 `*Test`, 실제 DB·세션 연결 검증은 `*IT`로 이름을 구분하도록 했다.

당시 Gradle에는 이미 `test`에서 `*IT`를 제외하고 `integrationTest`에서 실행하는 구성이 있었다. 따라서 테스트 이름과 배치는 실행 범위에도 영향을 준다. 이 PR이 Gradle 실행 구성을 새로 도입한 것은 아니다.

테스트를 옮길 때는 기존 시나리오가 새 위치에서도 보존되는지 먼저 확인해야 한다. 같은 검증을 여러 곳에 추가하면 변경할 곳만 늘어난다. 다만 슬라이스의 권한 판단과 통합 테스트의 실시간 역할 반영처럼 입증하는 사실이 다르면, 비슷한 요청이 등장해도 각각 유지할 이유가 있다.

## 9. 다음 리팩토링에 적용할 질문

- 기존 시나리오의 이동과 신규 검증을 구별하고 중복을 점검했는가?
- 구조 변경과 외부 동작 변경을 각각 검토할 수 있는가?
