# 오류 응답 설계에서 배운 API 계약과 사용자 안내의 분리

**서버는 실패한 사실과 원인을 구조화해서 전달하고, 화면은 사용자가 이해하고 행동할 수 있는 문구를 결정한다.** 이 원칙을 실제 서비스에 적용하려면 오류 코드뿐 아니라 필드 검증 정보, 알 수 없는 응답의 처리, 배포 중 버전 호환성까지 함께 설계해야 한다.

이 글은 Kotlin·Spring Boot 백엔드와 TypeScript·React 프론트엔드를 사용하는 업무 시스템의 오류 응답 개선 사례를 정리한다. 차량·정비·금융계약을 관리하는 시스템이지만, 아래의 판단 기준은 폼 입력과 로그인 기능이 있는 다른 웹 서비스에도 적용할 수 있다.

## 1. 문제: 사용자 문장이 사실상 통신 규약이 되어 있었다

변경 전 프론트엔드는 서버 오류 응답의 `message`를 사용자에게 표시했다. 일부 입력 오류는 영어 문장에 정규식을 적용해 의미와 제한값을 추출했다.

실제 금융계약 입력 화면에는 다음과 같은 처리가 있었다.

```typescript
// 변경 전 코드에서 발췌
const size = /size must be between (\d+) and (\d+)/i.exec(message);
if (size) {
  return `차량번호는 한 번에 ${size[1]}개 이상 ${size[2]}개 이하로 등록해 주세요.`;
}
```

이 코드는 서버의 검증 규칙뿐 아니라 문장의 언어와 표현에도 의존한다. 의미가 같은 문장으로 바뀌어도 정규식이 맞지 않을 수 있다. 화면별 안내를 개선하려고 해도 서버가 어떤 문장을 보내는지 알아야 한다.

이 사례에서 `code` 자체가 없었던 것은 아니다. 이미 존재하던 오류 코드에 더해, 사용자 문장과 필드 검증 정보가 뒤섞여 있었다. 따라서 해결해야 할 문제는 **문장에 숨어 있던 의미를 명시적인 데이터로 옮기는 것**이었다.

## 2. HTTP 상태, 오류 코드, 상세 원인의 역할을 나눈다

변경 후 오류 응답은 다음과 같은 형태를 가진다. 아래 값은 계약을 설명하기 위한 예시다.

```json
{
  "timestamp": "2026-09-08T05:00:00Z",
  "status": 400,
  "code": "INVALID_PASSWORD",
  "reason": "PASSWORD_REUSED",
  "path": "/api/v1/auth/password",
  "requestId": "8f7f0a3b-bc70-43d8-9571-69a0c71b1420",
  "fieldErrors": []
}
```

| 정보 | 책임 | 예시 |
| --- | --- | --- |
| HTTP 상태 | 요청 실패의 큰 분류 | 400: 잘못된 요청, 401: 인증 필요, 409: 충돌 |
| `code` | 클라이언트가 구분할 안정적인 실패 종류 | `INVALID_PASSWORD` |
| `reason` | 같은 코드 안에서 필요한 상세 원인 | `PASSWORD_REUSED`, `POLICY_VIOLATION` |
| `fieldErrors` | 수정할 입력 위치와 검증 조건 | 필드명, 필드 오류 코드, 제한값 |
| `requestId` | 응답과 서버 로그를 연결할 식별자 | 특정 실패 요청 추적 |
| 사용자 안내 | 화면 문맥과 언어에 맞는 설명 | “현재 비밀번호와 다른 비밀번호를 입력해 주세요.” |

`reason`은 필요한 경우에만 보낸다. 모든 오류를 억지로 두 단계로 분류할 필요는 없다. 코드만으로 충분하면 상세 원인은 생략한다.

프론트엔드가 문구를 소유한다고 해서 검증 규칙까지 프론트엔드로 옮기는 것은 아니다. 비밀번호 재사용 여부나 입력 제한 위반은 서버가 판단한다. 프론트엔드는 그 판단 결과를 사용자에게 설명한다.

또한 `message`를 제거한 것은 서버 응답 계약이다. 프론트엔드의 `ApiError`는 여전히 JavaScript `Error`를 상속하고 `message`를 가진다. 다만 그 값은 서버 문장의 복사본이 아니라 프론트엔드가 생성한 안내다.

## 3. 상세 원인은 타입으로 제한하고 공개 범위도 결정한다

변경 전 `InvalidPasswordException`은 문자열을 받았다. 변경 후에는 명시적인 원인 타입을 받는다.

```kotlin
class InvalidPasswordException(val reason: Reason) : RuntimeException(reason.name) {
    enum class Reason {
        POLICY_VIOLATION,
        PASSWORD_REUSED,
    }
}
```

웹 예외 처리기는 `exception.message`를 해석하지 않고 `exception.reason.name`을 응답에 넣는다. 계정 충돌도 같은 방식으로 `EMAIL_ALREADY_IN_USE`를 표현했다.

이렇게 하면 호출부가 임의의 문장으로 실패 원인을 표현하는 일을 줄일 수 있다. 대신 enum 이름을 그대로 직렬화하므로 그 이름은 외부 계약이 된다. 이름을 바꾸는 작업도 클라이언트 호환성을 고려해야 한다.

상세 원인을 표현할 수 있다는 것과 모두 공개해야 한다는 것은 별개의 판단이다. 이 사례에서는 로그인 실패에 `reason`을 추가하지 않았다. 알 수 없는 이메일, 틀린 비밀번호, 비활성 계정을 `AUTHENTICATION_FAILED`로 처리하는 기존 구분 방식을 유지했다.

반면 로그인한 사용자의 비밀번호 변경에서는 재사용과 정책 위반을 구분해 수정에 필요한 정보를 제공했다. **상세 원인의 범위는 클라이언트가 해야 할 행동과 공개해도 되는 정보를 함께 고려해 정한다.**

## 4. 필드 오류에는 문장 대신 위치·원인·매개변수를 담는다

입력 오류에서 문장만 제거하면 “입력값을 확인해 주세요” 이상의 안내를 만들기 어렵다. 이번 변경에서는 문장에 포함돼 있던 제한값과 업무 식별자를 별도 필드로 전달했다.

```json
{
  "field": "name",
  "code": "SIZE_OUT_OF_RANGE",
  "limits": { "min": 0, "max": 20 }
}
```

이 오류는 “이름 입력은 최대 20자까지 가능합니다”와 같은 문구로 바꿀 수 있다. 서버는 `name`이라는 입력 위치와 제한 조건을 알려 주고, 화면은 “이름”이라는 라벨과 표현을 선택한다.

서버는 검증 애노테이션의 메시지를 파싱하는 대신 검증 메타데이터를 읽었다. 예를 들어 `NotBlank`는 `REQUIRED`, `Size`는 `SIZE_OUT_OF_RANGE`, `Min`은 `BELOW_MINIMUM`으로 변환했다. 숫자 제한은 `min`, `max`, `value`, `integer`, `fraction` 중 필요한 항목만 추출했다.

금융계약처럼 여러 상환 회차를 가진 입력에는 업무 식별자도 필요했다.

```json
{
  "field": "rows",
  "code": "REPAYMENT_SEQUENCE_DUPLICATED",
  "sequences": [2]
}
```

`sequences`는 상환 회차를 뜻한다. 위 정보로 “2회차가 중복되었습니다”라는 안내를 만들 수 있다. “어느 회차인지”를 영문 오류 문장에서 추출할 이유가 없어진다.

여기서 회차와 배열 인덱스는 구분해야 한다. `rows[2]`는 배열의 세 번째 원소를 가리키지만 `sequences: [2]`는 업무상 2회차를 가리킨다. 화면 상태와 API 필드 경로가 다를 수도 있으므로 이를 연결하는 변환 책임은 화면 측에 필요하다. 실제 초안 화면은 `rows`와 `entries`, 서버 필드명과 화면 라벨을 연결하는 코드를 유지했다.

거부된 원래 입력값이나 검증 라이브러리의 메시지는 응답에 포함하지 않았다. 필요한 오류 설명을 만들 수 있는 메타데이터와 원본 입력의 재노출을 구분한 것이다.

## 5. TypeScript 타입 선언만으로 외부 JSON을 신뢰하지 않는다

기존 클라이언트는 JSON을 읽은 뒤 `as ApiErrorResponse`로 취급했다. 이 타입 단언은 실제 응답이 그 구조인지 확인하지 않는다.

변경 후에는 JSON을 `unknown`으로 받아 런타임에 확인하고, 사용할 필드만 골라 새 객체를 만들었다.

- 최상위 값이 객체인지 확인한다.
- 코드, 상태, 시각, 경로, 요청 식별자와 필드 오류 목록의 기본 타입을 확인한다.
- 필드 오류의 필드명과 코드 타입을 확인한다.
- `sequences`의 값들이 정수인지, `limits`의 값들이 유한한 숫자인지 확인한다.
- 형식이 맞지 않거나 JSON이 아니면 오류 본문을 사용할 수 없는 것으로 처리한다.

이는 전체 의미를 검증하는 스키마 검증기를 완성했다는 뜻은 아니다. 당시 구현은 기본 구조와 일부 메타데이터 타입을 확인한다. 예를 들어 날짜 문자열의 유효성이나 본문의 상태와 실제 HTTP 상태의 일치까지 확인하지는 않는다.

이 사례의 교훈은 **정적 타입과 네트워크 입력의 검증을 구별하고, 실제로 필요한 신뢰 경계를 코드로 만든다**는 것이다.

## 6. 알 수 없는 값의 처리도 오류 계약에 포함한다

새 서버가 새 오류 원인을 추가해도 기존 프론트엔드는 동작해야 한다. 프론트엔드 안내는 다음 순서로 결정했다.

```text
알고 있는 code + 알고 있는 reason → 상세 안내
알고 있는 code + 없거나 모르는 reason → 코드의 기본 안내
모르는 code 또는 잘못된 응답 → 실제 HTTP 상태를 포함한 일반 안내
```

예를 들어 `USER_ACCOUNT_CONFLICT`에서 모르는 `reason`이 오면 계정 충돌의 기본 안내를 보여 준다. 코드까지 모르거나 응답이 HTML·일반 텍스트라면 “요청에 실패했습니다. (HTTP 500)” 같은 안내를 사용한다. 일반 안내의 상태값은 실제 응답의 `response.status`에서 가져온다.

문구 사전의 조회에도 `Object.hasOwn`을 사용했다. 테스트에는 오류 코드가 `toString`인 경우가 포함됐다. 일반 객체의 상속된 프로퍼티를 오류 문구로 잘못 취급하지 않도록, 사전에 직접 정의한 키인지 확인한 것이다.

기본 안내가 있다는 것은 실패를 성공으로 바꾸거나 자동 재시도한다는 뜻이 아니다. 요청은 여전히 `ApiError`로 실패한다. 클라이언트가 이해하지 못하는 응답 때문에 오류 표시까지 깨지지 않도록 하는 장치다.

## 7. 배포 호환성은 버전 조합별로 확인한다

응답에서 `message`를 제거하는 것은 클라이언트가 소비하던 필드의 삭제다. 백엔드와 프론트엔드를 한 PR에서 수정했더라도 실행 중에는 서로 다른 버전이 만날 수 있다.

이번 변경은 프론트엔드를 먼저 배포하도록 정했다. 새 프론트엔드는 이전 응답의 `message`를 무시하고, 코드가 없는 이전 필드 오류는 `INVALID_VALUE`로 정규화한다.

| 프론트엔드 | 백엔드 | 예상 동작 |
| --- | --- | --- |
| 이전 버전 | 이전 버전 | 기존 서버 문구 사용 |
| 새 버전 | 이전 버전 | 서버 문구를 무시하고 코드 기반 안내, 이전 필드 오류는 일반 입력 오류로 변환 |
| 새 버전 | 새 버전 | 코드·상세 원인·필드 메타데이터로 안내 생성 |
| 이전 버전 | 새 버전 | 공통 `ApiError`는 `message`가 없어 HTTP 상태 기반 안내 사용 |

마지막 조합은 이전 클라이언트의 `body?.message ?? 기본문구` 코드와 PR의 호환성 설명에 근거한다. 요청 실패 처리를 유지한다는 의미이며, 이전 화면의 세부 필드 안내가 모두 동일하게 보존된다는 뜻은 아니다.

따라서 순서가 바뀌어도 기본 처리가 가능하다는 이유로 배포 순서를 생략해서는 안 된다. 새 소비자가 두 형식을 먼저 받아들이도록 만든 뒤 생산자의 필드를 제거하는 순서가 세부 안내의 손실을 줄인다.

이 글에서 확인한 것은 당시 호환성 설계와 코드다. 실제 운영 배포가 이 순서로 진행됐는지는 별도로 확인하지 않았다.

## 8. 테스트는 제공할 정보와 제공하지 않을 정보를 함께 확인한다

오류 계약 테스트는 기대하는 코드가 있는지뿐 아니라 제거하기로 한 문구가 없는지도 확인했다.

| 검증 경계 | 당시 추가·수정한 확인 사항 |
| --- | --- |
| 인증 웹 예외 매핑 | 비밀번호 오류 enum별 `reason`, 최상위 `message` 부재, 로그인 실패의 `reason` 부재 |
| 공통 입력 검증 | 필드 코드, 최대 길이·최솟값의 숫자 보존, 회차 정보, 필드 `message` 부재 |
| 실제 인증 흐름 | 비밀번호 재사용과 정책 위반이 올바른 원인으로 응답되는지 확인 |
| 프론트엔드 API 클라이언트 | 서버 문구 무시, 이전 필드 오류 정규화, 모르는 코드·원인과 잘못된 본문 처리 |
| 화면 소비부 | 금융계약 초안과 정비 입력 등에서 새 정보로 안내 생성 |

인증 컨트롤러 테스트는 필터를 끄고 업무 포트를 대체해 예외와 HTTP 응답의 매핑을 검증했다. 실제 세션 테스트에서는 사용자 흐름을 통해 오류 원인을 확인했다. 두 테스트는 검증하는 경계가 다르다.

공통 DTO와 API 클라이언트만 수정해서는 계약 전환이 끝나지 않는다. 필드의 `message`를 직접 표시하던 정비 화면과 영문 문장을 파싱하던 계약 초안 화면까지 수정해야 한다. 변경 범위는 선언부보다 **실제 소비 지점**을 따라 추적해야 한다.

## 9. 적용하면서 남는 설계 과제

문구 소유권을 분리하면 화면별 표현과 다국어 처리를 바꿀 기반이 생긴다. 이 PR에서 실제 여러 언어를 지원한 것은 아니다. 코드·원인 사전과 화면 라벨을 프론트엔드에서 관리하게 됐다는 것이 확인된 변화다.

운영 진단에는 기존 `requestId`를 유지했다. 사용자 문구를 제거해도 응답과 로그를 연결할 수 있다. 다만 오류 응답을 구조화했다고 서버 진단 정보의 수집과 보존 문제까지 해결되는 것은 아니다. 당시 ADR은 원본 입력과 예외 메시지 등의 기본 로그 노출을 제한하고, 추가 진단 체계를 별도 과제로 남겼다.

다른 서비스에 적용할 때는 다음 질문을 먼저 점검할 수 있다.

- 화면이나 클라이언트가 오류 문장을 파싱하는 곳이 있는가?
- 코드만으로 구분할 수 있는가, 상세 원인이 필요한가?
- 상세 원인을 공개해도 되는가?
- 문장을 제거한 뒤에도 입력 위치, 제한값, 업무 식별자가 남는가?
- 서버의 검증 규칙과 화면의 표현 책임이 구분돼 있는가?
- 모르는 코드와 잘못된 JSON에도 예측 가능한 기본 안내가 있는가?
- 이전 응답을 새 클라이언트가 받아들일 수 있는가?
- 제거된 필드가 없다는 것을 테스트로 확인하는가?
- 코드 정의부터 실제 화면 소비부까지 변경을 추적했는가?
