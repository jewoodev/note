# 소프트웨어 개발에서 영수증(receipt)의 의미

소프트웨어에서 **영수증(receipt)**은 어떤 요청을 수신하거나 처리한 사실과 그 결과를 나타내는 반환값·기록을 가리킨다. 종이 영수증처럼 특정 작업과 관련된 정보를 남긴다는 비유다.

다만 `Receipt`라는 이름에 공통으로 적용되는 성공 보장은 없다. 요청 접수만 나타낼 수도 있고, 처리 결과나 후속 작업에 사용할 식별자를 담을 수도 있다. 무엇을 의미하는지는 해당 API의 계약, 즉 반환 조건과 사용 규칙을 확인해야 한다.

## 접수와 완료를 구분해야 하는 이유

파일을 업로드하고 그 내용을 메시지로 보내는 서비스를 생각해 보자. 이 서비스는 다음 단계를 거칠 수 있다.

```text
업로드 요청 접수 → 파일 저장 → 저장 내용 검증 → 메시지 전송 → 수신자 열람
```

각 단계에서 확인 기록을 반환할 수 있지만, 그 기록이 보장하는 범위는 다르다.

| 기록의 의미 | 확인할 수 있는 사실 | 그것만으로 확인할 수 없는 사실 |
| --- | --- | --- |
| 요청 접수 확인 | 서버가 요청을 받음 | 파일 저장 완료 |
| 저장 완료 확인 | 정의된 저장 절차가 끝남 | 수신자에게 메시지 전달 |
| 전달 확인 | 해당 시스템이 정의한 전달 조건 충족 | 수신자 열람 |
| 읽음 확인 | 해당 시스템이 정의한 열람 조건 충족 | 수신자가 내용을 이해하거나 동의함 |

이 표는 개념을 설명하기 위한 예시다. 실제 서비스의 확인 조건은 각각 다르다. 이름에 receipt가 들어 있다는 이유만으로 전체 과정의 완료를 추론하면 안 된다.

## 실제 API에서 사용하는 예

### Amazon SQS의 ReceiptHandle

Amazon SQS는 메시지를 보관하고 소비자 프로그램이 가져가도록 하는 메시지 큐다. 메시지를 수신하면 `ReceiptHandle`이라는 값을 받으며, 이후 메시지를 삭제할 때 이 값을 사용한다.

이 값은 메시지 자체의 ID와 다르다. 같은 메시지를 다시 수신해도 새로운 receipt handle이 발급된다. 따라서 이를 업무 처리 성공 증명서로 해석하기보다는 **해당 수신에 연결된 후속 작업용 핸들**로 이해하는 것이 정확하다. [AWS 공식 문서](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-queue-message-identifiers.html)

### Ethereum의 transaction receipt

Ethereum의 거래 영수증에는 거래 실행의 성공·실패를 나타내는 상태가 포함된다. 영수증에 실패 상태가 기록될 수도 있으므로, **영수증이 존재한다는 사실과 거래가 성공했다는 사실은 다르다.** [EIP-658](https://eips.ethereum.org/EIPS/eip-658)

두 사례는 receipt라는 단어가 반드시 “모든 작업이 성공했다”는 뜻으로 사용되지 않는다는 점을 보여 준다.

## 애플리케이션에서 정의하는 저장 영수증

다음은 특정 제품의 표준 API가 아닌, 설명을 위한 가상의 저장 계약이다.

보고서 저장 기능이 두 파일을 만든다고 가정하자.

- **본문 파일**: 사람이 읽을 보고서 텍스트.
- **메타데이터 파일**: 보고서 ID, 생성 시각, 본문 저장 위치, 본문 해시 등 본문을 설명하는 정보.

저장 기능은 두 파일을 업로드한 뒤 다시 읽어 검증한다. 본문은 저장 전후의 SHA-256을 비교하고, 메타데이터는 저장하려던 내용과 다시 읽은 내용을 비교한다. SHA-256은 데이터로부터 계산하는 해시값으로, 여기서는 내용이 달라졌는지 확인하는 데 사용한다.

검증을 통과했을 때 아래와 같은 Kotlin 객체를 반환할 수 있다.

```kotlin
data class StoredDocument(
    val bodyKey: String,
    val metadataKey: String,
    val bodySha256: String,
)
```

`bodyKey`와 `metadataKey`는 저장소 안에서 각 파일을 찾는 식별자이고, `bodySha256`은 본문의 해시값이다. 파일 내용 전체를 담는 객체는 아니다.

이 반환값을 설명할 때 “저장 영수증”이라고 부를 수 있다. 이 계약에서 의미하는 것은 다음과 같다.

> 본문과 메타데이터를 저장하고 재조회 검증까지 마쳤으며, 저장 위치와 본문 해시를 반환한다.

여기서 영수증을 만드는 주체는 애플리케이션이다. 외부 저장 서비스가 공식 증명서를 발급한다는 뜻은 아니다. 또한 파일이 영구 보존된다거나, 다른 데이터베이스에 완료 상태가 기록됐다거나, 사용자에게 전송됐다는 것까지 보장하지 않는다.

**객체의 필드나 이름 자체가 검증 완료를 증명하는 것도 아니다.** 위 코드는 누구나 값을 넣어 객체를 만들 수 있다. 검증된 경로에서만 이 값을 반환하고 후속 코드가 그 계약을 지키도록 설계해야 의미가 생긴다. 해시값을 담는 것만으로 발급자의 신원이나 위변조 방지까지 보장되지는 않는다.

## 비슷한 이름과 선택 기준

다음 구분은 강제된 업계 표준이 아니라, 타입이나 문서의 이름을 정할 때 사용할 수 있는 기준이다.

| 이름 | 강조하는 의미 |
| --- | --- |
| `Receipt` | 특정 접수·처리에 대한 확인 기록 |
| `Result` | 작업 결과 전반. 설계에 따라 성공과 실패를 모두 포함 |
| `Reference` | 저장된 대상의 위치나 식별자 |
| `StoredDocument` | 저장된 문서를 나타내는 값 |
| `VerifiedStorageResult` | 검증을 마친 저장 결과라는 계약 |

확인 기록이라는 개념이 업무에 익숙하다면 receipt를 사용할 수 있다. 단순히 저장 위치와 해시를 전달하는 반환값이라면 “저장 결과” 또는 “검증된 저장 결과”가 더 직접적인 설명일 수 있다.

어떤 이름을 선택하든 문서에는 **언제 반환되는지, 무엇을 확인했는지, 어디까지 보장하는지**를 적어야 한다. 반환 전에 실패했더라도 서버에 일부 또는 전체 작업이 이미 반영됐을 수 있다는 점도 별도로 설명해야 한다. “영수증을 받지 못했다”는 사실만으로 “아무 작업도 수행되지 않았다”고 단정할 수는 없다.
