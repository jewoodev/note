# Facade 용어와 `reference` 모듈

## Facade란 무엇인가

Facade는 여러 내부 구성요소와 복잡한 사용 절차를 감추고, 외부에 더 단순하고 일관된 진입점을 제공하는 설계 개념이다. 건물 내부 구조를 가리고 외부에서 보이는 정면을 뜻하는 프랑스어 *façade*에서 유래했다.

호출자는 Facade가 제공하는 인터페이스만 알면 된다. 내부에서 어떤 객체나 테이블을 사용하고, 어떤 순서로 처리하고, 어떤 필터와 정렬 규칙을 적용하는지는 알 필요가 없다.

```text
호출자
  ↓
단순한 Facade 인터페이스
  ↓
여러 내부 구성요소와 처리 규칙
```

Facade는 내부 기능을 새로 정의하는 계층이라기보다, 이미 존재하는 기능을 호출자가 사용하기 좋은 형태로 정리한 경계다.

## `reference` 모듈이 Facade인 이유

ERP 화면에서는 차량 유형, 렌터카 회사, 정비업체처럼 여러 업무에서 반복해서 사용하는 선택 목록이 필요하다. 이 데이터는 각각 차량과 회사 영역이 소유하지만, 화면이 필요한 목록을 얻기 위해 각 영역의 내부 구조를 모두 알 필요는 없다.

`reference` 모듈은 다음과 같은 단순한 조회 진입점을 제공한다.

```kotlin
referenceQueryProvider.getVehicleTypes()
referenceQueryProvider.getRentalCompanies()
referenceQueryProvider.getMaintenanceProviders()
```

외부 호출자는 다음 내부 구현을 알지 못한다.

- 차량 유형과 차량 유형 그룹을 어떻게 조인하는지
- 렌터카 회사와 정비업체를 어떤 회사 유형으로 구분하는지
- 결과를 어떤 순서로 정렬하는지
- 실제 데이터가 어느 테이블에 저장되는지
- 영속성 조회를 어떤 기술로 구현하는지

따라서 `reference` 모듈은 여러 기준정보 조회를 선택지에 필요한 최소 인터페이스로 감싸는 Facade 역할을 한다.

## 얇은 Facade라는 의미

여기서 "얇다"는 표현은 새로운 업무 규칙이나 데이터 소유권을 갖지 않는다는 뜻이다.

`reference` 모듈이 담당하는 것은 다음과 같다.

- 여러 업무 화면에서 공통으로 사용하는 선택 목록 조회
- `id`, `name`, `code` 등 선택지에 필요한 최소 필드 반환
- 회사 유형 필터, 조인, 정렬과 같은 조회 규칙 캡슐화

다음 책임은 담당하지 않는다.

- 회사나 차량 유형의 생성·수정·삭제
- 회사와 차량 카탈로그의 업무 규칙
- 차량 상세, 정비 이력, 계약 상태와 같은 업무 조회
- 기준정보의 원본 데이터 소유

회사 데이터의 소유자는 `company`, 차량 카탈로그의 소유자는 `vehicle`이다. `reference`는 이 데이터를 다른 화면이 사용하기 편한 읽기 모델로 제공할 뿐이다.

## Read-only Facade인 이유

`reference` 모듈은 데이터를 변경하지 않고 조회만 제공한다. 선택 목록을 사용하는 화면이 기준정보의 변경 권한까지 가져서는 안 되기 때문이다.

```text
차량·정비·계약 화면
        ↓
reference 조회 API
        ↓
선택지 전용 읽기 모델
        ↓
companies / vehicle_types / vehicle_type_groups
```

읽기와 변경 책임을 분리하면 다음 효과가 있다.

- 여러 화면이 동일한 선택지 계약을 재사용할 수 있다.
- 업무 모듈이 다른 모듈의 repository나 엔티티에 직접 의존하지 않는다.
- 원본 테이블이나 엔티티가 변경돼도 외부 응답을 안정적으로 유지할 수 있다.
- 선택지에 불필요한 내부 필드와 업무 규칙이 외부로 노출되지 않는다.

## MyBatis와의 관계

Facade라는 이유만으로 MyBatis를 선택해야 하는 것은 아니다. Facade는 외부 인터페이스와 책임에 관한 설계 개념이고, MyBatis는 영속성 구현 기술이다.

다만 `reference` 조회는 다음 특성이 있어 MyBatis와 잘 맞는다.

- 읽기 전용이다.
- 엔티티의 생명주기와 변경 감지가 필요하지 않다.
- 여러 테이블에서 필요한 필드만 projection한다.
- 조인, 필터, 정렬 조건이 명확하다.
- 결과가 `id`, `name`, `code` 같은 단순한 형태다.

따라서 JPA 엔티티와 연관관계를 불러오는 것보다 SQL을 명시적으로 작성하고 결과 행을 읽기 모델로 변환하는 방식이 간결하다. JPA projection으로도 구현할 수 있으므로 MyBatis가 유일한 선택은 아니지만, 현재 조회의 성격과 프로젝트의 읽기·쓰기 분리 원칙에는 적합하다.

## 모듈 경계 유지 원칙

`reference`가 모든 단순 조회를 모으는 범용 모듈이 되지 않도록 다음 원칙을 지킨다.

- 여러 업무에서 공통으로 사용하는 선택지와 코드 목록만 포함한다.
- 상세정보와 업무 상태를 판단하는 조회는 원래 업무 모듈에 둔다.
- 생성과 변경 기능은 데이터를 소유한 모듈이 담당한다.
- 호출자에게 필요한 최소 필드만 응답한다.
- 특정 화면 하나에서만 사용하는 조회는 해당 화면의 업무 모듈에 둔다.

## 한 문장 정의

`reference`는 여러 업무 화면이 공통 기준정보를 내부 구조에 의존하지 않고 조회할 수 있도록 단순한 인터페이스를 제공하는 얇은 read-only Facade이며, 그 조회 특성에 맞춰 MyBatis를 영속성 구현으로 사용한다.
