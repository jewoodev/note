# AWS AMI란 무엇인가?

AWS의 **AMI(Amazon Machine Image)** 는 EC2 인스턴스를 생성할 때 사용하는 **서버의 실행 환경을 정의한 이미지**다.

쉽게 말하면, EC2가 가상 서버라면 AMI는 그 서버를 어떤 상태로 만들어서 실행할지 결정하는 템플릿이라고 이해하면 된다.

예를 들어 백엔드 서비스를 운영하기 위해 다음과 같은 환경을 구축했다고 가정해 보자.

- 운영체제: Ubuntu 24.04
- 런타임: Java 21
- 웹 서버: Nginx
- 애플리케이션: Spring Boot
- 기타: CloudWatch Agent 및 각종 설정

이렇게 구성한 EC2에서 AMI를 생성하면, 해당 서버의 운영체제와 설치된 프로그램, 설정 파일 등을 기반으로 새로운 EC2 인스턴스를 생성할 수 있다.

![img.png](https://github.com/jewoodev/blog-img/blob/main/aws/ami/img.png?raw=true)
 
여기서 중요한 점은 **AMI 자체가 실행 중인 서버는 아니라는 것**이다. AMI는 EC2 인스턴스를 생성하기 위한 원본 이미지이고, 실제 컴퓨팅 자원을 사용하는 것은 AMI로부터 생성한 EC2 인스턴스다.

## 1. AMI는 내부적으로 어떻게 구성될까?
   
EBS 기반 EC2에서 생성한 AMI는 주로 다음 정보로 구성된다.

| 구성 요소              | 역할                                                          |
|------------------------|---------------------------------------------------------------|
| EBS 스냅샷             | 운영체제, 프로그램, 파일 등이 저장된 EBS 볼륨의 시점별 데이터 |
| 블록 디바이스 매핑     | EC2 실행 시 연결할 EBS 볼륨 구성                              |
| 실행 권한              | 어떤 AWS 계정이 AMI를 사용할 수 있는지                        |
| 아키텍처 등 메타데이터 | x86_64 / arm64, 가상화 방식 등 인스턴스 실행에 필요한 정보    |
   
즉, AMI는 서버의 파일을 압축한 단순한 ZIP 파일이 아니라, EBS 스냅샷과 EC2 실행에 필요한 메타데이터를 묶어서 관리하는 AWS 리소스라고 이해하는 것이 정확하다.

AMI로 EC2를 실행하면 스냅샷을 바탕으로 새 EBS 볼륨이 만들어지고, 해당 볼륨을 연결한 EC2 인스턴스가 시작된다.

또한 AMI는 RAM에 있는 데이터나 CPU의 실행 상태까지 보존하는 것은 아니다. 실행 중인 애플리케이션 프로세스가 그대로 이어서 실행되는 방식도 아니고.

## 2. AMI는 어떤 상황에서 활용할까?
   
AMI의 대표적인 활용 사례는 크게 네 가지다.
   
### ① 서버 환경 복제
   
가장 기본적인 활용이다.

기존 서버에 Java, Nginx, 환경 설정 등을 설치했다면 같은 설정을 새로운 서버에서 반복할 필요 없이 AMI를 이용할 수 있다.

예를 들어 운영 서버와 유사한 테스트 서버를 만들거나, 여러 대의 애플리케이션 서버를 동일한 설정으로 배포할 때 유용하다.

### ② Auto Scaling과 연계

실무에서는 이 활용법이 특히 중요하다.

![img_1.png](https://github.com/jewoodev/blog-img/blob/main/aws/ami/img_1.png?raw=true)

Auto Scaling Group이 새로운 EC2를 생성할 때 Launch Template에 지정된 AMI를 사용한다.

따라서 모든 EC2에 동일한 애플리케이션 환경을 제공할 수 있고, AMI에 애플리케이션을 포함했다면 시작할 때 별도의 배포 과정 없이 서비스를 실행하도록 구성할 수도 있다.

이처럼 미리 구성된 이미지를 배포하는 방식은 **Immutable Infrastructure(불변 인프라)** 설계에도 활용된다.

### ③ 배포 및 롤백

AMI를 애플리케이션 배포 단위로 사용할 수도 있다.

예를 들어 다음과 같이 버전별 이미지를 관리하는 것이다.

| AMI        | 구성                      |
|------------|---------------------------|
| backend-v1 | Java 21 + Spring Boot 1.0 |
| backend-v2 | Java 21 + Spring Boot 1.1 |
| backend-v3 | Java 21 + Spring Boot 1.2 |

`backend-v3`에서 심각한 문제가 발생하면 Launch Template의 AMI를 이전 버전으로 변경하고 인스턴스를 교체해서 롤백할 수 있다.

단, AMI를 변경한다고 실행 중인 인스턴스가 자동으로 이전 상태가 되는 것은 아니다. 또한 애플리케이션과 별도로 관리되는 DB 스키마나 데이터까지 롤백되지는 않는다.

### ④ 장애 복구 및 서버 이전

서버 장애에 대비해 정상 상태의 AMI를 보관해 두고, 필요할 때 새로운 인스턴스를 만드는 데 사용할 수 있다.

다만 AMI는 인스턴스의 모든 AWS 설정을 백업하는 수단은 아니다.

예를 들어 VPC, 보안 그룹, IAM 역할, Elastic IP, 외부 RDS 데이터 등은 AMI에 포함되지 않는다. 이러한 리소스는 별도로 구성하거나 백업해야 한다.

## 3. AMI는 실제로 어떻게 생성할까?
   
AWS 콘솔에서는 다음 순서로 생성할 수 있다.

1. EC2 콘솔에서 Instances(인스턴스) 선택
2. AMI를 생성할 EC2 인스턴스 선택
3. Actions → Image and templates → Create image 선택
4. AMI 이름과 설명 설정
5. 이미지 생성 후 AMIs 메뉴에서 상태 확인

AWS CLI에서는 다음과 같이 실행할 수 있다.
```bash
aws ec2 create-image \
--instance-id i-0123456789abcdef0 \
--name "backend-v1.0.0" \
--description "Spring Boot production image"
```

기본적으로 AWS는 파일 시스템 일관성을 확보하기 위해 인스턴스를 재부팅하는 과정을 수행할 수 있다. 따라서 운영 서버에서 생성할 때는 서비스 중단 가능성을 고려해야 한다. --no-reboot 옵션도 있지만 일관성이 보장되지 않을 수 있다.

이후 생성된 AMI ID를 사용해 새로운 EC2를 실행할 수 있다.

## 4. AMI와 Docker Image는 어떤 차이가 있을까?
   
백엔드 개발자 관점에서는 이 차이를 이해하는 게 중요하다.

| 구분        | AMI                                    | Docker Image                  |
|-------------|----------------------------------------|-------------------------------|
| 목적        | 가상 서버 실행 환경 구성               | 컨테이너 실행 환경 구성       |
| 범위        | OS, 시스템 설정, 설치된 프로그램       | 애플리케이션과 필요한 의존성  |
| 실행 대상   | EC2 인스턴스                           | 컨테이너 런타임               |
| 일반적 크기 | 상대적으로 큼                          | 상대적으로 작음               |
| 주요 활용   | 서버 복제, Auto Scaling, 인스턴스 교체 | 앱 배포, 컨테이너 확장, CI/CD |

두 기술은 경쟁 관계가 아니라 함께 활용할 수도 있다.

예를 들어 AMI에는 Ubuntu와 Docker Engine을 설치해 두고, 실제 Spring Boot 애플리케이션은 Docker Image로 배포하는 방식이 가능하다.

이렇게 하면 인프라 환경과 애플리케이션 배포를 분리할 수 있다는 장점이 있다.

## 5. AMI 사용 시 주의할 점

- **비용**: 직접 만든 EBS 기반 AMI는 연관된 EBS 스냅샷 스토리지 비용이 발생할 수 있다. EC2 인스턴스를 종료하더라도 AMI와 스냅샷 비용이 남을 수 있다.
- **보안**: 서버에 저장된 비밀번호, API 키, 인증서 등이 AMI에 포함될 수 있으므로 이미지를 만들기 전에 민감 정보를 제거하는 게 좋다.
- **리전**: AMI는 리전 단위 리소스이기 때문에 다른 리전에서 사용하려면 복사해야 한다.
- **호환성**: AMI의 CPU 아키텍처와 EC2 인스턴스 타입이 호환되어야 한다.

## 6. 백엔드 서비스에서는 어떻게 활용하는 게 좋을까?
   
Spring Boot 기반 서비스를 EC2에서 운영한다고 가정하면 다음 두 가지 접근법이 있다.

### A. AMI에 애플리케이션까지 포함하는 방식

```text
AMI
├── Ubuntu
├── Java 21
├── Nginx
└── Spring Boot application.jar
```

CI/CD 파이프라인에서 새로운 AMI를 만들어 EC2 인스턴스 자체를 교체하는 방식이다. 인스턴스마다 동일한 애플리케이션 버전을 실행하도록 관리하기에 좋다.

### B. AMI에는 실행 환경만 포함하는 방식

```text
AMI
├── Ubuntu
├── Java 21
├── Nginx
└── CloudWatch Agent

CodeDeploy 또는 별도 배포 시스템
└── Spring Boot application.jar
```

AMI는 비교적 드물게 변경하고, 애플리케이션은 CodeDeploy 등의 배포 시스템으로 자주 업데이트하는 방식이다.

이미 EC2와 CodeBuild, CodeDeploy를 활용하는 구조라면 B 방식부터 시작하는 것이 관리하기 편리할 수 있다. 매번 애플리케이션이 변경될 때마다 AMI를 다시 생성하지 않아도 되기 때문이다.

반대로 서버를 교체하는 방식의 배포와 Auto Scaling을 적극적으로 사용한다면 A 방식도 충분히 고려할 만하다.

핵심적으로 기억할 것은 AMI는 'EC2 서버를 어떤 환경으로 생성할 것인가'를 정의하는 기술이라는 점이다.

Docker Image가 애플리케이션의 실행 환경을 패키징한다면, AMI는 EC2 서버의 실행 환경을 이미지화한다고 이해하면 둘의 역할을 구분하기 쉽다.
