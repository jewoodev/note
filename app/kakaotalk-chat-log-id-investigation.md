# 카카오톡 메시지 수정으로 발생한 중복 응답을 추적하며 `chatLogId`를 확인한 과정

조사일: 2026년 10월 12일. 본문의 시각은 모두 한국시간(KST, UTC+9)이다.

## 1. 무엇을 알아냈는가

카카오톡 Android 앱 **26.7.2(versionCode `29260720`)**는 알림에 담긴 개별 채팅 메시지의 추가 데이터에 **`chatLogId`라는 64비트 정수(`Long`)**를 넣는다. 앱 내부에서는 이 값을 저장·조회하고, 기존 알림의 메시지 목록에서 대상 메시지를 찾는 데 사용한다.

실제 기기에서 메시지를 수정하는 실험도 수행했다. 두 차례 재현에서 **본문이 바뀌어도 `chatLogId`는 유지됐고, 같은 문구를 별개의 새 메시지로 보내면 값이 달라졌다.** 따라서 이 값은 단순히 알림이 게시된 시각이나 본문의 지문이 아니라, 해당 채팅 메시지를 식별하는 값이라는 결론을 얻었다.

이 결론은 필드 이름만 보고 추측한 결과가 아니다. 다음 세 가지 증거를 연결했다.

1. 실제 수정·새 메시지 실험에서 값이 유지되거나 달라지는 양상.
2. 진단 로그의 키 해시와 `chatLogId`라는 문자열의 해시 일치.
3. 운영 기기에 설치된 카카오톡 APK의 알림 코드에서 확인한 값의 저장·조회·비교 동작.

확인 범위는 **조사 당시 앱 버전과 관찰한 메시지들**이다. 모든 카카오톡 버전에서의 영구적인 API 계약이나 전체 서비스에 걸친 ID의 유일성을 증명한 것은 아니다. 이 조사에서는 진단 기능을 구현·배포했으며, `chatLogId`를 이용한 중복 응답 방지 로직은 아직 적용하지 않았다.

## 2. 프로젝트를 모르는 독자를 위한 시스템 설명

이 프로젝트는 렌트카 회사의 업무 질문에 답하는 AI 비서다. 카카오톡에서 비서 이름인 ‘카비’를 부르며 차량 사진 등을 요청하면, 서버가 필요한 정보를 조회하고 답변을 만든다.

카카오톡과 서버 사이에는 **Android Bridge**라는 별도 앱이 있다. Bridge는 카카오톡의 Android 알림을 받아 서버로 전달하고, 서버의 답변을 알림의 ‘답장’ 기능으로 전송한다.

```mermaid
flowchart LR
    A[직원이 카카오톡 메시지 전송] --> B[카카오톡 앱이 Android 알림 게시]
    B --> C[Bridge가 알림 수신]
    C --> D[서버가 질문 처리 및 답변 생성]
    D --> E[Bridge가 알림의 답장 기능 실행]
    E --> F[카카오톡 채팅방에 답변]
```

Android의 `NotificationListenerService`는 알림을 관찰하는 기능이고, `RemoteInput`은 알림에서 바로 답장할 때 사용하는 기능이다. 이 시스템은 이 둘을 연결한다. 카카오톡 서버가 제공하는 공식 수신 메시지 API를 직접 호출하는 구조는 아니다.

문제를 이해하려면 **채팅 메시지와 Android 알림은 서로 다른 객체**라는 점이 중요하다. 채팅 메시지 하나가 수정되면 기존 알림이 갱신될 수 있다. 같은 채팅방의 여러 메시지가 하나의 알림에 모일 수도 있다. 따라서 알림이 새로 전달됐다는 사실만으로 새 채팅 메시지가 생겼다고 판단할 수 없다.

### 조사에서 사용한 용어

| 용어 | 의미와 주의점 |
|---|---|
| 알림 `key` | Android가 알림을 식별하는 값. 이번 관찰에서는 같은 방의 다른 메시지에서도 재사용됐다. |
| `shortcutId` | Bridge가 채팅방 식별에 사용하는 값. 개별 메시지 식별값과는 다르다. |
| `postTime` | Android 알림의 게시 시각. 원래 채팅 메시지의 작성 시각과 같다고 가정할 수 없다. |
| 알림 `when` | 앱이 알림에 설정한 시각. `postTime`과 별도로 관찰했다. |
| `MessagingStyle.Message` | 대화형 알림 안에 담긴 개별 메시지. 본문·시각·발신자·추가 데이터를 가질 수 있다. |
| `extras` / `Bundle` | 추가 데이터를 이름과 값의 쌍으로 담는 공간. 알림 전체와 개별 메시지 각각에 존재할 수 있다. |
| Bridge의 `messageId` | Bridge가 직접 계산한 요청 식별값. 아래에서 확인한 카카오톡의 `chatLogId`와는 다른 값이다. |
| 해시 | 입력값을 고정 길이의 지문으로 바꾸는 함수의 결과. 원문을 로그에 쓰지 않고 값의 동일 여부를 비교하기 위해 사용했다. |

## 3. 출발점: 한 요청에 답변이 세 번 도착했다

18:44경 차량 사진을 요청한 메시지에 비서가 같은 차량 안내와 링크를 세 번 보냈다는 제보가 있었다. 요청 메시지에는 수정됐다는 표시가 있었다.

처음에는 ‘메시지 수정 때문에 새 요청으로 인식한 것 아닐까’라는 가설을 세웠다. 하지만 사용자가 조사한 내용에 따르면 수정은 일반적인 새 메시지처럼 재알림을 일으키지 않았다. 수정 표시만 보고 원인을 확정할 수 없었다.

먼저 서버의 답변 생성 로그와 Bridge의 수신·전송 로그를 대조했다.

| 구분 | Bridge의 알림 파싱 시각 | Bridge 요청 ID 앞부분 | 답장 기능 실행 시각 |
|---|---|---|---|
| 첫 번째 | 18:44:22.645 | `109a7132…` | 18:44:25.877 |
| 두 번째 | 18:44:25.819 | `476c642d…` | 18:44:28.413 |
| 세 번째 | 18:44:25.826 | `414e787e…` | 18:44:31.052 |

서버에도 별도의 차량 사진 조회·답변 생성이 세 번 남아 있었다. 이미 생성한 답변 하나를 단순히 재전송한 것과 달리, **서로 다른 요청으로 세 번 처리한 것**이었다.

두 번째·세 번째 알림은 첫 답장을 보내기 전에 들어왔다. 따라서 첫 답장이 새 알림을 만들어 다시 답하게 된 순환은 이 사건을 설명하지 못했다.

여기서 ‘답장 기능 실행’은 Bridge의 `remote_input_dispatched` 로그를 뜻한다. 이는 Android의 전송 호출이 성공했다는 증거이며, 상대방이 실제 메시지를 받았다는 증거와는 구분한다. 최초 세 번 수신했다는 사실은 사용자의 제보로 확인한 것이다.

### 사용자에게 다시 울리지 않아도 알림 갱신은 전달될 수 있다

Android 시스템 로그에서는 같은 알림 키로 최초 게시 후 두 차례 갱신이 확인됐다. 최초 알림의 flags는 `0x11`, 두 갱신의 flags는 `0x19`였다. 두 값의 차이인 `0x08`은 `FLAG_ONLY_ALERT_ONCE`다.

이 플래그는 이미 표시 중인 알림의 소리·진동 등 반복 알림 동작을 제한한다. 실제로 해당 구간의 `notification_alert` 이벤트는 최초 한 번이었지만 Bridge는 알림을 세 번 받았다. **사용자에게 재알림이 울리지 않는 것과 프로그램에 갱신 알림이 전달되지 않는 것은 다른 문제**였다.

이때까지 확정한 것은 ‘추가 알림이 별도 요청으로 처리됐다’는 경로다. 18:44 요청의 수정 전 원문이나 수정 동작 자체를 직접 확보한 것은 아니므로, 그 갱신의 계기가 수정이었다는 판단은 이후 재현 결과와 연결한 추론으로 남긴다.

## 4. 기존 식별 방식이 갱신을 새 요청으로 만들었다

당시 Bridge의 파서는 다음 값을 조합해 요청 ID를 만들었다.

```text
SHA-256(앱 패키지 | 알림 key | postTime | 본문)
```

다음은 실제 계산에 대응하는 코드다.

```kotlin
IdentifierHasher.sha256(
    "$KAKAO_PACKAGE_NAME|${statusBarNotification.key}|${statusBarNotification.postTime}|$text",
)
```

같은 채팅 메시지라도 알림의 게시 시각이나 본문이 달라지면 다른 요청 ID가 나온다. 서버의 중복 방지는 전달받은 요청 ID를 기준으로 하므로, 갱신 전후 ID가 달라지면 별개의 질문으로 처리한다.

본문이 같은지만 비교하는 방법도 충분하지 않다. 수정하면 본문이 달라지고, 반대로 직원이 같은 문구를 새 요청으로 다시 보낼 수도 있기 때문이다. 필요한 것은 **메시지 자체의 식별값과 그 메시지 내용의 변화를 따로 다루는 것**이었다.

## 5. 반례가 가설을 좁혔다: 답변 후 수정과 답변 전 수정

사용자는 18:50에 보낸 메시지를 여러 번 수정했지만 추가 응답이 없었다고 알려왔다. 확인 결과 수정은 비서의 답변을 받은 뒤에 수행했다.

로그에는 18:50:35.848에 처리 가능한 알림 한 건이 들어왔고, 18:50:38.287에 답장 기능이 한 번 실행됐다. 다음 새 요청 전까지 해당 방의 추가 개별 메시지 알림은 확인되지 않았다. 이 경우는 Bridge가 수정본을 잘 걸러낸 것이 아니라, 처리할 개별 알림이 추가로 들어오지 않은 경우였다.

이에 ‘답변 전에 원래 알림이 남아 있을 때 수정하는 경우’와 ‘답변 후 수정하는 경우’를 나누어 시험했다. 사용자가 답변 전에 수정하자 중복 응답이 재현됐다.

20:09 재현 로그에서는 20:09:42.094의 최초 게시 뒤 20:09:44.876과 20:09:44.880에 두 갱신이 발생했다. 첫 답장 기능 실행은 20:09:45.967이었다. 추가 갱신 두 건은 모두 첫 답변 전이었다.

이 결과는 수정 시점이 중요한 조건임을 보여준다. 다만 ‘답변 후에는 카카오톡이 어떤 내부 경로로 알림을 정리하는가’까지 이 조사에서 완전히 규명한 것은 아니다. 관찰하지 않은 내부 동작을 사실로 단정하지 않았다.

## 6. 진단을 추가해 알림 안의 개별 메시지를 관찰했다

기존 로그는 요청 ID와 처리 이벤트를 중심으로 남겼다. 원본 메시지를 식별할 정보를 찾으려면 알림 내부의 메타데이터를 추가로 관찰해야 했다.

Bridge **0.6.1(versionCode `10`)**에 필요할 때만 켜는 진단을 추가하고 운영 기기에 배포했다. 이 단계에서는 기존 응답·중복 판별 정책을 바꾸지 않았다.

진단은 세 층의 정보를 기록한다.

| 관찰 대상 | 기록한 정보 |
|---|---|
| 알림 전체 | 게시 시각, `when`, flags, 알림 ID, key·tag·방·정렬 키 등의 해시 |
| 개별 메시지 | 메시지 시각, 본문·발신자·발신자 key의 해시 |
| 추가 데이터 | 키 이름의 해시, 값의 타입, 문자열·숫자·불리언 값의 해시 |

본문과 발신자 이름은 원문으로 기록하지 않았다. 숫자 값은 십진 문자열로 바꾼 뒤 SHA-256을 계산했다. 따라서 이후 표의 ID 후보 값은 실제 ID 숫자가 아니라 **그 숫자의 해시**다. 해시 기록이 완전한 익명화를 보장하는 것은 아니다.

같은 알림 콜백에서 나온 여러 JSON 행은 `capture` 번호와 Bridge 요청 ID로 연결했다. `capture`는 프로세스 내 관측 순번일 뿐 카카오톡 메시지 ID가 아니다.

현재·과거 메시지는 각각 마지막 8개, 각 추가 데이터 묶음은 최대 16개 키로 제한했다. 실제 알림 전체의 추가 데이터는 27개여서 일부가 생략됐지만, 이번에 비교한 **개별 메시지의 추가 데이터는 3개로 모두 기록**됐다. 생략된 알림 전체 데이터까지 조사했다고 주장할 수는 없다.

SSM 원격 조회 결과도 출력 길이 제한으로 처음 조회가 잘렸다. 이후 알림 요약·개별 메시지·개별 메시지 추가 데이터를 나눠 다시 조회하고, 잘리지 않은 결과로 비교했다.

## 7. 20:26 실험: 수정해도 유지되는 숫자 값을 발견했다

사용자가 20:26에 시작한 테스트 중 중복이 발생한 요청은 20:26:58에 접수됐고, 갱신은 20:27:01에 발생했다.

아래 표의 본문 A와 B는 서로 다른 실제 본문 해시를 읽기 쉽게 표시한 것이다. A는 `68bf9532…`, B는 `90fe7369…`이며 본문 원문을 뜻하는 예시 문구가 아니다.

| 관찰 항목 | 최초 알림 | 갱신 ① | 갱신 ② |
|---|---|---|---|
| `capture` | 8 | 9 | 10 |
| 알림 `postTime` | 20:26:58.068 | 20:27:01.028 | 20:27:01.029 |
| 개별 메시지 시각 | **20:26:58.050** | **동일** | **동일** |
| 본문 | A | A | **B** |
| 발신자 key 해시 | 동일 | 동일 | 동일 |
| 추가 데이터의 특정 숫자 값 해시 | **`bf7e15f0abb6…`** | **동일** | **동일** |
| Bridge 요청 ID 앞부분 | `39a99cf4…` | `559f3fe7…` | `979bd889…` |

수정 과정에서 기존 본문을 유지한 알림 갱신이 먼저 들어오고, 수정된 본문을 담은 갱신이 뒤따랐다. 게시 시각은 각각 달라졌지만, 개별 메시지 시각과 특정 숫자 값은 유지됐다.

이 숫자가 ID 후보가 된 이유는 단순히 세 번 같은 값이 나왔기 때문만은 아니다. 앞선 별도 요청들과 비교하면 값이 달랐다.

| 별도 요청의 게시 시각 | 개별 메시지 시각 | 같은 추가 데이터 필드의 값 해시 |
|---|---|---|
| 20:26:43.415 | 20:26:43.399 | `085bf89aeeb3…` |
| 20:26:50.186 | 20:26:50.169 | `709f68a760da…` |
| 20:26:58.068 및 그 수정 알림 | 20:26:58.050 | `bf7e15f0abb6…` |

따라서 ‘새 메시지에는 다른 값, 같은 메시지의 수정에는 같은 값이 붙는 것 아닐까’라는 가설을 세웠다. 이 시점에는 이름도 의미도 아직 확정하지 않았다.

## 8. 20:36 실험: 수정과 같은 문구의 새 전송을 구분했다

같은 조건을 다시 시험하고, 답변이 끝난 뒤 별개의 새 메시지도 보냈다.

| 알림 게시 시각 | 상태 | 본문 | 식별 후보 값 해시 |
|---|---|---|---|
| 20:36:04.634 | 최초 요청 | A | **`c92c4c625c46…`** |
| 20:36:07.229 | 기존 본문으로 갱신 | A | **동일** |
| 20:36:07.231 | 수정 본문으로 갱신 | B | **동일** |
| 20:36:14.132 | 별개의 새 메시지 | A | **`e3dd6d6ed28c…`** |

개별 메시지 시각은 수정 전후에 **20:36:04.617로 유지**됐고, 별개의 새 메시지에서는 **20:36:14.115로 변경**됐다.

실험 안내에서는 최종 수정 문구를 다시 보내도록 제안했지만, 실제 로그의 마지막 메시지는 **수정 전 문구 A와 같았다.** 기록은 실제 결과를 기준으로 해석했다. 그래도 같은 본문 A의 첫 요청과 마지막 새 요청이 서로 다른 식별 후보 값을 갖는다는 점은 검증됐다.

20:36:04의 요청에 대해 Bridge의 답장 기능은 20:36:07.727, 20:36:10.294, 20:36:13.064에 각각 실행됐다. 기존 코드가 원본과 두 갱신을 계속 별개 요청으로 처리했음을 보여준다.

이 단계에서 실험적으로 뒷받침된 사실은 두 가지다.

- 메시지 내용이 바뀌어도 유지되는 값이 있다.
- 내용이 같더라도 별개 메시지를 보내면 그 값이 달라진다.

## 9. 키 해시를 실제 이름 `chatLogId`와 연결했다

후보 숫자가 들어 있던 추가 데이터의 키 해시는 다음과 같았다.

```text
45edfa7ec3c8ee328acd6d44e8465ae7bd38f9dac4bff48a5e3475e5af1274d3
```

키 이름도 해시로 기록했으므로, 로그만 읽어서는 이름을 알 수 없었다. 운영 기기에 설치된 카카오톡 APK에서 메시지·알림 관련 문자열 후보를 조사하고, 후보 이름의 SHA-256을 계산해 대조했다.

```text
SHA-256(UTF-8("chatLogId"))
= 45edfa7ec3c8ee328acd6d44e8465ae7bd38f9dac4bff48a5e3475e5af1274d3
```

관찰된 키 해시와 정확히 일치했다. 이는 해시를 복호화한 것이 아니라 **후보 문자열을 같은 방식으로 해시해 검증한 것**이다.

이 일치로 숫자 필드의 이름이 `chatLogId`임을 확인했다. 그러나 이름에 ‘ID’가 들어간다는 사실만으로 의미까지 확정하지 않고, 실제 사용 코드를 추가로 추적했다.

## 10. 카카오톡 26.7.2의 코드에서 역할을 확인했다

### 분석 대상과 방법

`pm path`와 패키지 정보를 이용해 운영 설치본의 APK 위치와 버전을 확인했다. APK는 Android 앱의 배포 파일이며, 그 안의 DEX 파일에는 실행 코드가 들어 있다.

해당 APK에서 알림 코드가 들어 있는 `classes10.dex`, `classes11.dex`를 읽고 Android SDK의 `dexdump`로 명령어를 확인했다. 이것은 카카오톡 개발 저장소의 원본 소스를 열어 본 것이 아니라, **설치된 앱의 바이트코드를 역어셈블해 확인한 것**이다. 메서드 이름 일부가 `a0`, `D`처럼 짧은 것은 앱의 난독화와 관련된 이름이며 버전 간 안정적인 이름으로 취급하지 않는다.

이 과정에서 앱을 패치하거나 계정 데이터베이스를 읽지는 않았다. 운영 앱의 재시작·재설치도 하지 않았다.

핵심 증거가 있는 `classes11.dex`의 SHA-256은 다음과 같다. 이는 **DEX 파일의 해시**이며 APK 전체의 해시는 아니다.

```text
b56763ebd3c86c3be8a7134a8d8f7881af1f07aaaab06d5cfca56ff7e20bb6c2
```

### 10.1. 메시지 객체의 ID를 알림 추가 데이터에 넣는다

`com.kakao.talk.notification.ChatNotifier`의 알림 생성 경로에서 다음 연결을 확인했다.

```text
NotificationMessage.d()가 메시지 객체의 long 값을 반환
    ↓
ChatNotifier$a$b.getChatLogId()가 그 값을 반환
    ↓
알림에 넣을 개별 메시지의 추가 데이터 Bundle 확보
    ↓
ChatNotifier.a0(Bundle, long) 호출
    ↓
Bundle.putLong("chatLogId", 값)
```

실제 `ChatNotifier.a0`에는 문자열 상수 `"chatLogId"`와 `BaseBundle.putLong` 호출이 있었다. 따라서 진단 로그에서 단지 `number`로 표시되던 값의 실제 저장 타입이 **`Long`**임을 확인했다.

### 10.2. 같은 이름으로 값을 읽는다

`ChatNotifier.D(Bundle)`에서는 `BaseBundle.getLong("chatLogId")`를 호출한다. 이 읽기 경로에는 실패를 0으로 처리하는 분기도 있다. 후속 구현에서 필드 누락이나 잘못된 타입을 유효한 공통 ID `0`으로 뭉뚱그려서는 안 되는 이유이기도 하다.

### 10.3. 카카오톡도 이 값으로 기존 메시지를 찾는다

가장 중요한 증거는 `ChatNotifier$c$b.c(long)`의 비교 동작이다. 이 메서드는 알림의 메시지 목록을 순회하고, 각 메시지의 추가 데이터에서 `chatLogId`를 읽어 입력받은 값과 비교한다. 다르면 다음 메시지로 넘어가고, 같으면 해당 메시지를 찾은 경로로 진행한다.

아래는 확인한 동작을 읽기 쉽게 재구성한 의사 코드다. 카카오톡의 원본 Kotlin 소스나 모든 분기를 그대로 복원한 코드는 아니다.

```kotlin
fun findMessage(targetChatLogId: Long): Message? {
    for (message in notificationMessages) {
        val chatLogId = message.extras.getLong("chatLogId")
        if (chatLogId == targetChatLogId) {
            return message
        }
    }
    return null
}
```

이는 이름보다 강한 증거다. **카카오톡 자체가 이 값을 메시지 일치 여부를 판단하는 기준으로 사용**하고 있기 때문이다. 여기에 실제 수정 실험의 값 유지와 새 메시지의 값 변경이 결합되어, `chatLogId`가 개별 채팅 메시지 식별자 역할을 한다는 결론을 뒷받침한다.

재검증을 위해 핵심 역어셈블 명령도 남긴다. 아래는 `classes11.dex`의 `dexdump` 결과에서 주소·바이트·주석을 생략한 발췌다. `J`는 64비트 정수, `V`는 반환값 없음을 뜻한다.

```text
# ChatNotifier.a0: 이름을 지정해 long 값을 저장
const-string v0, "chatLogId"
invoke-virtual {v1, v0, v2, v3}, Landroid/os/BaseBundle;.putLong:(Ljava/lang/String;J)V

# ChatNotifier.D: 같은 이름으로 long 값을 조회
const-string v2, "chatLogId"
invoke-virtual {v3, v2}, Landroid/os/BaseBundle;.getLong:(Ljava/lang/String;)J

# ChatNotifier$c$b.c: 읽은 값과 대상 ID를 비교하고, 다르면 순회를 계속
invoke-static {v3, v2}, Lcom/kakao/talk/notification/ChatNotifier;.e:(Lcom/kakao/talk/notification/ChatNotifier;Landroid/os/Bundle;)J
move-result-wide v2
cmp-long v2, v2, v11
if-nez v2, 0013
```

마지막 발췌의 `e`는 위의 읽기 메서드 `D`로 연결되는 호출이다. 이 역어셈블 결과에서 저장 경로는 284826행 부근, 조회 경로는 282255행 부근, 비교 경로는 276254행 부근에 있다. 행 번호는 이번에 생성한 출력 파일에만 해당하며, 다른 도구나 옵션으로 출력하면 달라질 수 있다.

### 10.4. 함께 관찰한 세 필드

실제 개별 메시지 추가 데이터의 세 키도 대조했다.

| 키 이름 | 타입·관찰 내용 | 이 조사에서 확인한 범위 |
|---|---|---|
| `chatLogId` | `Long`, 메시지마다 달라지고 수정 전후 유지 | 코드의 저장·조회·대상 메시지 비교와 실험 결과를 함께 확인 |
| `flags` | 코드에서 `putInt`로 저장, 해당 실험의 값 해시는 숫자 `1`의 해시와 일치 | 개별 메시지의 플래그 필드임을 확인. 각 비트의 전체 의미는 미분석 |
| `threadId` | 코드에서 `putLong`으로 저장, 해당 실험의 값 해시는 숫자 `0`의 해시와 일치 | 필드 이름·타입과 null을 0으로 저장하는 경로 확인. 전체 스레드 동작은 미분석 |

여기의 **개별 메시지 `extras.flags`와 Android 알림 전체의 `Notification.flags`는 서로 다른 필드**다. 앞서 본 `0x11`, `0x19`, `ONLY_ALERT_ONCE`는 알림 전체의 플래그다. 두 종류를 혼동해 수정 여부를 판정해서는 안 된다.

## 11. 무엇이 증명됐고, 무엇이 남았는가

| 판단 | 근거와 범위 |
|---|---|
| 필드의 실제 이름은 `chatLogId`다 | 키 해시 일치와 앱 코드의 문자열 상수 일치 |
| 실제 타입은 `Long`이다 | `putLong` / `getLong` 호출 확인 |
| 개별 메시지를 식별하는 역할을 한다 | 카카오톡이 이 값으로 알림의 메시지를 검색·비교 |
| 관찰한 수정 전후에 값이 유지된다 | 20:26·20:36 두 차례 재현 |
| 같은 문구라도 새 메시지에서는 값이 달라진다 | 20:36 실험 및 앞선 별도 요청 대조 |
| 기존 Bridge가 갱신을 새 요청으로 처리했다 | `postTime` 등을 포함한 ID 계산 코드와 세 건의 처리·전송 로그 |
| 18:44 원 사건도 메시지 수정이 계기였을 가능성이 높다 | 수정 표시 제보와 이후 재현 패턴의 일치. 당시 수정 동작 자체는 직접 증명하지 못함 |

아직 다음을 보장할 수는 없다.

- 모든 카카오톡 버전·채팅 유형·발신자·기기에서 같은 필드가 항상 제공되는지.
- `chatLogId`가 방이나 계정을 넘어 전역적으로 유일한지.
- 재로그인·재설치·장기간 경과 후에도 어떤 범위에서 값이 유지되는지.
- 이 값 하나만 바꾸면 앱·서버 재시작이나 전송 실패까지 포함해 정확히 한 번 응답하는지.

따라서 조사 결론은 **‘현재 버전에서 메시지 식별에 사용할 근거를 확보했다’**이다. 전체 중복 처리 설계가 끝났다는 뜻은 아니다.

## 12. 후속 구현에 주는 의미

기존 방식은 알림 갱신과 메시지 정체성을 한 ID에 섞었다. 이후에는 두 정보를 분리하는 것이 타당하다.

```text
메시지 식별 기준: 채팅방 식별자 + chatLogId
내용 변경 비교: 해당 메시지 본문의 해시
```

방까지 조합하는 것은 아직 확인하지 않은 전역 유일성에 의존하지 않기 위한 설계 방향이다. 여러 Bridge 계정을 지원하게 된다면 계정·기기 범위도 검토해야 한다.

| 관찰된 입력 | 해석 방향 |
|---|---|
| 같은 메시지 식별값 + 같은 본문 | 기존 메시지의 알림 재게시·갱신. 새 질문을 만들지 않음 |
| 같은 메시지 식별값 + 달라진 본문 | 기존 메시지의 수정본 |
| 다른 메시지 식별값 | 본문이 같더라도 별개의 새 요청 |

이 해석을 전송 정책과 연결하는 작업은 별도로 남아 있다. 답변 생성 중 수정되면 이전 내용의 답변 전송을 어떻게 막을지, 이미 답변한 뒤의 수정에는 다시 답할지, 전송 직전 경쟁 상태와 재시작을 어떻게 처리할지 정해야 한다.

또한 `chatLogId`가 없거나 유효하지 않은 경우를 명시적으로 처리해야 한다. 기존의 `postTime + 본문` 방식으로 무조건 되돌아가면 같은 중복 문제가 다시 발생할 수 있다. 이번 문서에서는 그 정책을 확정하거나 구현하지 않는다.

아래 문서는 Android의 알림 구조를 이해하기 위한 자료다. 카카오톡 내부 필드인 `chatLogId`의 의미를 보증하는 문서는 아니며, 그 의미의 근거는 이번 앱 코드 분석과 실험이다.

- [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService)
- [Notification.MessagingStyle.Message](https://developer.android.com/reference/android/app/Notification.MessagingStyle.Message)
- [Notification.FLAG_ONLY_ALERT_ONCE](https://developer.android.com/reference/android/app/Notification#FLAG_ONLY_ALERT_ONCE)

이번 조사의 핵심은 ‘비슷해 보이는 알림을 합치자’에서 멈추지 않고, **무엇이 같은 메시지인지 나타내는 데이터를 찾아 실제 동작과 앱의 비교 코드 양쪽에서 검증했다**는 데 있다.
